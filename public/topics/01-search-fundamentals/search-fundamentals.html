01 What is Search?

Search is the problem of finding the most relevant items from a large collection given a user's query. It's the backbone of the internet, every database, every e-commerce site, every RAG pipeline.

🔍

Analogy: Imagine a massive warehouse with millions of boxes. A customer walks in and says, "I need something about Italian cooking for beginners." Search is the system that - in milliseconds - finds the 10 best boxes out of millions, ranks them by relevance, and hands them over. The art is in deciding what "best" means and doing it fast.

The Core Problem: Information Retrieval

Information Retrieval (IR) is the field of computer science concerned with finding material (usually documents) of an unstructured nature (usually text) that satisfies an information need from within large collections.

Key distinction: IR is about relevance, not just matching. A relevant result answers the user's underlying intent, not just the literal words they typed.

Full-Text Search vs Structured Queries

Full-Text Search

Search through the content of documents - articles, web pages, PDFs. The data is unstructured natural language.

"best Italian pasta recipes for beginners"

Techniques: BM25, TF-IDF, vector search, inverted indexes.

Structured Queries

Query structured data in databases using a formal language (SQL). Data is organized in rows and columns with defined schemas.

SELECT * FROM recipes WHERE cuisine = 'Italian' AND difficulty = 'easy'

Techniques: B-trees, hash indexes, query planners.

Why full-text search is harder:

Structured queries have exact answers - a row either matches the WHERE clause or it doesn't. Full-text search must deal with ambiguity, synonyms, typos, context, user intent, and ranking by degree of relevance. There's no binary "match" - only a spectrum of relevance.

The Inverted Index: How Retrieval Gets Fast

The foundational data structure of text search. Instead of scanning every document, we pre-build a lookup table: term → list of documents containing that term.

Example corpus:
Doc Content
D1 "the cat sat on the mat"
D2 "the dog chased the cat"
D3 "the mat was red"
Inverted index:
Term Posting List
cat D1, D2
sat D1
dog D2
mat D1, D3
red D3
chased D2

Query "cat mat" → intersect posting lists → D1 appears in both → rank D1 highest. No full scan needed.

📖

Analogy: An inverted index is like the index at the back of a textbook. Instead of reading every page to find "photosynthesis," you flip to the index, find "photosynthesis → pages 42, 87, 156" and go directly there. Without the index, you'd have to scan every page.

02 Vector Search / Semantic Search

Keyword search fails when users express the same idea with different words. Vector search solves this by understanding meaning, not just matching words.

🧠

Analogy: Keyword search is like looking up a word in a dictionary - you need the exact word. Semantic search is like asking a knowledgeable friend - they understand what you mean even if you use different words. "automobile" and "car" are far apart in a dictionary but close in a friend's understanding.

What Are Embeddings?

An embedding is a dense vector (a list of floating-point numbers) that represents the meaning of text in a high-dimensional space. Texts with similar meanings get vectors that are close together.

The key idea:

"King" - "Man" + "Woman" ≈ "Queen"

Embeddings capture semantic relationships as geometric relationships in vector space. Words and sentences that mean similar things live near each other, and the directions between them encode meaning.

Evolution of Embeddings

Model Year Dimension Key Innovation
Word2Vec 2013 100–300 Word-level embeddings via skip-gram / CBOW. Showed arithmetic on word vectors works
GloVe 2014 50–300 Global co-occurrence statistics. Better at capturing global patterns

BERT 2018 768 Bidirectional transformers. Deep contextual embeddings, but not great for sentences out of the box
Sentence-BERT 2019 384–768 Fine-tuned for sentence-level similarity using siamese networks

Key insight about dimensionality:

Real embeddings live in 384–3072 dimensions. We project them to 2D for visualization, which loses information. In high dimensions, the distances are far more expressive - many concepts that appear overlapping in 2D are actually well-separated in the full space.

Distance Metrics: How Do We Measure "Similar"?

Given two vectors \(\mathbf{a}\) and \(\mathbf{b}\), there are three main ways to measure their similarity:

$$\color{#6c63ff}{\text{Cosine Similarity}} = \frac{\mathbf{a} \cdot \mathbf{b}}{\|\mathbf{a}\| \; \|\mathbf{b}\|} = \frac{\sum_i a_i b_i}{\sqrt{\sum_i a_i^2} \;\cdot\; \sqrt{\sum_i b_i^2}}$$
Measures the angle between vectors. Range: [-1, 1]. Most common in NLP.
$$\color{#00c9a7}{\text{Dot Product}} = \mathbf{a} \cdot \mathbf{b} = \sum_i a_i b_i$$
Measures both direction and magnitude. Preferred when vector norms carry meaning (e.g., popularity).
$$\color{#ff6b6b}{\text{Euclidean Distance}} = \|\mathbf{a} - \mathbf{b}\| = \sqrt{\sum_i (a_i - b_i)^2}$$
Straight-line distance. Lower = more similar. Sensitive to magnitude.
When to use which metric:
Metric Best For Note
Cosine Text similarity, NLP Ignores magnitude - only cares about direction. A 3-word sentence and a 300-word paragraph can still be "close"
Dot Product Recommendation, MIPS When normalized vectors are used, equivalent to cosine. Faster to compute
Euclidean Spatial data, clustering Sensitive to scale - may need normalization first

Approximate Nearest Neighbor (ANN)

With millions of vectors, exact nearest-neighbor search (comparing the query against every vector) is too slow. ANN algorithms trade a tiny bit of accuracy for massive speed gains.

🗺️

Analogy: Imagine finding the closest coffee shop. Exact search means measuring the distance to every coffee shop on earth. ANN is like knowing "I'm in downtown Manhattan" and only checking shops in nearby neighborhoods. You might miss a shop 1 block outside your search zone, but you find a great one in 1ms instead of 1 hour.

HNSW

Hierarchical Navigable Small World graphs. Builds a multi-layer graph where each layer is a "skip list." Start at the top (sparse) layer, greedily navigate toward the query, then descend to finer layers.

Speed: O(log N)
Memory: High
Accuracy: Very high

IVF

Inverted File Index. Cluster vectors with k-means, then at query time only search the nearest clusters (called "probes"). More probes = better recall but slower.

Speed: O(N/k · nprobe)
Memory: Low
Accuracy: Good (tunable)

PQ

Product Quantization. Compress vectors by splitting them into sub-vectors and quantizing each to a codebook entry. Distances are approximated using lookup tables.

Speed: Very fast
Memory: Very low (32x compression)
Accuracy: Lower (lossy)

In practice, these are combined:

Production systems like FAISS use IVF + PQ for memory-constrained billion-scale search, or HNSW for highest quality. Pinecone, Weaviate, Qdrant, and Milvus all use HNSW as their default index.

ANN Tradeoff: Speed vs Recall

03 Hybrid Search

Neither keyword search (BM25) nor vector search alone is perfect. Hybrid search combines both to get the best of exact matching and semantic understanding.

Why Combine BM25 + Vector Search?

BM25 Failures

Query: "automobile maintenance tips"

BM25 misses a great article titled "Car Repair Guide for Beginners" - no overlapping keywords.

Vector Search Failures

Query: "error code NX-4872"

Vector search returns generic "error handling" articles. BM25 finds the exact error code instantly.

When hybrid beats either alone:
Scenario BM25 Vector Hybrid
Exact ID / code lookup Excellent Poor Excellent
Synonym-heavy query Poor Excellent Excellent
Mixed: technical term + concept Partial Partial Excellent
Rare domain-specific jargon Good Varies Excellent
Conversational / vague query Poor Good Good

Reciprocal Rank Fusion (RRF)

RRF is the most popular method for combining results from multiple retrieval systems. It's simple, effective, and requires no training:

$$\color{#6c63ff}{\text{RRF}(d)} = \sum_{r \,\in\, R} \frac{1}{\color{#ffd93d}{k} + \color{#00c9a7}{r(d)}}$$
\(R\) = set of rankers  •  \(\color{#00c9a7}{r(d)}\) = rank of doc \(d\) in ranker \(r\)  •  \(\color{#ffd93d}{k}\) = smoothing constant (typically 60)
How RRF works - step by step:

1. Get top-100 results from BM25 (each doc has a rank: 1, 2, 3, ...)

2. Get top-100 results from vector search (each doc has a rank: 1, 2, 3, ...)

3. For each unique doc, compute: score = 1/(k + rank_bm25) + 1/(k + rank_vector)

4. Sort all docs by their combined RRF score

5. A doc ranked #1 in both systems gets: 1/(60+1) + 1/(60+1) = 0.0328

6. A doc ranked #1 in BM25 but #50 in vector gets: 1/(60+1) + 1/(60+50) = 0.0255

Weighted Combination

An alternative to RRF is a weighted linear combination of normalized scores:

$$\color{#6c63ff}{\text{Score}(d)} = \color{#ffd93d}{\alpha} \cdot \hat{s}_{\text{BM25}}(d) \;+\; \color{#00c9a7}{(1 - \alpha)} \cdot \hat{s}_{\text{vector}}(d)$$
\(\color{#ffd93d}{\alpha}\) = weight for keyword relevance (0 to 1)  •  \(\hat{s}\) = min-max normalized score
RRF vs Weighted: When to use which?
Approach Pros Cons
RRF No score normalization needed, no tuning, robust Ignores score magnitude - rank #1 with score 0.99 and rank #1 with score 0.51 are treated the same
Weighted Uses actual score values, tunable per-domain Requires score normalization, needs tuning of \(\alpha\)

04 Precision & Recall

How do you know if your search system is actually good? Precision and recall are the fundamental metrics of information retrieval.

🎯

Analogy: A search engine is like a fishing net. Precision asks: "Of all the fish I caught, what fraction are the type I wanted?" Recall asks: "Of all the target fish in the lake, what fraction did my net catch?" A tiny, fine net might catch only target fish (high precision) but miss most of them (low recall). A massive net catches everything (high recall) but also catches a lot of junk (low precision).

Definitions

$$\color{#6c63ff}{\text{Precision}} = \frac{\text{Relevant} \cap \text{Retrieved}}{|\text{Retrieved}|}$$
Of everything you returned, how much was actually relevant?
$$\color{#00c9a7}{\text{Recall}} = \frac{\text{Relevant} \cap \text{Retrieved}}{|\text{Relevant}|}$$
Of everything that's relevant, how much did you find?
$$\color{#ffd93d}{\text{F1}} = 2 \cdot \frac{\text{Precision} \times \text{Recall}}{\text{Precision} + \text{Recall}}$$
Harmonic mean of precision and recall - balances both equally
Why harmonic mean, not arithmetic mean?

If precision = 1.0 and recall = 0.01, the arithmetic mean = 0.505 (sounds fine!). But the harmonic mean = 0.0198 (correctly shows the system is terrible). The harmonic mean penalizes extreme imbalance, which is exactly what we want - a system that's great at one metric but terrible at the other is not useful.

Beyond Precision & Recall: Ranking Metrics

Precision and recall treat search as a set problem - a doc is either retrieved or not. But ranking order matters. These metrics capture whether the best results appear at the top:

MRR - Mean Reciprocal Rank

$$\color{#6c63ff}{\text{MRR}} = \frac{1}{|Q|} \sum_{i=1}^{|Q|} \frac{1}{\text{rank}_i}$$

For each query, find the rank of the first relevant result. MRR averages 1/rank across all queries. Focuses entirely on the first correct answer - great for navigational queries ("take me to X").

Query First relevant at rank Reciprocal Rank
Q1 1 1/1 = 1.000
Q2 3 1/3 = 0.333
Q3 2 1/2 = 0.500

MRR = (1.000 + 0.333 + 0.500) / 3 = 0.611

MAP - Mean Average Precision

$$\color{#00c9a7}{\text{AP}(q)} = \frac{1}{|\text{Rel}|} \sum_{k=1}^{n} P(k) \cdot \text{rel}(k)$$

For each query: at every rank position where a relevant doc appears, compute precision at that cutoff. Average those. Then average across queries. Rewards systems that rank relevant docs higher.

Example: Results: [R, N, R, N, R] (R=relevant, N=not)

P@1 = 1/1 = 1.0, P@3 = 2/3 = 0.67, P@5 = 3/5 = 0.60

AP = (1.0 + 0.67 + 0.60) / 3 = 0.756

NDCG - Normalized Discounted Cumulative Gain

$$\color{#ffd93d}{\text{DCG}@k} = \sum_{i=1}^{k} \frac{2^{\text{rel}_i} - 1}{\log_2(i + 1)}$$
$$\color{#ffd93d}{\text{NDCG}@k} = \frac{\text{DCG}@k}{\text{IDCG}@k}$$

Unlike P/R (binary: relevant or not), NDCG supports graded relevance (e.g., 0 = irrelevant, 1 = somewhat relevant, 2 = highly relevant, 3 = perfect). The log denominator discounts results at lower positions. IDCG is the ideal (best possible) DCG - the ratio normalizes the score to [0, 1].

Example: Results with graded relevance: [3, 2, 0, 1]

DCG = (2³-1)/log₂2 + (2²-1)/log₂3 + (2⁰-1)/log₂4 + (2¹-1)/log₂5

DCG = 7/1 + 3/1.585 + 0/2 + 1/2.322 = 7 + 1.893 + 0 + 0.431 = 9.324

Which metric to use?
Metric Handles Graded Relevance? Position-Aware? Common Use Case
Precision@K No (binary) Only via cutoff Quick sanity check
Recall@K No (binary) Only via cutoff Retrieval stage evaluation
F1 No (binary) No Balanced set evaluation
MRR No (binary) Yes (first hit) Navigational / QA queries
MAP No (binary) Yes (all hits) General search evaluation
NDCG Yes (graded) Yes Web search, recommendations - gold standard

Common questions and answers:

Q: Why not just use vector search for everything?

A: Vector search can miss exact keyword matches (e.g., error codes, product IDs). It requires expensive embedding models and more storage. BM25 is faster, interpretable, and works out of the box without ML infrastructure.

Q: How does RRF work and why is k=60?

A: RRF assigns score 1/(k+rank) per ranker and sums. k=60 was found empirically in the original paper (Cormack et al., 2009) to work well - it smooths out the difference between high ranks so rank #1 vs #2 isn't as dramatic as it would be with k=1.

Q: What's the difference between bi-encoder and cross-encoder?

A: Bi-encoders embed query and doc independently → fast but less accurate (used for retrieval). Cross-encoders process query+doc together → slow but much more accurate (used for reranking top-k results).

Q: When would you prioritize recall over precision?

A: When the cost of missing a relevant item is high (legal discovery, medical screening, RAG where the LLM can filter noise). Prioritize precision when users see results directly (web search, e-commerce) and noise erodes trust.
