BM25: Zero to Hero

The complete interactive guide to the most important ranking algorithm in search

The Problem Term Frequency IDF TF-IDF BM25 Formula Parameters Saturation Playground Implementation Variants vs Semantic

01 The Problem

You have a collection of documents and a user types a query. How do you rank which documents are most relevant?

📚

Analogy: Imagine you're a librarian. Someone asks for books about "machine learning." You can't just count which book says "machine learning" the most - a 1000-page textbook will mention it more than a brilliant 20-page tutorial, but that doesn't make it more relevant. You also know that a book mentioning a rare, specific term is probably more relevant than one repeating a common word. BM25 formalizes this librarian intuition into math.

Why not just count word matches?

Problem 1: Longer docs win unfairly

A 10,000-word document mentions "python" 50 times. A 200-word doc mentions it 10 times. Raw count says the big doc is better, but the small one is 10x more focused on Python.

Problem 2: Common words dominate

The word "the" appears in every document. Matching on "the" tells you nothing. But matching on "eigenvalue"? That's very informative. Raw counting treats them equally.

Problem 3: Diminishing returns

If a doc mentions "cat" 100 times vs 50 times, is it really 2x more relevant? Probably not. After a point, more mentions don't add much. Raw counting is linear - but relevance isn't.

Problem 4: No principled scoring

Raw counts give you absolute numbers with no meaningful scale. Is a score of 47 good? Compared to what? We need a framework that produces comparable, meaningful scores.

BM25 solves all four problems. Let's build up to it step by step.

02 Term Frequency (TF)

The first building block: how often does the query term appear in a document?

$$\color{#6c63ff}{\text{TF}(t,\, d)} \;=\; \text{count of term } t \text{ in document } d$$
Raw Term Frequency

But raw TF has the diminishing returns problem. Common fixes:

Variant Formula Idea
Raw \( f(t,d) \) Just count occurrences
Log-scaled \( 1 + \log f(t,d) \) Compress high frequencies
Boolean \( \mathbb{1}_{[f(t,d) > 0]} \) Only care about presence
BM25-style \( \dfrac{f(t,d)}{k_1 + f(t,d)} \) Saturating - approaches but never reaches 1

The BM25-style TF is the key insight: it creates a saturation curve where the first few occurrences matter a lot, but additional ones give rapidly diminishing gains. We'll explore this in depth soon.

03 Inverse Document Frequency (IDF)

The second building block: how rare or common is this term across all documents?

💎

Analogy: Diamonds are valuable because they're rare. The word "the" is like sand - everywhere, worthless for search. The word "mitochondria" is like a diamond - rare, and finding it in a document tells you a LOT about what that document is about.

$$\color{#00c9a7}{\text{IDF}(t)} \;=\; \ln\!\left(\frac{\color{#ffd93d}{N}}{\color{#ff6b6b}{\text{df}(t)}}\right)$$
\(\color{#ffd93d}{N}\) = total documents  •  \(\color{#ff6b6b}{\text{df}(t)}\) = documents containing term \(t\)

BM25 uses a slightly different IDF formula (from Robertson-Sparck Jones):

$$\color{#00c9a7}{\text{IDF}_{\text{BM25}}(t)} \;=\; \ln\!\left(\frac{\color{#ffd93d}{N} - \color{#ff6b6b}{\text{df}(t)} + 0.5}{\color{#ff6b6b}{\text{df}(t)} + 0.5} + 1\right)$$
Prevents negative IDF values and handles edge cases
IDF intuition with numbers:
Term Docs containing it (of 10,000) IDF ≈ Meaning
"the" 9,950 0.005 Essentially zero - useless for ranking
"python" 500 3.0 Moderately informative
"asyncio" 25 6.0 Very informative - rare and specific
"eigendecomposition" 3 8.1 Extremely informative - highly targeted

04 TF-IDF: The Stepping Stone

Before BM25, there was TF-IDF - simply multiply TF by IDF:

$$\color{#6c63ff}{\text{TF-IDF}(t,\, d)} \;=\; \underbrace{\color{#6c63ff}{\text{TF}(t, d)}}_{\text{frequency in doc}} \;\times\; \underbrace{\color{#00c9a7}{\text{IDF}(t)}}_{\text{rarity across corpus}}$$
High score = term is frequent in this doc AND rare across all docs

Score!

TF-IDF was a huge leap forward, but it still has weaknesses:

No saturation

TF grows linearly (or log-linearly). 100 mentions vs 50 still matters too much.

No length normalization

Longer documents naturally have higher TF. TF-IDF doesn't correct for this.

BM25 fixes both. It's essentially a better-tuned, probabilistically-motivated version of TF-IDF.

05 The BM25 Formula

Here it is - the formula that powers Elasticsearch, Lucene, and most search engines on earth:

$$\color{#6c63ff}{\text{BM25}(q,\, d)} \;=\; \sum_{t \,\in\, q} \;\color{#00c9a7}{\text{IDF}(t)} \;\cdot\; \frac{\color{#6c63ff}{f(t,d)} \;\cdot\; \bigl(\color{#ffd93d}{k_1} + 1\bigr)}{\color{#6c63ff}{f(t,d)} \;+\; \color{#ffd93d}{k_1} \;\cdot\; \left(1 - \color{#ff6b6b}{b} + \color{#ff6b6b}{b} \;\cdot\; \dfrac{|d|}{\text{avgdl}}\right)}$$
Sum over each query term: IDF weight × saturating TF with length normalization

Breaking it down piece by piece

\(\color{#6c63ff}{f(t,\, d)}\) Raw term frequency - how many times term \(t\) appears in document \(d\)
\(\color{#00c9a7}{\text{IDF}(t)}\) Inverse document frequency - how rare term \(t\) is across the corpus
\(\color{#ffd93d}{k_1}\) TF saturation parameter (typically 1.2–2.0). Controls how quickly TF saturates
\(\color{#ff6b6b}{b}\) Length normalization parameter (0–1, typically 0.75). How much to penalize long docs
\(|d|\) Length of document \(d\) (in words/tokens)
\(\text{avgdl}\) Average document length across the whole corpus

The three layers of BM25

IDF: How rare is this term?
×
Saturating TF: How frequent (with diminishing returns)?
÷
Length norm: Adjust for document length
Why \((k_1 + 1)\) in the numerator?

This is a mathematical convenience. It ensures that when a term appears at least once (\(f \geq 1\)), the TF component is always \(\geq 1\) (rather than some fraction). Without it, the score would be between 0 and 1 - with it, the score ranges from \(0\) to \((k_1 + 1)\), which scales more meaningfully with IDF.

06 The Parameters: \(k_1\) and \(b\)

\(k_1\) - Saturation Control

Controls how quickly term frequency saturates.

\(k_1 = 0\) Binary model - only presence/absence matters
\(k_1 = 1.2\) Default - moderate saturation (most common)
\(k_1 = 2.0\) Slower saturation - extra occurrences still help
\(k_1 \to \infty\) No saturation - linear TF (like raw counting)

\(b\) - Length Normalization

Controls how much document length affects scoring.

\(b = 0\) No length normalization - ignore doc length entirely
\(b = 0.75\) Default - moderate penalty for long docs
\(b = 1.0\) Full normalization - strongly penalize long docs
When to tune these:

\(k_1\): Increase for verbose collections (news articles, books) where repetition indicates topicality. Decrease for short documents (tweets, titles) where one mention is enough.

\(b\): Decrease for collections with uniform document lengths. Increase when long docs tend to be less focused (e.g., web pages with lots of boilerplate).

09 Implementation from Scratch

Here's BM25 implemented in Python - every line maps to the math above:

import math
from collections import Counter

class BM25:
    def __init__(self, corpus, k1=1.2, b=0.75):
        self.k1 = k1
        self.b = b
        self.corpus = [doc.lower().split() for doc in corpus]
        self.N = len(self.corpus)
        self.avgdl = sum(len(d) for d in self.corpus) / self.N

        # Build document frequency table
        self.df = {}
        for doc in self.corpus:
            for term in set(doc):
                self.df[term] = self.df.get(term, 0) + 1

        # Pre-compute IDF for every term
        self.idf = {}
        for term, freq in self.df.items():
            self.idf[term] = math.log(
                (self.N - freq + 0.5) / (freq + 0.5) + 1
            )

    def score(self, query, doc_idx):
        doc = self.corpus[doc_idx]
        doc_len = len(doc)
        tf = Counter(doc)
        score = 0.0

        for term in query.lower().split():
            if term not in self.idf:
                continue

            f = tf[term]                      # raw TF
            idf = self.idf[term]              # pre-computed IDF

            # BM25 TF component with length normalization
            numerator = f * (self.k1 + 1)
            denominator = f + self.k1 * (
                1 - self.b + self.b * doc_len / self.avgdl
            )

            score += idf * numerator / denominator

        return score

    def rank(self, query, top_k=10):
        scores = [
            (i, self.score(query, i))
            for i in range(self.N)
        ]
        scores.sort(key=lambda x: x[1], reverse=True)
        return scores[:top_k]
# Usage
corpus = [
    "Machine learning is a subset of AI",
    "Deep learning uses neural networks",
    "BM25 is a ranking algorithm for search",
]

bm25 = BM25(corpus)
results = bm25.rank("machine learning")

for idx, score in results:
    print(f"Score: {score:.3f} | {corpus[idx]}")
Complexity:

Index building: \(\mathcal{O}(\text{total tokens})\) - done once.
Query time: \(\mathcal{O}(|q| \times D)\) naive, but with inverted indexes: \(\mathcal{O}(|q| \times \overline{L})\) where \(\overline{L}\) = avg posting list length.
Space: \(\mathcal{O}(|V| + D)\) where \(|V|\) = vocabulary size, \(D\) = number of documents.

10 BM25 Variants

Researchers have proposed improvements to the original BM25 (a.k.a. BM25 Okapi):

BM25+ (2011)

Adds a small constant \(\delta\) (typically 1) to the TF component. Solves the problem where BM25 can give a score of 0 to a document that contains the query term but is very long.

$$\text{TF}_{\text{BM25+}} \;=\; \underbrace{\frac{f(t,d) \cdot (k_1 + 1)}{f(t,d) + k_1 \cdot \bigl(1 - b + b \cdot \frac{|d|}{\text{avgdl}}\bigr)}}_{\text{original BM25 TF}} \;+\; \color{#ffd93d}{\delta}$$

BM25L (2011)

Modifies the length normalization to be less aggressive for long documents. Replaces \(f(t,d)\) with a boosted version:

$$f'(t,d) \;=\; \frac{f(t,d)}{1 - b + b \cdot \frac{|d|}{\text{avgdl}}} \;+\; \delta$$

BM25F (Field-aware)

Extends BM25 to handle structured documents with multiple fields (title, body, anchor text). Computes a weighted pseudo-TF across fields:

$$\tilde{f}(t,d) \;=\; \sum_{c \,\in\, \text{fields}} \frac{w_c \;\cdot\; f(t, d_c)}{1 - b_c + b_c \cdot \frac{|d_c|}{\text{avgdl}_c}}$$

Each field \(c\) gets its own boost \(w_c\) and length normalization \(b_c\). This is what Elasticsearch/Lucene uses for multi-field queries.

Variant Key Change Best For
BM25 (Okapi) Original General purpose - great default
BM25+ Floor on TF component Corpora with high length variance
BM25L Softer length penalty Long documents that are genuinely relevant
BM25F Per-field weights Structured docs (web pages, products)

11 BM25 vs Semantic Search

In the age of embeddings and LLMs, is BM25 still relevant? Absolutely.

Aspect BM25 Semantic (Dense Retrieval)
Matching type Exact keyword matching Meaning-based similarity
Handles synonyms No - "car" won't match "automobile" Yes - understands meaning
Handles typos No (without preprocessing) Often yes
Exact term matching Excellent - never misses an exact match Can miss exact matches (embedding noise)
Speed Extremely fast (inverted index) Slower (ANN search)
Index size Small Large (dense vectors)
No ML needed Works out of the box Needs embedding model + fine-tuning
Interpretable Yes - you can trace why each doc scored high Not really - embeddings are opaque

Hybrid Search: Best of Both Worlds

Modern search systems use hybrid retrieval: BM25 + semantic search combined. This is the approach used by systems like Elasticsearch with vector search, Pinecone hybrid, Weaviate, and RAG pipelines.

This hybrid approach consistently outperforms either method alone. BM25 catches exact matches that embeddings miss, while semantic search catches conceptual matches that BM25 misses.

Key takeaway:

BM25 isn't outdated - it's complementary. Even the most advanced RAG systems (like those powering ChatGPT's retrieval) use BM25 as a critical component. Learn it, use it, love it.
