The Challenge

Why Brute Force Doesn't Scale

Comparing a query against every vector in a database is O(N). At 1 billion vectors, that's billions of distance calculations per query. We need smarter data structures.

Click to search all 200 vectors one by one

Three Solutions

  • HNSW - navigate a multi-layer graph to find neighbors fast
  • IVF - cluster vectors, only search relevant clusters
  • PQ - compress vectors so they fit in memory
Algorithm 1

HNSW - Hierarchical Navigable Small World

Build a multi-layer graph where the top layers have few, long-range connections (highways) and the bottom layer has dense, short-range connections (local streets). Search starts at the top and greedily descends.

Click Search to traverse the graph

How HNSW Works

  • Layer 0 (bottom): Contains ALL vectors, connected to nearby neighbors
  • Layer 1: A subset of vectors with medium-range edges
  • Layer 2 (top): A few vectors with long-range "express" connections
  • Search: Start at the top layer, greedily move to the closest node, descend when stuck, repeat until the bottom layer
Key Insight

HNSW's layered structure is like airport routing: intercontinental flights (top layer) get you close, then regional flights (middle), then a taxi (bottom layer) takes you to the exact address. This gives O(log N) search time.

Algorithm 2

IVF - Inverted File Index

Partition the vector space into clusters using k-means. At query time, find the nearest cluster centroids and only search vectors in those clusters - skipping most of the database.

Vectors clustered into 6 partitions

How IVF Works

  • Index time: Run k-means to create nlist cluster centroids, assign each vector to its nearest centroid
  • Query time: Compare query to centroids (fast, only nlist comparisons), then search the nprobe closest clusters exhaustively
  • nprobe tradeoff: Higher nprobe = better recall but slower; lower nprobe = faster but might miss results
Key Insight

IVF is like a library with labeled sections. Instead of scanning every book, you go to the 1–2 relevant sections. With nlist=1000 and nprobe=10, you skip 99% of vectors!

Algorithm 3

PQ - Product Quantization

Compress high-dimensional vectors by splitting them into sub-vectors, clustering each group independently, and storing only the cluster IDs. This can reduce memory 48× while maintaining reasonable accuracy.

Watch how a 768-dim vector gets compressed

How PQ Works - Step by Step

  • Split: Divide each 768-dim vector into M=8 sub-vectors of 96 dims each
  • Train codebooks: For each sub-space, run k-means with 256 centroids (1 byte per ID)
  • Encode: Replace each sub-vector with its nearest centroid ID → 8 bytes total
  • Search: Precompute distances from query sub-vectors to all centroids, then use lookup tables for fast approximate distances
The Math

Original: 768 × 4 bytes (float32) = 3,072 bytes per vector.
After PQ with M=8, k=256: 8 × 1 byte = 8 bytes per vector.
Compression ratio: 384×! A billion vectors goes from 3 TB to ~8 GB.

In Production

Combining IVF + PQ + HNSW

Real systems mix these techniques. FAISS's IVF-PQ clusters vectors (IVF), compresses them (PQ), then searches fast. HNSW gives the best recall. Some systems use HNSW with PQ for rescoring.

Algorithm Speed Memory Recall Best For
HNSW ~1 ms @ 10M High (full vectors + graph) ★★★★★ Best recall, moderate scale
IVF ~2 ms @ 100M Medium ★★★★☆ Large scale, tunable speed/recall
PQ ~5 ms @ 1B Very Low (compressed) ★★★☆☆ Billion-scale, memory constrained
IVF-PQ ~3 ms @ 1B Very Low ★★★★☆ Production billion-scale (FAISS)
HNSW + PQ Rescore ~2 ms @ 100M Medium-Low ★★★★★ Best quality at scale (Vespa, Qdrant)
Production Rule of Thumb

Under 1M vectors? Brute force or HNSW is fine. 1M–100M? HNSW with PQ rescoring. 100M–1B+? IVF-PQ (FAISS) with proper nprobe tuning. Always benchmark on YOUR data - recall depends on how clustered your vectors are.
