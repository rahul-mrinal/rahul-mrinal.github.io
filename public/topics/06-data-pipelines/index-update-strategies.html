Full reindex, partial update, upsert, and alias swap

01 The Four Strategies

When your source data changes, you need to update the search index. There are four fundamental strategies, each with different trade-offs in speed, safety, and complexity.

🔄
Full Reindex
Rebuild everything from scratch
✏️
Partial Update
Update only changed fields
🔀
Upsert
Insert or update by ID
🎯
Alias Swap
Build new, swap atomically
📖

Book analogy: Full Reindex = reprint the entire book. Partial Update = use white-out and retype one paragraph. Upsert = replace a specific page. Alias Swap = print a new edition, then swap it onto the shelf while no one's looking.

02 Full Reindex

The simplest strategy: delete the old index, create a new one, and re-ingest every document from scratch.

Pros

  • Simplest to implement
  • Guarantees consistency — no stale data
  • Good for mapping/schema changes
  • No delta tracking needed

Cons

  • Slowest — must process every document
  • Resource-intensive (CPU, memory, I/O)
  • Downtime risk during rebuild
  • Doesn't scale beyond ~10M docs easily
# Full reindex — nuclear option
def full_reindex(source, index_name):
    new_index = create_index(index_name + "_v2")
    for batch in fetch_all(source, batch_size=1000):
        new_index.bulk_insert(batch)
    swap_alias(index_name, new_index)  # atomic switch
    delete_index(index_name + "_v1")    # cleanup
When to Use

Full reindex is the right choice when you're changing the index mapping/schema, have a small dataset (<1M docs), or need to guarantee zero stale data. Combine with alias swap to avoid downtime.

Speed Up Full Reindex

Disable replicas (number_of_replicas: 0), increase refresh interval (refresh_interval: -1), and use bulk API with 1000-2000 doc batches. Restore settings after the reindex completes. This alone can cut indexing time by 40-60%.

03 Partial Update

Update only the fields that changed, leaving the rest of the document intact. Fast for field-level changes, but requires knowing exactly what changed.

# Partial update — change only what's different
client.update(
    index="products",
    id="prod_123",
    body={
        "doc": {
            "price": 29.99,
            "stock_count": 42,
            "last_updated": "2024-03-15T10:30:00Z"
        }
    }
)

Advantages

  • Very fast — minimal data transferred
  • Low resource usage
  • Great for frequently changing fields (prices, stock)

Gotchas

  • Internally, Elasticsearch re-indexes the entire document anyway
  • Requires _source to be stored
  • Can't change field mappings
Pro Tip

Partial updates in Elasticsearch use optimistic concurrency via version numbers. If two updates hit the same doc, one will retry. Use retry_on_conflict: 3 to handle this automatically.

Scripted Updates

For computed fields, use server-side scripts to update values atomically without read-modify-write cycles:

# Scripted partial update — atomic increment
client.update(
    index="products",
    id="prod_123",
    body={
        "script": {
            "source": "ctx._source.view_count += params.inc",
            "params": { "inc": 1 }
        }
    }
)
Update TypeMethodUse Case
Field replacementdoc parameterPrice changes, status updates
Computed updatescript parameterCounters, aggregations, conditional logic
Conditional updateScript with ifOnly update if value is stale/lower

04 Upsert

The "insert or update" pattern. If the document exists, update it. If it doesn't, create it. This is the workhorse of incremental pipelines.

# Upsert — idempotent by design
client.update(
    index="products",
    id="prod_456",
    body={
        "doc": { "title": "Widget Pro", "price": 49.99 },
        "doc_as_upsert": true
    }
)

Why Upsert Wins for Pipelines

  • Idempotent: Run it once or ten times, same result
  • No existence check needed: The engine handles it
  • Works with bulk API: Efficient at scale
  • Handles both new and updated documents in one pass

indexOverwrites entire docCreates new doc
updateMerges fieldsError (404)
upsertMerges fieldsCreates new doc

05 Alias Swap

The gold standard for zero-downtime reindexing. Build a completely new index behind the scenes, then swap the alias pointer in a single atomic operation.

Before Swap
products (alias)
→
products_v1 (live)
placeholder
→
products_v2 (building…)
After Swap
products (alias)
→
products_v2 (live)
placeholder
→
products_v1 (delete or keep as backup)
# Atomic alias swap — zero downtime
client.indices.update_aliases(body={
    "actions": [
        { "remove": { "index": "products_v1", "alias": "products" }},
        { "add":    { "index": "products_v2", "alias": "products" }}
    ]
})

Key Benefits

  • Zero downtime: Users always query a complete, consistent index
  • Instant rollback: Just swap the alias back to the old version
  • Schema changes supported: New index can have different mappings
  • No partial data: Users never see a half-built index

Complete Alias Swap Procedure

# Full alias swap workflow
def alias_swap_reindex(client, alias, source_db):
    old_index = get_current_index(client, alias)
    new_index = f"{alias}_v{int(time.time())}"

    # 1. Create new index with optimized settings
    client.indices.create(new_index, body={
        "settings": { "refresh_interval": "-1", "number_of_replicas": 0 }
    })

    # 2. Bulk index all documents
    for batch in fetch_all(source_db, batch_size=1000):
        bulk_index(client, new_index, batch)

    # 3. Restore production settings
    client.indices.put_settings(new_index, body={
        "refresh_interval": "1s", "number_of_replicas": 1
    })

    # 4. Atomic swap
    client.indices.update_aliases(body={
        "actions": [
            { "remove": { "index": old_index, "alias": alias }},
            { "add":    { "index": new_index, "alias": alias }}
        ]
    })

    # 5. Keep old index for rollback (delete later)
    log(f"Swapped {old_index} → {new_index}")
🎭

Stage curtain analogy: Alias swap is like a theater stage with two sides on a revolving platform. While the audience watches Act 1 on the front stage, stagehands build the Act 2 set on the back. When ready, the platform rotates — the audience sees a seamless transition. If Act 2's set has a problem, rotate back instantly.

07 Delta Detection

Before you can do incremental updates, you need to know what changed. There are three main approaches.

Timestamps

Every record has an updated_at column. Query: WHERE updated_at > last_run. Simple but requires every table to have timestamps.

CDC (Change Data Capture)

Read the database's write-ahead log to capture every insert, update, and delete as it happens. Tools: Debezium, Maxwell, AWS DMS.

Checksums

Hash each record and compare with the last known hash. If different, re-index. Works with any data source but requires storing previous hashes.

Timestamp-based Delta Code

# Timestamp-based delta detection
def detect_changes_by_timestamp(db, last_run_time):
    query = """
        SELECT * FROM products
        WHERE updated_at > %s
        ORDER BY updated_at ASC
    """
    changed_docs = db.execute(query, [last_run_time])
    return changed_docs

# Checksum-based delta detection
def detect_changes_by_checksum(db, hash_store):
    all_docs = db.execute("SELECT id, * FROM products")
    changed = []
    for doc in all_docs:
        current_hash = hashlib.md5(json.dumps(doc).encode()).hexdigest()
        if hash_store.get(doc["id"]) != current_hash:
            changed.append(doc)
            hash_store[doc["id"]] = current_hash
    return changed
Handling Deletes

Timestamps can't detect deleted records — the row is gone. Solutions: use soft deletes (a deleted_at column), CDC (captures DELETE events), or full reconciliation (compare source IDs against index IDs, delete missing ones).

08 Hybrid Approach

Most production systems use a combination: a nightly batch reindex for consistency plus real-time deltas for freshness.

Real-time Layer

  • CDC captures changes within seconds
  • Upserts keep the live index current
  • Handles 95% of freshness needs
  • Low latency, high throughput

Batch Layer

  • Nightly full reindex catches anything missed
  • Fixes any drift or inconsistency
  • Applies schema/mapping changes
  • Alias swap ensures zero downtime
Lambda Architecture for Search

This pattern mirrors the Lambda Architecture from stream processing: a speed layer (real-time CDC) plus a batch layer (nightly reindex). The batch layer acts as the source of truth that corrects any inconsistencies from the speed layer.

Hybrid Implementation Skeleton

# Hybrid: Real-time CDC + Nightly Batch
class HybridIndexUpdater:
    def __init__(self, client, alias):
        self.client = client
        self.alias = alias

    def handle_cdc_event(self, event):
        """Real-time: process individual change events."""
        if event.op == "DELETE":
            self.client.delete(index=self.alias, id=event.doc_id)
        else:
            self.client.index(
                index=self.alias,
                id=event.doc_id,
                body=event.after
            )

    def nightly_reconcile(self, source_db):
        """Batch: full reindex with alias swap."""
        new_index = create_fresh_index(self.client)
        bulk_load_all(self.client, new_index, source_db)
        atomic_alias_swap(self.client, self.alias, new_index)
        cleanup_old_indices(self.client, keep_last=2)

When Real-time and Batch Disagree

Occasionally, the real-time layer and batch layer will have conflicting data. The resolution strategy is simple: batch wins. The nightly reindex reads from the source of truth (the database) and rebuilds a clean, consistent index. Any stale data from missed CDC events gets automatically corrected.

10 Key Takeaway

Remember This

There is no single "best" index update strategy — each has trade-offs. Alias swap is non-negotiable for zero-downtime production systems. Upsert is the workhorse for incremental pipelines. And the hybrid approach (real-time deltas + nightly batch) gives you the best of both worlds: freshness and consistency.

Quick Reference

  • Always use alias-based access — never query raw index names
  • Implement delta detection before building incremental pipelines
  • Test your rollback procedure — swap back should take <1 second
  • Monitor index lag: how far behind is the index from the source?
  • Use the hybrid approach for production systems with >1M documents
