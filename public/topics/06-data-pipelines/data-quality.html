01 Why Quality Matters

Bad data in your search index is worse than missing data. A missing product just doesn't appear. A product with the wrong price gets purchased at the wrong cost. A misspelled title never matches the right query.

🍳

Kitchen analogy: The best chef in the world can't make a great meal from rotten ingredients. No amount of ranking algorithm sophistication, query processing magic, or UI polish can compensate for bad data. Data quality is the foundation everything else builds on.

Costs of Bad Data

  • Users see irrelevant or wrong results
  • Search ranking is polluted by noise
  • Analytics and metrics become unreliable
  • Trust erodes — users stop using search

Benefits of Clean Data

  • Ranking algorithms work as designed
  • Facets and filters are accurate
  • Embeddings capture real meaning
  • Users trust and rely on search
The 1-10-100 Rule

Preventing a data quality issue costs $1. Detecting it costs $10. Correcting it after it's in production costs $100. Invest in upstream validation.

04 Schema Validation

Schema validation is your first line of defense. Reject documents that don't conform before they pollute the index. Think of it as a bouncer at the door — no ID, no entry.

What to Validate

Required Fields

Every document must have: id, title, body, category. Missing any of these? Reject immediately.

Type Checking

price must be a number. tags must be an array. published_at must be ISO 8601. No exceptions.

Value Constraints

price > 0. rating between 0-5. category in allowed set. Enum fields match known values.

Cross-field Rules

If status = "published", then published_at must not be null. If type = "bundle", then components must be non-empty.

# Schema validation with JSON Schema
schema = {
    "type": "object",
    "required": ["id", "title", "body", "category"],
    "properties": {
        "id":       { "type": "string", "minLength": 1 },
        "title":    { "type": "string", "minLength": 1 },
        "price":    { "type": "number", "minimum": 0 },
        "category": { "enum": ["electronics", "books", "clothing"] }
    }
}

Validation in Practice

# Schema validation with structured error reporting
from dataclasses import dataclass
from typing import List

@dataclass
class ValidationResult:
    passed: bool
    doc_id: str
    errors: List[str]

def validate_document(doc, schema):
    errors = []

    # Check required fields
    for field in schema["required"]:
        if field not in doc or doc[field] is None:
            errors.append(f"Missing required field: {field}")
        elif isinstance(doc[field], str) and len(doc[field].strip()) == 0:
            errors.append(f"Empty required field: {field}")

    # Check field types
    for field, rules in schema["properties"].items():
        if field in doc and doc[field] is not None:
            expected_type = rules.get("type")
            if not type_matches(doc[field], expected_type):
                errors.append(f"Type mismatch: {field} should be {expected_type}")

    return ValidationResult(
        passed=len(errors) == 0,
        doc_id=doc.get("id", "unknown"),
        errors=errors
    )
🛂

Airport security analogy: Schema validation is like airport security screening. Every passenger (document) must pass through the same checks: valid boarding pass (required fields), no prohibited items (type constraints), and matching identity (value ranges). Some checks are instant rejections; others just flag for review.

Validation Best Practices

  • Validate as early as possible — ideally at ingestion time
  • Separate hard failures (missing ID) from soft warnings (missing optional field)
  • Log validation failures with the full document for debugging
  • Version your schemas — they evolve as your data model grows
  • Test with production data samples, not just synthetic data

# Freshness monitoring with alerting
def check_freshness(source, max_age_minutes):
    last_update = source.get_last_updated()
    age_minutes = (now() - last_update).total_seconds() / 60

    if age_minutes > max_age_minutes * 2:
        alert_critical(f"{source.name} is {age_minutes:.0f}m stale")
        return "expired"
    elif age_minutes > max_age_minutes:
        alert_warning(f"{source.name} is {age_minutes:.0f}m stale")
        return "stale"
    return "fresh"
Why Freshness Matters

Stale inventory data causes overselling. Stale pricing causes revenue loss. Stale product descriptions cause customer frustration. Each data source has a different freshness SLA — define them explicitly and monitor against them.

06 Deduplication

Duplicate records pollute search results, waste storage, and confuse ranking. Near-duplicates are the hardest — slight variations in spelling, formatting, or casing that represent the same entity.

Similarity Scoring

Near-duplicate detection relies on computing a similarity score between pairs of records. Different fields contribute differently to the overall score:

# Weighted similarity scoring
def record_similarity(r1, r2):
    name_sim  = levenshtein_similarity(r1["name"], r2["name"])
    email_sim = levenshtein_similarity(r1["email"], r2["email"])
    phone_sim = 1.0 if r1["phone"] == r2["phone"] else 0.0

    # Weighted average — email is most reliable
    return (name_sim * 0.3) + (email_sim * 0.5) + (phone_sim * 0.2)

# Similarity > 0.75 → likely duplicate
# Similarity > 0.90 → almost certain duplicate

Deduplication Techniques

Exact Match

Hash the document or key fields. If hash matches, it's a duplicate. Fast, but misses near-duplicates.

Fuzzy Matching

Compare strings using Levenshtein distance, Jaccard similarity, or phonetic algorithms (Soundex). Catches typos and variations.

MinHash / LSH

Approximate similarity using locality-sensitive hashing. Scales to millions of records where pairwise comparison is infeasible.

Embedding Similarity

Generate vector embeddings and cluster by cosine similarity. Catches semantic duplicates even with very different wording.

Per-Document Checks

  • Schema conforms to definition
  • Required fields are non-empty
  • Data types match expectations
  • Values within valid ranges

Per-Batch Checks

  • Batch size within expected range
  • No more than 5% failures in batch
  • Field distributions look normal
  • No sudden drops in record count
# Quality gate — block batch if too many failures
def quality_gate(batch, threshold=0.95):
    results = [validate(doc) for doc in batch]
    pass_rate = sum(r.passed for r in results) / len(results)

    if pass_rate < threshold:
        alert(f"Quality below threshold: {pass_rate:.1%}")
        raise QualityGateError(pass_rate)

    good = [doc for doc, r in zip(batch, results) if r.passed]
    bad  = [doc for doc, r in zip(batch, results) if not r.passed]
    send_to_dlq(bad)
    return good
Pro Tip

Track quality metrics over time. A sudden drop in completeness often means a source system changed its schema without telling you. Set up alerts on quality score derivatives, not just absolute values.

Monitoring Quality Over Time

Quality isn't a one-time check — it's a continuous signal. Track these metrics as time series and set up dashboards and alerts.

Leading Indicators

  • Schema validation failure rate per source
  • Null rate per required field
  • Freshness lag per data source
  • New duplicate clusters per day

Lagging Indicators

  • User-reported wrong results
  • Zero-result query rate increasing
  • Click-through rate dropping
  • Support tickets about stale data
# Quality score time-series tracking
def record_quality_metrics(batch_results, metrics_store):
    scores = {
        "timestamp":     now(),
        "schema_score":  batch_results.schema_pass_rate,
        "completeness":  batch_results.completeness_rate,
        "freshness":     batch_results.freshness_score,
        "uniqueness":    batch_results.uniqueness_rate,
        "overall":       batch_results.overall_score,
    }
    metrics_store.push(scores)

    # Alert on sudden drops
    prev = metrics_store.get_previous()
    if prev and scores["overall"] < prev["overall"] - 0.1:
        alert(f"Quality dropped {(prev['overall'] - scores['overall'])*100:.1f}%")

08 Key Takeaway

Remember This

Data quality is not a feature you add at the end — it's a practice you embed throughout the pipeline. Validate at ingestion (schema gates), monitor continuously (freshness checks), and deduplicate proactively. The goal isn't perfection — it's measurable, improving quality with clear thresholds and alerts.

Quality Checklist

  • Schema validation rejects structurally invalid documents
  • Required fields are enforced with hard gates
  • Freshness is monitored with SLA thresholds per source
  • Near-duplicate detection runs before indexing
  • Quality scores are tracked as time-series metrics
  • Circuit breakers halt the pipeline when quality degrades
