01 Why Data Pipelines Matter for Search

Your search system is only as good as the data it indexes. The most sophisticated ranking algorithm in the world is useless if the data feeding it is stale, incomplete, or corrupt. The pipeline is the backbone of every search system.

🏗️

Analogy: Think of a search engine like a restaurant. BM25 and vector search are the chefs - they create the final experience. But the data pipeline is the entire supply chain: sourcing ingredients, quality checking, prepping, and delivering them to the kitchen on time. If the supply chain breaks, the restaurant closes - no matter how talented the chef is.

The pipeline is the invisible backbone

When users complain about search quality, the root cause is often not the ranking algorithm - it's the data pipeline. Here's why:

Stale Index = Bad Results

A product was discontinued 3 hours ago but still shows up in search. A new article was published but won't appear until the nightly batch runs. Users lose trust fast.

Pipeline Failures = Search Outages

If your indexing pipeline crashes silently and nobody notices for 12 hours, your search index drifts further from reality with every passing minute. Partial failures are even worse - some documents update, others don't.

Bad Data In = Bad Results Out

HTML tags in your text fields, null prices, duplicate records, broken encodings - these all degrade search quality. The pipeline is where you catch and fix these.

Schema Drift = Silent Corruption

The upstream database added a new column, renamed a field, or changed a date format. If your pipeline doesn't handle this, you'll index garbage - and might not even notice.

When asked about search architecture, always start with the pipeline. Most candidates jump straight to ranking algorithms. What makes search pipelines special

Search pipelines have unique requirements compared to general data pipelines:

The most fundamental architectural decision in any search pipeline: how frequently do you update your index?

Hybrid: The production-grade answer

🔄

The real-world pattern: Almost every production search system uses a hybrid approach - real-time for incremental updates (keeps the index fresh) plus periodic batch for full reindex (catches anything the real-time stream missed and corrects drift). The batch acts as a "consistency checkpoint" - like reconciling your bank statement monthly even though you track expenses daily.

Extract: Getting the data out

The extraction strategy depends on your source system. Each has different tradeoffs:

Source Type Extraction Method Considerations
Relational DB SQL queries, CDC (Debezium), logical replication Watch for lock contention on production DB. Use read replicas. CDC avoids full table scans.
REST API Paginated GET requests, webhook subscriptions Rate limiting, pagination cursors, API versioning. Webhooks preferred for real-time.
File stores S3 listing + download, filesystem watch Track processed files to avoid re-processing. Handle partial uploads.
Event streams Kafka consumer, SQS polling Consumer group management, offset tracking, exactly-once vs at-least-once.
NoSQL (MongoDB) Change streams, periodic full export Change streams are like CDC. Beware of oplog size limits.
CDC (Change Data Capture) - the gold standard for extraction

Instead of repeatedly querying the database, CDC captures every INSERT, UPDATE, and DELETE as it happens by reading the database's write-ahead log. Tools like Debezium stream these changes into Kafka topics in real-time. This gives you:

  • Zero impact on source database performance
  • Guaranteed capture of every change (no polling gaps)
  • Ordered event stream with before/after values
  • Natural fit for the real-time ingestion path

Transform: Making data search-ready

Raw data is never directly indexable. The transform stage is where you shape it for search:

Cleaning
  • Strip HTML tags, scripts, CSS
  • Fix broken Unicode/encoding
  • Remove null/empty fields
  • Deduplicate records
  • Validate required fields exist
Normalizing
  • Standardize dates to ISO 8601
  • Normalize prices to cents (integers)
  • Lowercase and trim text fields
  • Canonicalize categories/tags
  • Map external IDs to internal IDs
Enriching
  • NER (named entity recognition)
  • Language detection
  • Sentiment analysis
  • Geo-coding addresses → lat/lon
  • Taxonomy classification
Embedding Generation
  • Dense vector embeddings for semantic search
  • Batch inference with GPU workers
  • Cache embeddings to avoid recomputation
  • Handle model versioning
  • Chunking strategies for long docs

04 Processing Structured Data

Structured data - database records, product catalogs, user profiles - is the most common data source for search systems. The main challenge is mapping relational schemas to flat search index documents.

The denormalization problem

Relational databases are normalized - data is split across tables to avoid duplication. But search indexes are flat - each document must contain all the fields needed for search and display. This fundamental mismatch is the core challenge.

🗃️

Analogy: A relational database is like a filing cabinet with cross-references - "for the customer's address, see drawer 3, folder 7." A search index is like a stack of index cards - each card must be self-contained with ALL the information you'd ever want to show or filter on. The pipeline's job is to "flatten" the filing cabinet into self-contained cards.

Relational (Source) 
-- 4 normalized tables
products: id, title, price, brand_id, cat_id
brands: id, name, country
categories: id, name, parent_id
reviews: id, product_id, rating, text
Denormalized (Search Index)

Join strategies for search denormalization

Strategy 1: Pre-join in SQL (recommended for batch)

Write a single SQL query that JOINs all tables and produces the denormalized output. Run it as a batch job.

SELECT
  p.id,
  p.title,
  p.price * 100 AS price_cents,
  b.name AS brand_name,
  b.country AS brand_country,
  c.name AS category,
  AVG(r.rating) AS avg_rating,
  COUNT(r.id) AS review_count
FROM products p
JOIN brands b ON p.brand_id = b.id
JOIN categories c ON p.category_id = c.id
LEFT JOIN reviews r ON r.product_id = p.id
GROUP BY p.id, p.title, p.price, b.name, b.country, c.name;
Strategy 2: Application-level enrichment (for real-time)

When a product changes, fetch the product row, then separately look up brand, category, and aggregate reviews in the application layer before indexing.

async def build_search_doc(product_id):
    product = await db.fetch_one("SELECT * FROM products WHERE id = $1", product_id)
    brand = await db.fetch_one("SELECT * FROM brands WHERE id = $1", product["brand_id"])
    reviews = await db.fetch_one(
        "SELECT AVG(rating) as avg_r, COUNT(*) as cnt FROM reviews WHERE product_id = $1",
        product_id
    )
    return {
        "id": product["id"],
        "title": product["title"].strip().lower(),
        "price_cents": int(product["price"] * 100),
        "brand_name": brand["name"],
        "avg_rating": float(reviews["avg_r"] or 0),
        "review_count": reviews["cnt"],
    }
Strategy 3: Materialized views (compromise)

Create a materialized view in the database that pre-joins the data. Refresh it periodically and read from it during indexing. This keeps the complex join logic in SQL but avoids the performance hit of running it during every real-time update.

Data normalization examples

Raw Value Problem Normalized
"$129.99" String, not numeric 12999 (cents integer)
"03/15/2024" Ambiguous locale format "2024-03-15T00:00:00Z"
"Electronics" / "electronics" / "ELECTRONICS" Inconsistent casing "electronics"

Pro tip - "cascading updates" question:

When someone asks "what happens when a brand name changes?", the answer is: in a denormalized search index, you must re-index every product belonging to that brand. This is the tradeoff of denormalization: write amplification. In a batch system, no problem - the next full reindex picks it up. In real-time, you need a mechanism to fan out: brand_update → find all products with that brand_id → re-index each one. This is why hybrid architectures work well: real-time handles the common case (product updates), batch handles the rare but expensive case (brand/category changes).

Chunking strategies for vector search

When documents are too long for a single embedding (most embedding models have a 512-token limit), you must split them into chunks. How you chunk dramatically affects retrieval quality.

Fixed-size chunking

Split every N tokens with M token overlap. Simple but can cut sentences mid-thought.

def fixed_chunks(text, chunk_size=256, overlap=64):
    tokens = text.split()
    chunks = []
    for i in range(0, len(tokens), chunk_size - overlap):
        chunk = " ".join(tokens[i:i + chunk_size])
        chunks.append(chunk)
    return chunks
Semantic chunking

Split at natural boundaries: paragraphs, section headers, sentence boundaries. Preserves meaning but produces variable-length chunks.

Recursive / hierarchical chunking (LangChain-style)

Try splitting by \n\n (paragraphs) first. If chunks are still too big, split by \n (lines). If still too big, split by sentences. Maintains as much context as possible.

Strategy Chunk Size Overlap Pros Cons
Fixed-size 256–512 tokens 64–128 tokens Simple, predictable Can split mid-sentence
Sentence-based 3–5 sentences 1 sentence Natural boundaries Uneven sizes
Paragraph-based 1–3 paragraphs Shared context Preserves topic coherence Very variable sizes
Recursive Configurable max Configurable Best quality More complex logic
$$\text{Chunk Overlap Ratio} = \frac{\text{overlap tokens}}{\text{chunk size}} \approx 0.1 - 0.25$$
Typical overlap ratios: 10-25% of chunk size to preserve context across boundaries

Embedding generation at scale

Generating embeddings is often the most expensive step in the pipeline - both in compute and latency.

# Batch embedding generation with caching
from sentence_transformers import SentenceTransformer
import hashlib, json, redis

model = SentenceTransformer("all-MiniLM-L6-v2")
cache = redis.Redis()

def get_embedding(text, model_version="v1"):
    cache_key = f"emb:{model_version}:{hashlib.md5(text.encode()).hexdigest()}"
    cached = cache.get(cache_key)
    if cached:
        return json.loads(cached)

    embedding = model.encode(text).tolist()
    cache.set(cache_key, json.dumps(embedding), ex=86400 * 7)
    return embedding

def batch_embed(chunks, batch_size=64):
    results = []
    for i in range(0, len(chunks), batch_size):
        batch = chunks[i:i + batch_size]
        embeddings = model.encode(batch, batch_size=batch_size)
        results.extend(embeddings)
    return results

For every unstructured document, extract as many structured metadata fields as possible. These enable filtering and faceted search - users searching for "quarterly report" want to filter by date, author, and department, not just full-text match.

06 Index Update Strategies

How you apply changes to your search index determines latency, consistency, and availability. This is one of the most important operational decisions in search engineering.

Full reindex vs partial update vs upsert

Strategy Mechanism Latency Consistency Complexity When to Use
Full Reindex Build entirely new index, swap alias High Perfect Low Schema changes, major data migration, periodic consistency fix
Partial Update Update specific fields of existing docs Low Good Medium Price changes, stock updates, view counts
Upsert Insert if new, update if exists Low Good Medium Real-time event processing, CDC streams
Delete + Reinsert Remove old doc, add new version Low Risk of gap Low Simple systems, small indexes

Step 1: Create new index with updated mapping

PUT /products-v3 with the new schema. The old index continues serving traffic undisturbed.

Step 2: Run full reindex into the new index

The ETL pipeline writes all documents to products-v3. This can take minutes to hours.

Step 3: Validate the new index

Run document count checks, sample queries, and data quality tests against products-v3.

One API call: remove alias from products-v2, add to products-v3. Zero queries are lost.

Step 5: Clean up old index

Keep products-v2 around briefly for rollback, then delete it to reclaim disk space.

Optimistic concurrency control

When multiple pipeline workers update the same document concurrently, you need to prevent stale writes from overwriting fresh data.

Version-based concurrency

Every document has a version number or sequence number. When you update, you specify "only apply this update if the current version is X." If another writer already incremented the version, your update is rejected and you must re-fetch and retry.

# Elasticsearch: update with seq_no + primary_term
PUT /products/_doc/123?if_seq_no=5&if_primary_term=1
{
  "title": "Updated Running Shoes",
  "price_cents": 14999
}
// Returns 409 Conflict if seq_no has changed

Handling deletions

Hard delete (risky)

Immediately remove the document from the index. Problem: if a real-time update arrives for a just-deleted doc, it might re-create it as a "zombie."

Soft delete + cleanup (recommended)

Mark documents as deleted: true, filter them out at query time, then periodically run a cleanup job to actually remove them. This avoids race conditions between delete and update events.

Refresh intervals and near-real-time search

In Elasticsearch and Lucene, documents aren't searchable immediately after indexing. They become visible after a "refresh" - which creates a new search segment.

$$\text{Search Visibility Delay} = \text{Pipeline Latency} + \text{Refresh Interval}$$
Default ES refresh_interval is 1 second. Increase it during bulk indexing for better throughput.
Refresh Interval Throughput Latency Use Case
1s (default) Good ~1s visibility Normal operations
30s Better ~30s visibility Heavy indexing workloads
-1 (disabled) Best Manual refresh only Bulk reindex, then refresh once at the end

Post-load sanity checks

def post_reindex_validation(es, new_index, old_index, threshold=0.95):
    new_count = es.count(index=new_index)["count"]
    old_count = es.count(index=old_index)["count"]

    ratio = new_count / old_count if old_count > 0 else 0
    if ratio < threshold:
        raise ValueError(
            f"Doc count dropped {(1-ratio)*100:.1f}%: "
            f"{old_count} → {new_count}. Aborting alias swap."
        )

    # Sample query test
    sample_queries = ["shoes", "laptop", "coffee maker"]
    for q in sample_queries:
        results = es.search(index=new_index, query={"match": {"title": q}})
        if results["hits"]["total"]["value"] == 0:
            raise ValueError(f"Canary query '{q}' returned 0 results!")

    return True

Data freshness monitoring

Freshness SLA formula
$$\text{Data Freshness} = t_{\text{now}} - \max\bigl(t_{\text{source\_updated}}\bigr)$$

Track the timestamp of the most recently indexed document. If the gap between "now" and "most recent source update" exceeds your SLA, fire an alert. A stale pipeline might still be "running" - just not processing new data.

Idempotency and delivery semantics

🔑

Idempotency: Processing the same message twice should produce the same result as processing it once. This is critical because retries and at-least-once delivery are facts of life in distributed systems. If your pipeline isn't idempotent, you'll get duplicate or corrupted documents.

Semantic Guarantee How to achieve Tradeoff
At-most-once Messages may be lost, never duplicated Commit offset before processing Data loss risk - almost never acceptable for search
At-least-once Messages never lost, may be duplicated Commit offset after processing; retry on failure Must handle duplicates - use document ID as idempotency key
Exactly-once Messages processed exactly once Transactional consumers + idempotent producers (Kafka transactions) Higher latency, more complex infrastructure
Practical tip:

At-least-once + idempotent writes is the sweet spot for search pipelines. Since search engines use document IDs, upserting the same document twice is a no-op. You get the simplicity of at-least-once with the correctness of exactly-once for free - as long as your transforms are deterministic (same input always produces the same output).

Retry strategies

Exponential backoff with jitter
$$\text{delay} = \min\bigl(\text{base} \times 2^{\text{attempt}} + \text{random}(0, \text{jitter}),\; \text{max\_delay}\bigr)$$ 
import random, time

def retry_with_backoff(fn, max_retries=5, base=1, max_delay=60):
    for attempt in range(max_retries):
        try:
            return fn()
        except Exception as e:
            if attempt == max_retries - 1:
                send_to_dlq(e)
                raise
            delay = min(base * 2 ** attempt + random.uniform(0, 1), max_delay)
            time.sleep(delay)

When your data grows from thousands to millions (or billions) of documents, every part of the pipeline needs to scale. This section covers the key patterns and knobs.

🍕

You can't make one pizza faster by using a bigger oven (vertical scaling has limits), but you can cook 10 pizzas simultaneously in 10 ovens (horizontal scaling). The "partition" is how you decide which pizza goes to which oven - by topping type, by table number, etc.

Partition key selection is critical

The partition key determines which worker processes which messages - and guarantees ordering within a partition.

Partition Key Ordering Guarantee Balance Use Case
document_id All updates for a doc → same partition → ordered Good Default choice for most search pipelines
tenant_id All updates for a tenant → same partition Varies Multi-tenant systems with per-tenant indexes
random / round-robin No ordering Perfect When ordering doesn't matter (idempotent upserts)

Kafka consumer groups

Kafka consumer groups enable horizontal scaling of stream processors. Each consumer in a group reads from a unique subset of partitions.

$$\text{Max Parallelism} = \min(\text{num\_partitions},\; \text{num\_consumers})$$
Adding consumers beyond the partition count provides no benefit - extra consumers sit idle
Partitions Consumers Behavior
6 3 Each consumer reads 2 partitions - good utilization
6 6 Each consumer reads 1 partition - maximum parallelism
6 9 6 active + 3 idle - wasted resources

Backpressure handling

Backpressure occurs when the pipeline can process data slower than it arrives. Without handling it, you get OOM crashes, increasing lag, and eventually data loss.

Healthy pipeline

Processing rate ≥ ingestion rate. Consumer lag is stable and near zero. Memory usage is flat.

Ingestion: 5K/s
→
Processing: 6K/s
→
Lag: ~0
Backpressured pipeline

Processing rate < ingestion rate. Consumer lag grows linearly. Eventually, Kafka retention evicts unread messages.

Ingestion: 10K/s
→
Processing: 3K/s
→
Lag: ↑↑↑
Backpressure mitigation strategies:
Strategy How it works
Auto-scale consumers Monitor lag, spin up more consumer instances when lag exceeds threshold
Increase batch size Process more docs per bulk request - reduces per-doc overhead
Rate limiting at source Slow down producers when consumers can't keep up
Priority queues Critical updates (price changes) in high-priority topic, less critical (view counts) in low-priority
Drop stale updates If multiple updates for same doc are queued, skip to the latest
Increase partitions More partitions = more parallel consumers (but can't easily decrease later)

Batch size tuning

The bulk API batch size dramatically affects throughput. Too small = too much overhead per request. Too large = high memory usage and timeouts.

$$\text{Throughput} = \frac{\text{batch\_size}}{\text{batch\_latency}} \times \text{num\_workers}$$
Optimize batch_size to maximize this ratio without hitting memory limits
Batch Size Throughput Memory Failure Impact
10 docs Low - too much HTTP overhead Minimal Only 10 docs to retry
500 docs Good - sweet spot for most systems Moderate Acceptable retry cost
5,000 docs High - good for bulk reindex High Large retry batches
50,000 docs Diminishing returns Very high OOM risk, timeout risk
Practical batch size tuning process:
  1. Start with 500 documents per bulk request
  2. Measure throughput (docs/sec) and p99 latency
  3. Double the batch size, measure again
  4. Keep doubling until throughput stops improving or latency becomes unacceptable
  5. Also monitor: bulk request payload size should stay under 10-15MB

Memory management

Common memory pitfalls in search pipelines:
Problem Cause Solution
OOM on bulk index Loading all docs in memory before sending Use generators / streaming - process and send in chunks
Embedding cache bloat Caching all embeddings in process memory Use external cache (Redis) with TTL, or LRU with size limit
Large document accumulation Slow consumer + fast producer → messages pile up Bound internal queues, apply backpressure upstream
PDF extraction spike One 500-page PDF consumes gigabytes during parsing Set per-document memory limits, process large docs in subprocess

Summary: The pipeline checklist

When designing or reviewing a search pipeline, walk through this mental checklist:

  1. Source: What data sources? How do you extract changes? CDC, polling, webhooks?
  2. Transport: Kafka, SQS, or direct? Partitioning strategy? At-least-once?
  3. Transform: What cleaning, normalization, enrichment? Embedding generation?
  4. Load: Bulk or single-doc? Batch size? Upsert or full reindex?
  5. Zero-downtime: Using aliases? Validation before swap?
  6. Monitoring: Throughput, latency, error rate, freshness dashboards?
  7. Error handling: DLQ? Retry with backoff? Idempotent writes?
  8. Scaling: Partition count? Consumer group size? Auto-scaling policy?
