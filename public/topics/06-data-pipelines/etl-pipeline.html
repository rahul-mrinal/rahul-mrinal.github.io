01 The Assembly Line Analogy

An ETL pipeline is exactly like a factory assembly line. Raw materials enter one end, each station performs a single well-defined job, and finished products emerge at the other end.

🏭

Factory floor: Station 1 receives raw metal sheets (Extract). Station 2 cuts, bends, and polishes them (Transform). Station 3 packages and ships the final product (Load). If a sheet is warped, it's pulled off the line — not jammed through.

Why separate stages?

  • Each stage can be tested independently
  • Stages can scale horizontally on their own
  • Failures are isolated and debuggable
  • Different teams can own different stages

Single Responsibility

Each station does one job well. Extract doesn't clean data. Transform doesn't write to the index. Load doesn't fetch from APIs. Clean boundaries prevent cascading failures.

02 Extract

The first stage pulls raw data from source systems. The goal is to get data out reliably without transforming it — preserving the original form so nothing is lost.

Common Data Sources

Databases

PostgreSQL, MySQL, MongoDB. Use CDC (Change Data Capture) or periodic queries to pull new/updated records.

APIs

REST, GraphQL, webhooks. Paginate through results, handle rate limits, manage auth tokens.

Files

CSV, JSON, XML, PDFs. Watch directories or S3 buckets for new arrivals. Parse with schema awareness.

Extraction Patterns

Extraction Code Pattern

# Incremental extraction with checkpointing
class IncrementalExtractor:
    def __init__(self, source, checkpoint_store):
        self.source = source
        self.checkpoints = checkpoint_store

    def extract(self, batch_size=1000):
        last_id = self.checkpoints.get("last_extracted_id", 0)
        while True:
            batch = self.source.query(
                "SELECT * FROM docs WHERE id > %s ORDER BY id LIMIT %s",
                [last_id, batch_size]
            )
            if not batch:
                break
            yield batch
            last_id = batch[-1]["id"]
            self.checkpoints.save("last_extracted_id", last_id)
Key Principle

Extract should be idempotent and resumable. If it fails halfway through, you should be able to restart without duplicating data. Use cursor-based pagination and checkpoint offsets.

Rate Limiting

When extracting from external APIs, always implement rate limiting with token buckets. A common pattern: 100 requests/minute with a burst capacity of 10. Back off exponentially if you hit 429 (Too Many Requests) responses.

03 Transform

The transform stage is where raw data becomes search-ready. This is the heart of the pipeline — cleaning, normalizing, and enriching documents.

Common Transformations

Clean

  • Strip HTML tags and special characters
  • Fix encoding issues (UTF-8 normalization)
  • Remove duplicate whitespace
  • Handle null/missing fields

Normalize

  • Lowercase text fields
  • Standardize date formats (ISO 8601)
  • Unify currency/units
  • Map categories to canonical values

Enrich

  • Add computed fields (word count, reading time)
  • Geo-code addresses
  • Generate embeddings for semantic search
  • Extract entities (NER)

Validate

  • Check required fields exist
  • Verify data types match schema
  • Ensure values are within expected ranges
  • Flag or reject invalid documents

Transform Pipeline Pattern

# Chain of transformations — each function is independent
def transform_pipeline(doc):
    transforms = [
        strip_html,
        normalize_encoding,
        lowercase_text_fields,
        standardize_dates,
        parse_price,
        split_category,
        compute_word_count,
        validate_schema,
    ]
    for fn in transforms:
        doc = fn(doc)
        if doc is None:
            return None  # rejected by validation
    return doc

Transform Rules of Thumb

  • Pure functions: Each transform takes a doc in, returns a doc out. No side effects.
  • Fail early: Validate before expensive operations like embedding generation.
  • Log everything: Record what changed so you can debug issues downstream.
  • Test with production data: Synthetic test data never covers all the edge cases you'll encounter in the real world.

04 Load

The final stage pushes transformed documents into the search index. Done poorly, this can be the bottleneck of the entire pipeline.

Loading Strategies

StrategyDescriptionThroughput
Single insertIndex one document at a time~50 docs/sec
Bulk insertBatch 500-5000 docs per request~5,000 docs/sec
Parallel bulkMultiple bulk workers concurrently~20,000+ docs/sec

Bulk Indexing Best Practices

  • Batch size: 500-2000 docs per batch (tune by testing)
  • Disable refresh: Set refresh_interval=-1 during bulk load
  • Increase replicas after: Set replicas to 0 during load, restore after
  • Monitor queue size: Watch for rejected execution exceptions
Pro Tip

Use alias swapping for zero-downtime reindexing. Build the new index in the background, then atomically swap the alias pointer. Users never see partial data.

Bulk Loading Code

# Efficient bulk loading with error handling
from elasticsearch.helpers import streaming_bulk

def bulk_load(client, index, documents, chunk_size=500):
    successes = 0
    errors = []

    for ok, info in streaming_bulk(
        client,
        documents,
        index=index,
        chunk_size=chunk_size,
        raise_on_error=False,
        max_retries=3,
        initial_backoff=2,
    ):
        if ok:
            successes += 1
        else:
            errors.append(info)

    print(f"Indexed {successes}, failed {len(errors)}")
    return successes, errors

06 Error Handling

In production, things fail constantly. Network blips, malformed data, service outages. A robust pipeline doesn't just detect errors — it recovers gracefully.

Retry Strategies

  • Immediate retry: Try again right away (transient errors)
  • Exponential backoff: Wait 1s, 2s, 4s, 8s… (overloaded services)
  • Jittered backoff: Add randomness to prevent thundering herd
  • Max retries: Give up after N attempts and route to DLQ

Circuit Breaker

When a downstream service is failing, stop sending requests entirely. Three states:

  • Closed: Normal operation, requests flow through
  • Open: Service is down, all requests fail fast
  • Half-open: Try one request to see if service recovered

Dead Letter Queue (DLQ)

Documents that fail all retry attempts are sent to a DLQ — a separate storage area for manual review. Each entry records:

What failed

The original document payload

Why it failed

Error message and stack trace

When it failed

Timestamp and retry count

Production Reality

In most search pipelines, 0.1-1% of documents hit the DLQ. That's normal. What's not normal is ignoring them. Set up alerts when DLQ depth exceeds a threshold.

Retry with Exponential Backoff

# Exponential backoff with jitter
import random, time

def retry_with_backoff(fn, max_retries=5, base_delay=1.0):
    for attempt in range(max_retries):
        try:
            return fn()
        except TransientError:
            if attempt == max_retries - 1:
                raise
            delay = base_delay * (2 ** attempt)
            jitter = random.uniform(0, delay * 0.1)
            time.sleep(delay + jitter)

07 Monitoring

You can't improve what you can't measure. Pipeline monitoring gives you real-time visibility into health and throughput.

The Three Pillars of Pipeline Observability

Throughput

Documents processed per second. Track at each stage to find bottlenecks. If Extract outputs 100/s but Transform only handles 60/s, you have a backup forming.

Error Rate

Percentage of documents that fail at each stage. Normal is <1%. Above 5% warrants investigation. Above 10% should trigger circuit breakers.

Latency

Time from extraction to index availability. Track p50, p95, p99. A spike in p99 often indicates resource contention or garbage collection pressure.

08 Idempotency

An idempotent pipeline produces the same result whether you run it once or ten times. This is critical for reliability.

🔑

Elevator analogy: Pressing the "3rd floor" button once or twenty times has the same effect — you go to floor 3. An idempotent pipeline works the same way. Re-running it doesn't create duplicate documents or corrupt your index.

How to achieve idempotency

Document-level IDs

Every document gets a deterministic ID derived from its content or source ID. Re-indexing the same document overwrites rather than duplicates.

Upsert semantics

Use index (not create) operations. If the doc exists, it's updated. If not, it's created. Same result either way.

Checkpoint tracking

Record exactly which records were processed. On restart, resume from the last checkpoint instead of starting over.

Atomic swaps

Build the entire new index, then swap the alias. The old index stays intact as a rollback point.

# Idempotent upsert — safe to re-run
for doc in documents:
    doc_id = compute_id(doc["source"], doc["external_id"])
    index.upsert(id=doc_id, body=doc)  # insert or overwrite

Deterministic ID Generation

import hashlib

def compute_id(source, external_id):
    """Generate a stable, deterministic document ID."""
    raw = f"{source}:{external_id}"
    return hashlib.sha256(raw.encode()).hexdigest()[:16]

# Same input always produces the same ID
compute_id("postgres", "12345")  # → "a3f2b8c91e4d7f06"
compute_id("postgres", "12345")  # → "a3f2b8c91e4d7f06"  (same!)

index with fixed IDYesOverwrites entire doc — safe but replaces everything
create with fixed IDNoFails if doc already exists — use for first-write only
update with upsertYesMerges fields — good for partial updates
Auto-generated IDsNoCreates duplicates on re-run — avoid in pipelines

09 Key Takeaway

Remember This

A search ETL pipeline is only as good as its weakest stage. Extract reliably, Transform defensively (validate everything), and Load efficiently (bulk operations). Build in retries, circuit breakers, and monitoring from day one — they're not optional in production.

Pipeline Health Checklist

  • Every document has a deterministic ID (idempotency)
  • Failed documents go to DLQ, not into the void
  • Throughput, error rate, and latency are monitored
  • Pipeline can be restarted mid-run without duplicates
  • Schema validation catches issues before they reach the index
