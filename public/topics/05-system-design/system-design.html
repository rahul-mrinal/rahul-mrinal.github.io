01 Design an eCommerce Search System

This is the canonical system design question for search engineers. Let's walk through it exactly as you would in practice - requirements, estimation, API, then architecture.

Pro Tip

Always start by asking clarifying questions and defining scope. Don't jump into architecture. Experienced engineers want to see that you can think structurally about ambiguous problems.

Step 1: Clarify Requirements

Functional Requirements
  • Keyword search - users type free text, get ranked product results
  • Autocomplete - type-ahead suggestions as user types
  • Filters - price range, brand, rating, availability
  • Faceted navigation - dynamic counts per filter option
  • Sorting - by relevance, price, rating, newest
  • Spell correction - "iphne" → "iphone"
  • Synonyms - "sneakers" = "trainers" = "running shoes"
  • Pagination - page through results
Non-Functional Requirements
  • Latency - p99 < 200ms end-to-end
  • Availability - 99.9% uptime (8.76h downtime/year)
  • Throughput - 10,000 queries per second (QPS) peak
  • Consistency - eventual (new products visible within minutes)
  • Scalability - horizontal scaling for catalog and traffic growth
  • Freshness - price/stock updates within 5 minutes
  • Fault tolerance - no single point of failure
  • Relevance - high quality ranking (measurable via NDCG)

03 Data Ingestion

Getting product data from the source of truth into a search-optimized index is the foundation. Get this wrong and nothing else matters.

Data Sources

Product Information Management (PIM)

The authoritative source for product data: titles, descriptions, images, categories, attributes. Typically a relational DB or specialized PIM system (Akeneo, Salsify).

Real-Time Event Streams

Price changes, inventory updates, promotions, new listings, delistings. These flow through Kafka topics and must be reflected in search within minutes.

Ingestion Pipeline

1
Change Data Capture (CDC) - Debezium reads the binlog from the product database. Every INSERT, UPDATE, DELETE is published to a Kafka topic.
│
2
Event Stream (Kafka) - Decouples producers from consumers. Provides durability, replay capability, and backpressure handling. Topic: product.changes
│
3
Enrichment Service - Joins data from multiple sources: category taxonomy lookup, brand normalization, attribute extraction, image feature extraction.
│
4
Embedding Generation - Pass title + description through a sentence-transformer model (e.g., all-MiniLM-L6-v2) to generate dense vectors for semantic search.
│
5
Index Writer - Bulk API for batch loads. Single-doc API for real-time updates. Handles retries, dead-letter queue for failures.

Batch vs Incremental Indexing

Aspect Full Re-Index (Batch) Incremental Updates
When Nightly or weekly Continuous (real-time)
Scope All 50M documents Changed documents only (~5M/day)
Duration 2–6 hours Seconds per document
Strategy Build new index → alias swap In-place update via doc ID
Risk Resource-heavy, but clean slate Index can drift from source over time
Use case Schema changes, embedding model updates Price, stock, new products

Embedding throughput math:

A single GPU (A100) can process ~500 texts/second with a 384-dim model. For 50M products: ~28 hours on a single GPU, or ~3.5 hours on 8 GPUs. Plan for daily incremental embedding of only changed products (~5M/day = ~2.8 hours on 1 GPU).

Mention Kafka as the backbone of your ingestion layer - it shows you understand decoupling, backpressure, and event-driven architecture. Always discuss the alias swap pattern for zero-downtime re-indexing. Mention the embedding generation latency and how you'd parallelize it.

04 Indexing Strategy

The index schema and sharding strategy fundamentally determine your search performance, cost, and operational complexity.

Index Schema Design

{
  "mappings": {
    "properties": {
      "product_id":    { "type": "keyword" },
      "title":         { "type": "text", "analyzer": "custom_english",
                          "fields": {
                            "keyword": { "type": "keyword" },
                            "suggest": { "type": "completion" }
                          }},
      "description":   { "type": "text", "analyzer": "custom_english" },
      "brand":         { "type": "keyword" },
      "category":      { "type": "keyword" },
      "category_path": { "type": "keyword" },
      "price":         { "type": "float" },
      "rating":        { "type": "float" },
      "review_count":  { "type": "integer" },
      "in_stock":      { "type": "boolean" },
      "attributes":    { "type": "nested",
                          "properties": {
                            "name":  { "type": "keyword" },
                            "value": { "type": "keyword" }
                          }},
      "embedding":     { "type": "dense_vector",
                          "dims": 768,
                          "index": true,
                          "similarity": "cosine" },
      "popularity":    { "type": "float" },
      "created_at":    { "type": "date" },
      "updated_at":    { "type": "date" }
    }
  }
}
Field Type Decisions:
text Full-text searchable, analyzed (tokenized + stemmed). Used for title, description.
keyword Exact match only, not analyzed. Used for brand, category, product_id. Essential for filtering and aggregations.
nested For structured key-value pairs (attributes). Allows querying "color=red AND size=XL" without cross-contamination.
dense_vector Stores embedding vectors for kNN search. Requires dimension specification and similarity metric.
completion Optimized for autocomplete. Uses FST (Finite State Transducer) data structure for prefix matching.

Sharding Strategy

Sharding determines how data is distributed across nodes. It's one of the most impactful decisions you'll make.

Strategy How Pros Cons Best For
Hash-based hash(product_id) % N Even distribution, simple Queries hit all shards General eCommerce
Category-based One shard per category Category queries hit one shard Uneven shard sizes (electronics vs. books) Category-heavy browsing
Time-based Daily/monthly indices Easy to archive old data Uneven query load (recent data hotter) Log-style data, not products
Size-based New shard when current exceeds threshold Predictable shard sizes Complex routing Growing catalogs
Recommended: Hash-based sharding for eCommerce

Most eCommerce queries search across all categories, so category-based routing rarely helps. Hash-based gives you even distribution and simplicity. Use custom routing only for specific access patterns (e.g., a marketplace where queries are always scoped to a seller).

How Many Shards? How to Size Them?

Elasticsearch shard sizing rules of thumb:
Guideline Value Rationale
Target shard size 10–50 GB Smaller = faster queries, larger = fewer shards to manage
Shards per GB of heap < 20 shards per GB Each shard has overhead (file handles, memory, cluster state)
Max docs per shard ~200M (Lucene limit) Theoretical max is 2.1B but performance degrades well before
QPS per shard ~100-500 QPS Depends on query complexity, hardware, cache hit ratio

Calculation for our 50M product index:

$$\text{Number of primary shards} = \left\lceil\frac{650\text{ GB}}{30\text{ GB per shard}}\right\rceil \approx 22 \text{ shards}$$
With a target of ~30 GB per shard and 1 replica: 44 total shards across the cluster

Replica Configuration

Read Scaling

Each replica can serve read queries independently. With 10K QPS and ~300 QPS per shard, you need: 10,000 / (22 shards × 300 QPS) ≈ 1.5 → at least 2 replicas.

Availability

Replicas provide fault tolerance. With 1 replica, you survive 1 node failure. With 2 replicas, you survive 2 concurrent node failures. For 99.9% SLA: minimum 1 replica, recommended 2.

Refresh Interval

The refresh_interval controls how quickly newly indexed documents become searchable.

Setting Value Trade-off
Default 1s Near real-time but high I/O overhead
Recommended for search 5s - 30s Good balance of freshness vs performance
During bulk indexing -1 (disabled) Maximum indexing throughput, re-enable after
Pro Tip

Show your shard math. Say "50M products × ~13 KB per indexed doc = ~650 GB. Target 30 GB per shard = ~22 primary shards. With 2 replicas for HA and read scaling, that's 66 total shards across maybe 12 data nodes." Concrete numbers backed by reasoning are compelling.

05 Query Service

The query service is the brain of the search system. It transforms a raw user query into a ranked list of results through a multi-stage pipeline.

Request Flow

1
API Gateway - Rate limiting, auth, request validation. Route to the query service cluster. Latency budget: ~5ms
│
2
Cache Check - Check Redis for cached results of this exact (query, filters, sort, page) tuple. If hit → return immediately. Latency: ~1ms
│
3
Query Parser - Tokenize, lowercase, remove stop words, apply stemming. Identify structured parts: "sony headphones under $200" → query: "headphones", brand: "Sony", price_max: 200. Latency: ~2ms
│
4
Query Understanding - Spell check (did-you-mean), synonym expansion, category prediction, intent detection (navigational vs. informational). Latency: ~10ms
│
5
L1 Retrieval - Execute hybrid search: BM25 (keyword) + kNN (vector) in parallel. Fetch top 500-1000 candidates. Latency: ~30-80ms
│
6
L2 Re-Ranking - ML model (XGBoost / LambdaMART / cross-encoder) re-scores top candidates using rich features (CTR, conversion, freshness, personalization). Latency: ~20-50ms
│
7
Business Rules - Apply pinned products, boosted brands, ad slots, out-of-stock demotion. Latency: ~2ms
│
8
Response Formatting - Generate snippets with highlighting, assemble facets, attach metadata, paginate. Latency: ~5ms
Latency Budget Breakdown:
Stage Budget % of Total
Network + Gateway 10ms 5%
Cache check 1ms 0.5%
Query parsing + understanding 15ms 7.5%
L1 Retrieval (BM25 + kNN) 80ms 40%
L2 Re-ranking 50ms 25%
Business rules + formatting 10ms 5%
Buffer 34ms 17%
Total p99 < 200ms 100%

Category Prediction

Use a lightweight classifier (or rule engine) to predict which category the query targets:

Query Predicted Category Action
"nike air max" Shoes → Sneakers Boost results in Shoes, filter sidebar shows shoe attributes
"macbook pro 16" Electronics → Laptops Show laptop-specific facets (RAM, storage, screen size)
"birthday gift" Ambiguous Show broad results, category facets prominent

Multi-Stage Retrieval

L1: Candidate Generation (~1000 docs)

Fast, cheap retrieval. Run BM25 and kNN in parallel. Merge with Reciprocal Rank Fusion (RRF) or weighted score combination. Goal: high recall - don't miss good results.

$$\text{RRF}(d) = \sum_{r \in \text{rankers}} \frac{1}{k + \text{rank}_r(d)}$$
k = 60 (constant), rank = position in each ranker's list
L2: Re-Ranking (~top 200)

Expensive but precise. ML model with rich features: text relevance score, click-through rate, conversion rate, recency, price competitiveness, seller quality. Goal: high precision - put the best results on top.

Pro Tip

Walk through the request flow step by step with latency budgets. It's essential to demonstrate that you understand the cost of each operation. Mention that L1 retrieval is the bottleneck (~40% of latency) and that caching can eliminate it entirely for repeated queries.

How facet counts work:

When a user searches "wireless headphones", Elasticsearch runs the search query AND computes aggregation counts in a single request. The counts reflect how many results match each filter option within the current search results.

The "OR within, AND across" rule:

Selecting multiple brands (Sony OR Bose) shows union. Combining brand + price shows intersection. This is the standard UX for faceted navigation.

Dynamic vs Static Facets

Type Definition Example Implementation
Static facets Same facets always shown regardless of query Brand, Price, Rating (always present) Hardcoded in UI, always requested in aggregation
Dynamic facets Facets change based on query/category context "Screen Size" only for TVs, "Material" only for clothing Category → facet mapping table. Query intent detection selects which facets to show.

Filter Caching

Elasticsearch filter cache (node query cache):

Filters on keyword and boolean fields are automatically cached as bitsets. A bitset for brand:Sony marks which documents match - subsequent queries reuse it without re-evaluating. The cache is per-segment and invalidated on segment merges.

Pro Tip

Mention the "post_filter" pattern: when computing facet counts, apply the search query and OTHER filters but NOT the current facet's filter - so the count for "Sony" shows how many Sonys match the query even if the user hasn't selected Sony yet. This is the standard UX and a detail that demonstrates deep understanding.

07 Ranking Layer

Ranking is the difference between a search engine that "works" and one that drives revenue. A sophisticated ranking pipeline uses multiple layers, each progressively more expensive and precise.

Multi-Stage Ranking Architecture

Full Catalog: 50M products
▼ L0: Inverted Index Pruning
L1 Candidates: ~1,000 docs
BM25 + kNN retrieval (~50ms)
▼ L1 → L2: Feature Enrichment
L2 Re-Ranked: ~200 docs
ML Model scoring (~30ms)
▼ L2 → Business Rules
Final Results: 20 docs (page 1)
Pins, boosts, ads, deduplication

L1: BM25 + Vector Retrieval

BM25 (Keyword)

Exact term matching via inverted index. Fast, interpretable, excels at precision for specific queries ("SKU-12345", "iPhone 15 Pro Max 256GB").

$$\text{BM25}(q, d) = \sum_{t \in q} \text{IDF}(t) \cdot \frac{f(t,d) \cdot (k_1+1)}{f(t,d) + k_1 \cdot (1 - b + b \cdot \frac{|d|}{\text{avgdl}})}$$
kNN Vector Search (Semantic)

Meaning-based matching via embedding similarity. Handles synonyms, paraphrases, conceptual queries ("noise canceling headphones for plane travel").

$$\text{sim}(q, d) = \frac{\vec{q} \cdot \vec{d}}{\|\vec{q}\| \cdot \|\vec{d}\|}$$
Cosine similarity between query and document embeddings

L2: ML Re-Ranker

The L2 ranker uses a machine learning model (typically LambdaMART or a neural model) trained on click/purchase data to optimize ranking for business metrics.

Feature Categories for the Ranking Model:
Cache hit Filters cost ~0ms (bitset intersection)
Cache miss First execution builds the bitset (~5-20ms for large indices)
Invalidation Automatic on segment merge or refresh
Memory Default 10% of heap (configurable via indices.queries.cache.size)
Category Features Signal
Text Relevance BM25 score, vector similarity, query-title overlap How well the product matches the query
Popularity Click-through rate, conversion rate, view count, order count How popular the product is overall
Product Quality Average rating, review count, return rate Customer satisfaction signal
Freshness Days since listing, days since last price change Recency of the product
Commercial Price vs category average, margin, stock level Business value of showing this product
Personalization User's category affinity, brand affinity, price sensitivity Tailored to this specific user
Context Device type, time of day, location, session depth Situational relevance

Business Rules Layer

After ML ranking, apply deterministic business rules:

Demotion Rules
  • Out-of-stock → push to bottom
  • Low seller rating → demote
  • Policy violations → suppress
  • Duplicate products → deduplicate
Promotion Rules
  • Sponsored products → insert at positions 1, 4, 8
  • Promoted brands → boost score by 1.5x
  • New arrivals → temporary boost for 7 days
  • Bestsellers → boost during sales events

Pro Tip

Structure your ranking discussion as L1 → L2 → Business Rules. For each layer, state: (1) what it does, (2) latency cost, (3) how many docs it processes. Always mention A/B testing - it shows you understand that ranking is an iterative, data-driven process, not a one-time implementation.

08 Scalability & Performance

Scaling a search system from 1K QPS to 100K QPS requires systematic thinking about every layer of the stack.

Horizontal Scaling Strategy

Scaling the Index Layer (Elasticsearch/OpenSearch)
Dimension How to Scale When Impact
More data Add primary shards (requires re-index) Catalog grows beyond shard capacity Linear storage increase
More reads Add replica shards QPS exceeds current capacity Linear read throughput increase
More nodes Add data nodes to cluster CPU/memory pressure on existing nodes Distributes shard load
Better hardware Upgrade to faster SSDs, more RAM Vertical scaling before horizontal Faster per-shard performance

Performance Numbers (Rules of Thumb)

Metric Typical Value Notes
QPS per shard 100–500 QPS Depends on query complexity, shard size, hardware
Memory per shard ~1–2 GB heap Field data, filter cache, segments
Shard query latency 5–30ms Per-shard, before coordination overhead
Coordination overhead ~5–15ms Scatter-gather + merge results from all shards
Optimal heap size ≤ 31 GB JVM compressed oops boundary
Heap to storage ratio 1 GB heap : 20–30 GB disk For search-heavy workloads
Indexing throughput 5K–20K docs/sec per node Depends on document size and pipeline

Capacity Planning Example

$$\text{Required shard-copies} = \frac{\text{Peak QPS}}{\text{QPS per shard}} = \frac{10{,}000}{300} \approx 34 \text{ shard-copies}$$
With 22 primary shards: need ⌈34/22⌉ - 1 = 1 replica minimum. Use 2 replicas for safety.
$$\text{Data nodes} = \frac{\text{Total shards} \times \text{Heap per shard}}{\text{Heap per node}} = \frac{66 \times 1.5\text{ GB}}{30\text{ GB}} \approx 4 \text{ nodes (minimum)}$$
In practice: 8–12 nodes for headroom, rolling upgrades, and failure resilience

Caching Strategy Overview

Cache Type What's Cached Hit Ratio Target Tech
Query result cache Full serialized response for (query, filters, sort, page) 30–50% Redis / application-level
Filter cache Bitsets for common filters (brand, category, in_stock) 80–95% Elasticsearch node query cache
Field data cache Uninverted field values for sorting/aggregations ~100% (warm) Elasticsearch field data / doc values
Embedding cache Pre-computed query embeddings 20–40% Redis
Autocomplete cache Popular prefix → suggestions 60–80% Redis sorted sets

Load Balancing

Application Layer

Round-robin or least-connections across query service instances. Health checks every 5s. Graceful drain on shutdown (finish in-flight requests before stopping).

Elasticsearch Layer

Built-in coordinating node distributes queries across shards. Adaptive replica selection picks the least-busy replica for each shard. No external LB needed at this layer.

Auto-Scaling

Scaling triggers:
Metric Threshold Action
CPU utilization > 70% for 5 min Add query service instances
p99 latency > 180ms for 5 min Add ES replicas or query instances
Queue depth > 100 pending requests Scale out query service
Cache miss rate > 80% Increase Redis memory or warm cache

Elasticsearch data nodes don't auto-scale easily (shard rebalancing is expensive). The query service layer and cache layer are the primary auto-scaling targets.

Pro Tip

Show your math. "10K QPS, ~300 QPS per shard, 22 primary shards → need 34 shard-copies → 2 replicas. With 2 replicas across ~10 data nodes, each node handles ~6 shards. At 1.5 GB heap per shard, that's ~9 GB heap per node, well within the 31 GB compressed oops boundary." This level of detail demonstrates deep expertise.

09 High Availability & Fault Tolerance

For 99.9% availability (≤ 8.76 hours of downtime per year), every component must be designed for failure.

Failure Modes & Mitigations

Failure Impact Mitigation Recovery Time
Single ES node dies Shards on that node unavailable Replicas on other nodes promoted to primary. Cluster auto-rebalances. ~30s (replica promotion) + minutes (rebalancing)
Query service instance dies Reduced capacity Load balancer health check removes it. Auto-scaling replaces it. ~10-30s (health check) + ~60s (new instance boot)
Redis cache down All queries hit ES directly → latency spike Redis Cluster with replicas. Circuit breaker: if cache down, bypass and serve from ES. ~5s (failover to Redis replica)
Kafka broker failure Ingestion pipeline stalls Kafka replication factor = 3. Producer retries. Consumer offset tracking. ~30s (leader election)
Entire region outage Complete service outage Cross-region deployment with DNS failover (Route 53, Cloudflare). ~1-5 min (DNS TTL)
Bad ranking model deploy Search quality degradation Canary deployment (5% traffic). Automatic rollback if CTR drops > 10%. ~2 min (automated rollback)

Replicas on Node 3 automatically promoted to primaries. Cluster remains GREEN if enough replicas exist.

Cross-Region Deployment

Active-Passive

Primary region serves all traffic. Secondary region has a warm standby with replicated data. DNS failover on primary failure. Simpler but slower failover (~minutes).

Active-Active

Both regions serve traffic. Users routed to nearest region. Requires cross-region index replication (Cross-Cluster Replication in ES). More complex but near-instant failover.

Circuit Breakers

Prevent cascading failures when downstream services are unhealthy:

// Circuit Breaker States
CLOSED  → Normal operation. Requests flow through.
           If failure rate > 50% in 10s window → OPEN

OPEN    → All requests immediately fail-fast (no downstream call).
           After 30s timeout → HALF-OPEN

HALF-OPEN → Allow 1 probe request through.
           If succeeds → CLOSED. If fails → OPEN.

Graceful Degradation

When under extreme load or partial failure, serve degraded but functional results:

Degradation Level What's Reduced User Impact
Level 1 Disable L2 re-ranking Slightly less relevant results, saves ~30ms
Level 2 Disable vector search (BM25 only) No semantic matching, saves ~20ms
Level 3 Disable facet aggregations No filter counts, saves ~15ms
Level 4 Serve from cache only (stale results) Results may be outdated but fast
Level 5 Show popular/trending products No personalized search, but page still loads
Pro Tip

Discuss graceful degradation as a priority hierarchy. "If the ML ranker is down, fall back to BM25. If ES is overloaded, serve from cache. If everything is down, show trending products." This shows you think about user experience during failure, not just uptime percentages. Mention circuit breakers by name - engineers in senior roles expect it.

10 Caching Deep Dive

Caching is the single most impactful optimization for search latency and cost. A well-designed cache can reduce ES load by 40-60%.

What to Cache

Query Result Cache

Cache the entire serialized response for a specific (query, filters, sort, page) tuple. Highest impact: eliminates all downstream processing.

Key format: search:{hash(query+filters+sort+page)}

TTL: 5–15 minutes

Hit ratio: 30–50% (power law of queries)

Embedding Cache

Cache the dense vector representation of frequent queries. Avoids calling the embedding model on every search.

Key format: emb:{hash(normalized_query)}

TTL: 24 hours (embeddings don't change)

Hit ratio: 20–40%

Filter Result Cache

Cache bitsets for popular filter combinations (e.g., "brand:Nike AND in_stock:true"). ES does this internally but you can also cache at the application level.

TTL: 5 minutes (stock changes)

Hit ratio: 80–95% (finite filter combinations)

Autocomplete Cache

Cache top suggestions for popular prefixes. "iph" → ["iphone", "iphone case", "iphone charger"]. Critical because autocomplete fires on every keystroke.

TTL: 1 hour

Hit ratio: 60–80%

Cache Invalidation Strategies

🧠

"There are only two hard things in computer science: cache invalidation and naming things." - Phil Karlton. For search, getting invalidation right is critical because stale prices or out-of-stock products damage trust.

Strategy How It Works Pros Cons Use For
TTL-based Entries expire after fixed time Simple, predictable Stale data during TTL window Query results, embeddings
Event-driven Kafka consumer invalidates on product change events Fast, precise Complex, requires knowing which cached queries are affected Price/stock changes
Tag-based Tag cache entries with product IDs. Invalidate all entries containing a changed product. Precise per-product invalidation Storage overhead for tag sets Result caches with product-level freshness needs
Write-through Update cache simultaneously with index update Always fresh Write amplification, complex Critical fields (price, availability)

TTL Design

Cache Layer TTL Rationale
Query results 5 min Balance freshness vs hit ratio. Price/stock changes within 5 min acceptable.
Autocomplete 1 hour Suggestions change slowly. Popularity-weighted, recomputed hourly.
Embeddings 24 hours Model doesn't change daily. Invalidate on model deploy.
Facet counts 1 min Counts must be fairly accurate. Short TTL, high hit ratio due to few unique filter combos.
Spell corrections 7 days Dictionary changes rarely. Rebuild weekly.

Memory sizing:

Estimate cache memory: 200K unique queries/hour × 2 KB avg response × 5-min TTL = ~3.3 GB at any time. With embeddings (768 × 4 bytes = 3 KB per query): additional ~2 GB. Add autocomplete and filters: ~10 GB total. Use a 64 GB cluster for headroom.

Cache Hit Ratio Targets

$$\text{Effective QPS on ES} = \text{Total QPS} \times (1 - \text{Cache Hit Ratio})$$
At 40% cache hit ratio: 10K QPS × 0.6 = 6K QPS reaching ES - a 40% reduction in cluster load

Cache Warming

Pre-populate the cache before it's needed to avoid cold-start latency spikes:

  • On deployment: Replay the top 10K queries from yesterday's analytics against the new deployment before switching traffic.
  • On re-index: After alias swap, immediately warm the cache with popular queries against the new index.
  • Scheduled: Every morning at 6 AM, warm the cache with predicted high-traffic queries (seasonal, promotional).
Pro Tip

Mention the query frequency power law: the top 1% of queries account for ~30% of traffic. Caching these gives you disproportionate benefit. Explain your TTL reasoning: "5 minutes for results because price freshness within 5 minutes is acceptable for most eCommerce. For flash sales, use event-driven invalidation." This shows you balance pragmatism with correctness.

Search Quality Metrics

Offline Metrics (Measured via Evaluation Sets)
NDCG@10 Normalized Discounted Cumulative Gain at position 10. Gold standard for ranking quality.
MRR Mean Reciprocal Rank. Where does the first relevant result appear?
Recall@K What fraction of relevant docs are in the top K results?
Precision@K What fraction of top K results are relevant?
Online Metrics (Measured in Production)
CTR Click-Through Rate. % of searches where user clicks a result.
Zero-result rate % of queries returning 0 results. Target: < 5%.
Abandonment rate % of searches with no click and no refinement.
Conversion rate % of searches leading to a purchase.
Revenue per search Total revenue / total searches. The ultimate business metric.

NDCG Formula

$$\text{NDCG@K} = \frac{\text{DCG@K}}{\text{IDCG@K}} \quad \text{where} \quad \text{DCG@K} = \sum_{i=1}^{K} \frac{2^{\text{rel}_i} - 1}{\log_2(i + 1)}$$
reli = relevance grade of result at position i (0–4). IDCG = DCG of the ideal (perfect) ranking.
