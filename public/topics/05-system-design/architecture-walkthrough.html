01 Requirements

Every system design starts with defining what we're building and the constraints we operate under.

Functional Requirements

  • Keyword search — full-text ranked product results
  • Autocomplete — type-ahead suggestions
  • Filters — price, brand, rating, availability
  • Faceted navigation — dynamic filter counts
  • Sorting — relevance, price, rating, newest
  • Spell correction — handle typos gracefully
  • Synonyms — map equivalent terms
  • Pagination — page through results

Non-Functional Requirements

  • Latency — p99 < 200ms end-to-end
  • Availability — 99.9% uptime
  • Throughput — 10,000 QPS peak
  • Consistency — eventual (minutes)
  • Scalability — horizontal scaling
  • Freshness — price/stock updates < 5 min
  • Fault tolerance — no SPOF
  • Relevance — high NDCG scores
Pro Tip

In a system design interview, always start by clarifying requirements and scope. Don't jump to architecture — show that you think structurally about ambiguous problems.

API Design

// Search endpoint
GET /api/v1/search
  ?q=wireless+headphones       // query text
  &category=electronics        // filter
  &price_min=20&price_max=200  // range filter
  &brand=sony,bose             // multi-value filter
  &sort=relevance              // sort order
  &page=1&size=20              // pagination

// Response shape
{
  "results": [...],          // product objects
  "facets": {...},           // filter counts
  "total": 1423,             // total matches
  "spell_suggestion": null,  // correction if any
  "took_ms": 42              // server-side latency
}

Query Parameters

  • q — free text search query
  • filters — category, brand, price range, rating
  • sort — relevance, price_asc, price_desc, newest, rating
  • page/size — offset-based pagination
  • fields — which fields to return (projection)

Design Decisions

  • Use GET for cacheability (CDN, browser)
  • Normalize queries server-side (lowercase, trim)
  • Return took_ms for client-side monitoring
  • Cursor-based pagination for deep pages
  • Version the API (/v1/) from day one

Key Formulas

$$ \text{Storage} = \text{Products} \times \text{Avg Size} \times 1.5 $$
1.5× for index overhead (inverted index, doc values, norms)
$$ \text{Shards} = \lceil \frac{\text{Index Size}}{\text{Max Shard Size}} \rceil $$
Round up — partial shards still need a full shard allocation
$$ \text{Bandwidth} = \text{QPS} \times \text{Avg Response Size} $$
Peak bandwidth requirement for search responses
$$ \text{Nodes} = \frac{\text{Shards} \times \text{Replication Factor}}{\text{Shards per Node}} $$
Typically 3-5 shards per node for balanced performance
Pro Tip

Always add 30-50% headroom to your capacity estimates. Real-world traffic has spikes (flash sales, viral products, marketing campaigns). If your system runs at 70% capacity normally, you have room to absorb 40% spikes without degradation.

Search Cluster Internals

Coordinator Node

Receives search request, fans out to shards, merges results. Stateless — any node can coordinate.

Data Nodes

Hold shards and execute local searches. CPU and I/O intensive. Scale these for more capacity.

Master Nodes

Manage cluster state, shard allocation, index settings. Lightweight — 3 dedicated nodes for HA.

Separation of Concerns

In production clusters, use dedicated master nodes (3 for quorum) that don't hold data. This prevents data node GC pauses or crashes from destabilizing the cluster's management layer. Coordinator nodes should also be separate from data nodes for large clusters.

Preprocess
~5ms
▼

Normalize the raw query string into a structured search request.

  • Tokenization — split "wireless noise-cancelling headphones" into tokens
  • Lowercasing — normalize case
  • Synonym expansion — "headphones" → ["headphones", "earphones", "earbuds"]
  • Stopword removal — remove "the", "a", "is" (optional)
  • Query classification — is this navigational ("Apple Store") or generic ("laptop")?
2
Spell Check & Rewrite
~15ms
▼

Detect and correct spelling errors, then optionally rewrite the query for better recall.

  • Edit distance — "iphne" → "iphone" (Levenshtein distance = 2)
  • Phonetic matching — "fone" → "phone" (Soundex/Metaphone)
  • Context-aware correction — "samsung galxy" → "samsung galaxy"
  • Query relaxation — if no results, broaden the query by dropping terms
3
Retrieve (Scatter-Gather)
~60ms
▼

The most expensive step. Fan out the query to all shards, each searches its local index.

  • BM25 scoring — compute relevance score per document
  • Top-K per shard — each shard returns its best K candidates
  • Merge — coordinator merges K×S candidates into final top-K
  • Latency = max(shard latencies) — bounded by slowest shard

This is where 60-70% of your latency budget goes.

4
Filter & Facet
~30ms
▼

Apply post-retrieval filters and compute facet counts for the UI.

  • Boolean filters — price range, in_stock=true, brand="Nike"
  • Bitset intersection — pre-computed filter bitsets ANDed with result set
  • Facet aggregation — count docs per brand, per category, per price bucket
  • Filter caching — frequently used filters cached as bitsets
5
Re-Rank
~50ms
▼

Apply a more sophisticated ranking model on the top candidates.

  • L1: BM25 — fast lexical retrieval (done in retrieve step)
  • L2: LTR model — gradient-boosted tree with click features, conversion rate, etc.
  • Business rules — boost sponsored products, pin featured items
  • Personalization — adjust scores based on user's brand affinity, purchase history
  • Diversity — ensure top results aren't all from the same brand
6
Return Response
~10ms
▼

Assemble the final response and send it back to the client.

  • Response assembly — combine products, facets, spell suggestions, metadata
  • Field projection — only return fields the client needs (title, price, image)
  • Highlighting — bold the matching terms in titles/descriptions
  • Serialization — JSON serialization and compression (gzip)
  • Logging — emit search event for analytics pipeline
Total Latency Budget
~170ms
Well within the 200ms p99 target, leaving 30ms headroom for network and serialization

Why Kafka?

  • Decoupling — DB and indexer evolve independently
  • Buffering — absorbs spikes without overloading the search cluster
  • Replay — re-index from any point by resetting consumer offset
  • Ordering — per-partition ordering ensures updates apply in sequence

Indexer Workers

  • Transform — flatten nested product data, compute derived fields
  • Enrich — join with category taxonomy, add brand metadata
  • Validate — skip corrupt records, alert on schema drift
  • Bulk index — batch 500-1000 docs per request to ES
Key Design Decision

Use CDC (Change Data Capture) over polling. CDC captures every change as it happens (INSERT, UPDATE, DELETE) from the DB's write-ahead log. Polling misses changes between intervals and creates unnecessary DB load.

Handling Deletes and Updates

Soft Deletes

  • Mark document as deleted=true in index
  • Filter out in query time
  • Periodically purge via background job
  • Simpler, but stale docs consume storage

Hard Deletes

  • Remove document from index immediately
  • Lucene marks as deleted, purges on merge
  • Cleaner, but can cause segment churn
  • Use bulk delete for efficiency
Pro Tip

Run a daily reconciliation job that compares the search index against the source-of-truth database. This catches any documents that were missed by CDC, partially indexed, or corrupted. It's your safety net against silent data divergence.

06 Failure Modes

Design for failure — because in distributed systems, failure is the norm, not the exception.

💥

Node Failure

A search node crashes or becomes unresponsive. Remaining nodes in the shard group take over reads. Cluster promotes a replica to primary if needed.

Mitigation

  • Replication factor ≥ 2
  • Spread replicas across availability zones
  • Automated health checks and failover
  • Capacity to absorb one node's traffic
🌐

Network Partition

Network split isolates some nodes. The cluster must decide: continue serving (risk inconsistency) or stop (guarantee consistency). CAP theorem in action.

Mitigation

  • Quorum-based writes (majority acknowledgment)
  • Minimum master nodes to prevent split brain
  • Cross-zone deployment with multiple network paths
🔥

Cascading Failure

One component fails → downstream components get overloaded → they fail too → chain reaction takes down the entire system.

Mitigation

  • Circuit breakers (fail fast, don't pile up)
  • Bulkheads (isolate critical from non-critical)
  • Load shedding (reject excess traffic gracefully)
  • Never run above 70% capacity
🐌

Ingestion Lag

Indexing falls behind — products show stale prices, sold-out items still appear in results. Users lose trust in the search experience.

Mitigation

  • Monitor Kafka consumer lag
  • Auto-scale indexer workers on lag threshold
  • Priority queue for price/stock updates
  • Freshness SLA dashboard (p95 < 5 min)

Graceful Degradation Strategies

ScenarioDegraded ResponseUser Impact
Search cluster downServe cached results or popular productsSlightly stale results
Ranking service downFall back to BM25 scores onlyLower relevance quality
Spell check service downSkip spell correction, search as-isTypos not corrected
Personalization downUse default (unpersonalized) rankingGeneric results for all users
One shard unavailableReturn partial results from N-1 shardsSlightly fewer results
Resilience Philosophy

A degraded search experience is always better than an error page. Design every non-critical component (spell check, personalization, re-ranking) to be optional and bypassable. The core retrieve + filter + return path should work even if everything else is down.

CPU-Based

Scale when avg CPU > 70% across search nodes for 5 minutes. Add replicas to absorb the load.

QPS-Based

Scale when QPS exceeds 80% of measured capacity. Predictive scaling based on traffic patterns.

Lag-Based

Scale indexer workers when Kafka consumer lag exceeds threshold. Ensures freshness SLA is met.

09 Key Takeaway

Complete Design Checklist

1. Requirements first. Clarify functional and non-functional requirements. Get agreement on latency, availability, and freshness SLAs before drawing boxes.

2. Estimate capacity. Products × doc size × replication factor → cluster size. QPS → number of nodes needed. These numbers drive every architecture decision.

3. Separate read and write paths. Query path optimized for latency, ingestion path optimized for throughput. Kafka decouples them.

4. Design for failure. Replicate data, circuit-break dependencies, shed load gracefully. Assume any component can fail at any time.

5. Measure everything. p50/p95/p99 latency, QPS, error rate, zero-result rate, index freshness. You can't improve what you don't measure.

Interview Tips

What Interviewers Look For

  • Structured approach: requirements → estimation → API → architecture
  • Trade-off awareness: consistency vs availability, latency vs freshness
  • Depth in your area of expertise (ranking, indexing, scaling)
  • Ability to estimate capacity and justify decisions with numbers
  • Awareness of failure modes and mitigation strategies

Common Pitfalls

  • Jumping to architecture without clarifying requirements
  • Forgetting non-functional requirements (latency, availability)
  • Single point of failure in the design
  • Ignoring the write path (ingestion pipeline)
  • Not mentioning monitoring and observability
