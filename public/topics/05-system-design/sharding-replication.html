Sharding & Replication

Split data for throughput, replicate for availability

01 The Pizza Kitchen Analogy

Think of your data as pizza dough and your servers as ovens.

🍕

Sharding = Multiple ovens. When one oven can't bake fast enough for all the orders, you split the workload across several ovens. Each oven handles a subset of pizza types. Pepperoni goes to Oven A, Margherita to Oven B, etc. Together they handle more throughput than any single oven could.

Just like in a real kitchen, the challenge isn't splitting the work — it's coordinating the results. When a customer orders a "pizza combo," you need all ovens to contribute their part and assemble it at the serving counter. That coordination cost is the scatter-gather overhead.

🔄

Replication = Backup oven. What if Oven A breaks down? You keep a second oven running with the same recipes ready to go. That's a replica — it has a copy of the same data and can take over reads (or even writes) if the primary fails. More replicas = higher availability.

Sharding

  • Goal: Horizontal throughput scaling
  • How: Partition data across nodes
  • Each shard: Holds a subset of documents
  • Trade-off: Cross-shard queries are expensive
  • Also known as: Partitioning, horizontal splitting

Replication

  • Goal: Fault tolerance and read scaling
  • How: Copy data to multiple nodes
  • Each replica: Has the same data as the primary
  • Trade-off: Write amplification, consistency lag
  • Also known as: Mirroring, redundancy
$$ \text{Capacity} = \text{Shards} \times \text{QPS per shard} \times (\text{Replicas} + 1) $$
Combined formula: sharding multiplies data capacity, replication multiplies read capacity

02 Why Shard?

When your data outgrows a single machine, you have no choice but to split it.

Single-Node Limits

Key Insight

Sharding is the only way to achieve linear scalability. If you need 3× throughput, add 3× shards. If your index grows 5×, add enough shards so each still fits comfortably in RAM.

When to Shard

Data Volume

Index exceeds single node storage or RAM capacity

Query Throughput

QPS exceeds what one node can handle at acceptable latency

Write Throughput

Indexing rate exceeds single node's write capacity

💡

Think of it like moving apartments. Scale up = renting a bigger apartment. At some point, the biggest apartment isn't big enough. Scale out = renting multiple apartments and splitting your stuff across them. More flexible, but you need to remember where you put things.

Real-World Shard Counts

Small (1-10M docs)

1-3 shards, 1 replica each. Single-node or small cluster. Most internal search systems.

Medium (10-100M docs)

5-20 shards, 1-2 replicas. 3-10 node cluster. Mid-size eCommerce or SaaS search.

Large (100M+ docs)

20-100+ shards, 2+ replicas. 10-50+ nodes. Major eCommerce, media, or logging platforms.

03 Shard Strategies

How you distribute data across shards determines query patterns and performance.

Hash-Based Sharding

Apply a hash function to the document ID (or routing key) and mod by the number of shards:

$$ \text{shard} = \text{hash}(\text{doc\_id}) \bmod N $$
  • Pro: Even data distribution, no hotspots
  • Con: Range queries must hit all shards
  • Best for: Uniform access patterns (e.g., user-facing search)

Range-Based Sharding

Partition by value range — e.g., products A-M on shard 0, N-Z on shard 1:

  • Pro: Range queries can target a single shard
  • Con: Uneven distribution → hotspots
  • Best for: Time-series data, alphabetical lookups

Custom Routing

Elasticsearch-style: route by a field value (e.g., category or tenant_id):

  • Pro: Co-locate related docs, avoid scatter-gather
  • Con: Requires domain knowledge, can create skew
  • Best for: Multi-tenant systems, category-heavy search

Pro Tip

Elasticsearch defaults to hash-based routing on _id. Override with routing parameter if you know queries always filter by a specific field — this turns scatter-gather into single-shard queries.

Why Stragglers Matter

Total latency = max(shard latencies) + merge time. A single slow shard sets the floor for every query. This is why tail latency (p99) is the metric that matters most in distributed search.

Scatter-Gather Optimization Strategies

StrategyHowTrade-off
Adaptive replicasRoute to the least-loaded replica of each shardRequires real-time load tracking
Hedged requestsAfter a timeout, send duplicate to another replicaIncreases load by ~5%, cuts tail latency significantly
Custom routingRoute queries to a single shard when possibleOnly works for filtered queries
Shard pruningSkip shards that can't match (e.g., time-range filtering)Only works with range-partitioned data
Partial resultsReturn results from fast shards, skip the slow oneIncomplete results — use as last resort with timeout
$$ P(\text{straggler}) = 1 - (1 - p)^N $$
Probability of at least one slow shard: p = per-shard straggler rate, N = number of shards
Pro Tip

Google's "tail at scale" paper introduced hedged requests — send the same request to two replicas and use whichever responds first. This nearly eliminates p99 tail latency at a modest cost of ~5% extra load.

Write Path

  • Writes go to primary shard only
  • Primary replicates to replicas (sync or async)
  • Sync = stronger consistency, higher latency
  • Async = lower latency, risk of stale reads

Read Path

  • Reads can go to any replica
  • Load balancer distributes across replicas
  • More replicas = more read throughput
  • Prefer preference=_local for latency

Replica Scaling Formula

$$ \text{Read QPS capacity} = \text{QPS per node} \times (\text{replicas} + 1) \times \text{shards} $$
Each shard group (primary + replicas) can serve reads from any copy

Consistency Models

ModelWrite LatencyRead ConsistencyUse Case
Sync replicationHigh (wait for all replicas)Strong — all replicas identicalFinancial data, inventory counts
Async replicationLow (return after primary write)Eventual — replicas lag by ms-secondsSearch results, product catalog
Semi-syncMedium (wait for 1 replica)Durable — at least one copy confirmedBalanced workloads
Elasticsearch Default

Elasticsearch uses sync replication by default — a write isn't acknowledged until all in-sync replicas confirm. You can set wait_for_active_shards=1 to switch to primary-only acknowledgment for faster writes at the cost of durability.

Cross-Zone Replica Placement

For true fault tolerance, replicas must live in different failure domains. Elasticsearch supports shard allocation awareness — tag each node with its availability zone, and the cluster ensures no shard and its replica share a zone.

Rule of Thumb

Aim for 20 shards per node or fewer. Each shard consumes a thread pool, file handles, and memory. Thousands of tiny shards on a single node causes more overhead than a few well-sized ones.

07 Rebalancing

Adding or removing nodes requires moving data — and that has consequences.

When Rebalancing Happens

  • Scale out: Add nodes → move shards to new nodes to even out load
  • Scale in: Remove nodes → migrate their shards elsewhere
  • Hot shard: One shard gets disproportionate traffic → split or relocate
  • Disk full: Node running low on storage → move shards away

Shard Relocation

Move an entire shard from one node to another. The source streams data to the target while continuing to serve reads. Once synced, traffic switches over.

Low Risk

Shard Splitting

Split one shard into two when it grows too large. Requires re-indexing the data with a new routing scheme. Elasticsearch supports this via the Split API.

Higher Risk

Consistent Hashing

Traditional modular hashing (hash % N) means adding one node remaps almost all keys. Consistent hashing minimizes the disruption:

$$ \text{Keys remapped} \approx \frac{K}{N} \quad \text{(instead of nearly all K keys)} $$
K = total keys, N = number of nodes

Without Consistent Hashing

  • Add 1 node to 4-node cluster
  • hash % 4 → hash % 5
  • ~80% of keys need to move
  • Massive data shuffle, latency spike

With Consistent Hashing

  • Add 1 node to 4-node cluster
  • Only ~20% of keys remapped
  • Minimal data movement
  • Virtual nodes for even distribution
Pro Tip

Over-shard from the start. It's much easier to relocate small shards across new nodes than to split large ones. A common rule of thumb: plan for 2-3× your expected growth. With over-sharding, you can rebalance by simply moving shards — no splitting required.

Rebalancing Checklist

StepActionRisk
1Disable shard allocation temporarilyLow
2Add new node to clusterLow
3Re-enable allocationLow
4Monitor shard migration progressLow
5Verify cluster health = greenLow

08 Failure Modes

Distributed systems fail in distributed ways. Know the failure modes and plan for them.

Murphy's Law for Distributed Systems

If a node can fail, it will fail — and usually at the worst possible time. Design your system so that any single component failure is invisible to users. Two simultaneous failures should degrade gracefully. Three failures should be survivable.

Node Failure

A node crashes or becomes unreachable. The cluster promotes replicas to primary and reroutes traffic. Data is safe as long as at least one copy exists.

Mitigation

  • Replication factor ≥ 2
  • Replicas on different racks/zones
  • Automatic failover with health checks
  • Maintain capacity to absorb a failed node's load

Split Brain

Network partition causes two halves of the cluster to each believe they are the master. Both accept writes, leading to divergent state.

Mitigation

  • Quorum-based master election
  • Minimum master nodes = ⌊N/2⌋ + 1
  • Fencing / STONITH for partitioned nodes

Cascading Failure

One node fails → remaining nodes take extra load → they slow down → timeouts cascade → more failures. A classic death spiral.

Mitigation

  • Circuit breakers on query paths
  • Backpressure / load shedding
  • Capacity headroom (never run at 100%)

Data Corruption

Bit rot, bad writes, or bugs corrupt index segments. Queries return wrong results silently — the most dangerous failure mode.

Mitigation

  • Checksums on segments (Lucene does this)
  • Periodic full re-indexing from source of truth
  • Monitoring for anomalous result quality

09 Key Takeaway

Summary

Shard for throughput and capacity. When data or query volume exceeds one node, split your index across shards using hash, range, or custom routing.

Replicate for availability. Copies of each shard on separate nodes ensure no single point of failure and allow read scaling.

Scatter-gather is the cost. Every distributed query must fan out to all shards and merge results. Total latency = max(shard latencies). Minimize shard count where possible, and watch tail latency religiously.

$$ \text{Cluster Nodes} = \frac{\text{Total Data}}{\text{Max Shard Size}} \times \text{Replication Factor} $$
The fundamental equation of cluster sizing

Elasticsearch Defaults

  • Shards per index: 1 (was 5 before v7)
  • Replicas: 1 per shard
  • Routing: hash(_id) % num_shards
  • Max shard size: ~50 GB recommended
  • Shards per node: ≤ 20 per GB heap

Solr Defaults

  • Shards: Manual configuration in SolrCloud
  • Replicas: Configurable per collection
  • Routing: compositeId (hash-based)
  • Leader election: ZooKeeper-based
  • Auto-scaling: Policy-based triggers
Pro Tip

In interview settings, always mention data locality. If you can route related queries to a single shard (e.g., all products for one category), you convert scatter-gather into a single-shard query — dramatically reducing latency and resource usage.
