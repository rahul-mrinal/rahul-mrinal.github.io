01 The Librarian's Desk Analogy

Caching is the oldest optimization in computing — keep frequently needed data close.

📚

Imagine a librarian who keeps the most requested books on their desk instead of walking to the stacks every time. When someone asks for "Harry Potter," it's right there — instant. When someone asks for an obscure book, the librarian has to walk to the shelves (slow). The desk has limited space, so when it's full, the librarian removes the book that hasn't been asked for the longest time. That's LRU caching.

Cache Hit

Requested data is in the cache. Response is near-instant (microseconds vs milliseconds).

~0.1ms

Cache Miss

Data not in cache. Must compute the full query, then store result for next time.

~50-200ms

02 What to Cache

Not all data is equal. Cache the expensive-to-compute, frequently-accessed layers.

Query Results

  • Full search results for exact query strings
  • Highest hit rate for popular queries
  • Key = normalized query + filters
  • Invalidate on index update

Filter Bitsets

  • Precomputed bitmaps for common filters
  • e.g., "in_stock=true" → bitset of doc IDs
  • Reusable across different queries
  • Elasticsearch caches these automatically

Field Data

  • Uninverted index for sorting/aggregations
  • Loaded into heap on first access
  • Very expensive to build, persists across queries
  • Use doc_values for columnar storage

Pro Tip

The OS page cache is the most underrated cache in search. Lucene relies heavily on mmap to memory-map segment files. Leave at least 50% of node RAM for the OS page cache — don't give it all to the JVM heap.

Production Choice

W-TinyLFU (used by Caffeine in the JVM world) combines a small LRU admission window with frequency-based eviction. It adapts to workload shifts while maintaining near-optimal hit rates. Elasticsearch's internal node query cache uses a similar approach.

06 TTL and Invalidation

Cached results become stale. TTL and invalidation strategies keep data fresh.

Time-To-Live (TTL)

  • Each cached entry expires after a fixed duration
  • Simple to implement, predictable staleness bound
  • Short TTL = fresher data, lower hit rate
  • Long TTL = higher hit rate, staler data
$$ \text{Staleness} \leq \text{TTL} $$

Event-Driven Invalidation

  • Invalidate cache when underlying data changes
  • Product updated → purge all queries matching that product
  • More complex, but zero staleness for known changes
  • Hard to invalidate "all queries affected by this doc"
Pro Tip

Use a hybrid approach: short TTL (30-60s) as a safety net, plus event-driven invalidation for known changes. This gives you both freshness guarantees and protection against missed invalidation events.

08 Zipf's Law

Caching works because query traffic is heavily skewed — a small % of queries account for most traffic.

Zipf's Law

The frequency of the n-th most common query is proportional to 1/n. The most popular query is twice as frequent as the second, three times as frequent as the third, etc.

$$ f(k) = \frac{1/k^s}{\sum_{n=1}^{N} 1/n^s} $$
Zipf distribution: k = rank, s = skew exponent (typically ~1.0 for search)

Real-World Impact

Top Queries% of TrafficCache Size Needed
Top 100~25-30%Tiny (< 1 MB)
Top 1,000~40-50%Small (10 MB)
Top 10,000~60-70%Moderate (100 MB)
Top 100,000~80-85%Large (1 GB)
Pro Tip

Always measure your actual query distribution before sizing caches. Zipf's law is a good starting model, but real traffic can be even more skewed (e.g., trending queries during sales events).

Measuring Your Distribution

Unique Query Ratio

Count distinct queries / total queries over a day. If this ratio is low (e.g., 10-20%), caching will be very effective. If high (e.g., 80%+), most queries are unique and caching helps less.

Frequency Decay Rate

Plot query rank vs frequency. If the curve drops steeply, a small cache captures most traffic. If it's flat, you need a larger cache or a different strategy (like result-component caching).

09 Key Takeaway

Summary

Cache query results aggressively. Zipf's law means a small cache handles a large fraction of traffic. Use LRU for simplicity, LFU when access frequency patterns are stable.

Layer your caches. Client → CDN → Application → Engine. Each layer catches different query patterns and reduces load on downstream systems.

Warm your caches. After a deploy, restart, or scale event, pre-load the top queries to avoid a cold-start latency spike that can cascade into failures.

$$ \text{Effective Latency} = (1 - \text{hit\_rate}) \times \text{miss\_latency} + \text{hit\_rate} \times \text{hit\_latency} $$
Cache hit rate is the single most impactful knob for search performance

Common Caching Pitfalls

Cache Stampede

When a popular cache key expires, hundreds of concurrent requests all miss and hit the backend simultaneously. Use lock-based refresh or early expiry jitter to prevent this.

Cache Pollution

One-time or rare queries fill the cache and evict popular entries. LFU or admission policies (like TinyLFU) help prevent pollution by only caching items that prove their frequency.

Thundering Herd

Similar to stampede, but occurs when the cache layer itself restarts. Solution: stagger TTLs with random jitter, and implement cache warming on startup.

Inconsistency Window

Stale cached data served after a write. Acceptable for search (eventual consistency), but set clear staleness SLAs. Monitor the gap between writes and cache invalidation.

Pro Tip

Implement stale-while-revalidate — serve the stale cached result immediately while asynchronously refreshing it in the background. Users get instant responses, and the cache stays warm. This is what Cache-Control: stale-while-revalidate=60 does at the HTTP level.
