01 Why Evaluate RAG Separately?

A RAG system has two independently failing components: retrieval and generation. Evaluating only the final answer hides where things went wrong.

🔍

Analogy: Imagine grading a student's essay. If the essay is wrong, was it because they researched the wrong sources (retrieval failure), or because they had good sources but misinterpreted them (generation failure)? You need to grade both the research and the writing separately.

Bad Retrieval, Good Generation

The LLM perfectly summarizes irrelevant context. The answer sounds great but is completely wrong. This is the most dangerous failure mode because it looks correct and reads confidently.

Good Retrieval, Bad Generation

The right chunks were retrieved but the LLM hallucinated, ignored the context, or extracted the wrong information. Easier to catch because the evidence is right there in the context.

Why End-to-End Evaluation Alone Fails

If you only evaluate the final answer, you can't tell whether a wrong answer came from bad retrieval or bad generation. This matters because the fixes are completely different:

  • Bad retrieval: Fix chunking, embedding model, metadata filters, re-ranking
  • Bad generation: Fix prompt template, grounding instructions, model selection

Component-level evaluation (measuring retrieval and generation separately) gives you actionable diagnostics.

Evaluation is Not Optional

"The system seems to be working" is not acceptable for production RAG. Without systematic evaluation, you will miss silent failures where the system confidently returns wrong answers. These are the most dangerous failures because users trust the system and act on incorrect information.

02 Metric 1: Context Relevance

Are the retrieved chunks actually relevant to the question? This metric evaluates the retrieval component in isolation, before the LLM ever sees the context.

$$\text{Context Relevance} = \frac{\text{Number of relevant chunks retrieved}}{\text{Total chunks retrieved}}$$
Measures retrieval precision — are we retrieving the right chunks?

What It Catches

  • Embedding model returning semantically distant chunks
  • Keyword mismatch between query and indexed terms
  • Stale or outdated content being retrieved
  • Chunks from wrong document sections
  • Index contamination from unrelated documents

High Score (0.8+)

Most retrieved chunks directly address the question. The retrieval pipeline is working well. The LLM has strong evidence to work with.

Low Score (<0.4)

Retrieved chunks are off-topic. Fix your chunking strategy, try a better embedding model, add metadata filtering, or consider a re-ranker.

Common Causes of Low Context Relevance

CauseSymptomFix
Poor chunkingChunks mix multiple topicsUse semantic or recursive chunking
Wrong embedding modelSemantic similarity doesn't match human judgmentTest multiple models on your domain
Vocabulary mismatchUser terms differ from doc termsAdd HyDE or multi-query retrieval
No metadata filteringResults from irrelevant categoriesAdd category/date filters to search
Stale indexOutdated info ranked highlyImplement incremental re-indexing

03 Metric 2: Faithfulness

Does the answer stick to the provided context, or does the LLM hallucinate?

$$\text{Faithfulness} = \frac{\text{Claims in answer supported by context}}{\text{Total claims in answer}}$$
Measures grounding — 1.0 means zero hallucination

What It Catches

  • LLM adding information not in the retrieved context
  • Fabricated statistics, dates, or names
  • Overconfident answers when context is insufficient
  • Subtle distortions of factual claims
⚖️

Think of a courtroom: A faithful witness only testifies about what they personally observed (the context). An unfaithful witness adds speculation and hearsay. We want our RAG system to be a faithful witness.

Faithful Answer

Context: "Python 3.12 was released in October 2023."

Answer: "Python 3.12 was released in October 2023."

Score: 1.0 — Every claim is directly supported.

Unfaithful Answer

Context: "Python 3.12 was released in October 2023."

Answer: "Python 3.12, created by Guido van Rossum, was released in October 2023 with 40% speed improvements."

Score: 0.33 — Only the release date is in context. Creator and speed claims are hallucinated.

Measuring Faithfulness in Practice

Automated faithfulness scoring decomposes the answer into individual claims, then checks each against the context. Tools like RAGAS, DeepEval, and TruLens use LLM-as-judge approaches for this. Keyword overlap heuristics (like the one in our playground) are a fast approximation but miss paraphrasing.

04 Metric 3: Answer Relevance

Does the answer actually address what the user asked?

$$\text{Answer Relevance} = \text{Semantic Similarity}(\text{question},\; \text{answer})$$
Measures whether the answer is on-topic

What It Catches

  • Answer discusses the right topic but misses the specific question
  • Tangential responses that address context but not query
  • "I don't know" when the context actually contains the answer
  • Overly broad answers that don't address specifics

High Score (0.9)

Q: What is the time complexity of binary search?
A: Binary search has O(log n) time complexity because it halves the search space with each comparison.

Directly addresses the specific question asked.

Low Score (0.2)

Q: What is the time complexity of binary search?
A: Binary search is a classic algorithm taught in computer science courses. It was invented by John Mauchly in 1946.

Talks about binary search but never answers the actual question.

Measuring Answer Relevance

There are several approaches to computing answer relevance, ranging from simple heuristics to LLM-based judges:

Keyword Overlap

Count shared terms between question and answer. Fast but misses synonyms and paraphrasing. Good for a quick first pass.

Embedding Similarity

Embed both question and answer, compute cosine similarity. Handles paraphrasing well. The approach used by RAGAS framework.

LLM-as-Judge

Ask an LLM "Does this answer address the question?" on a 1-5 scale. Most accurate but slowest and most expensive.

Question Regeneration

Generate questions from the answer, check if they match the original. If the answer is relevant, regenerated questions should be similar. Used by RAGAS for answer relevance scoring.

Practical Tip

When answer relevance is low but context relevance and faithfulness are high, the problem is almost always in the prompt template. The LLM has the right information and is using it faithfully, but it's not extracting the specific answer the user needs. Add explicit instructions like "Directly answer the question in the first sentence" to fix this.

Improving Answer Relevance

If answer relevance is consistently low despite good retrieval, the issue is almost always in the prompt template. Add explicit instructions like "Answer the specific question asked" and "Be concise and directly address the query." Chain-of-thought prompting can also help the model stay focused on the question.

Answer Relevance vs Faithfulness

These metrics are independent. An answer can be highly faithful (everything it says is in the context) but completely irrelevant (it doesn't answer the question). Conversely, an answer can be highly relevant (it addresses the question perfectly) but unfaithful (it hallucinated the response).

Faithful but Irrelevant

Q: How fast is binary search?
Context: "Binary search requires a sorted array..."
A: "Binary search requires a sorted array as input." (True but doesn't answer the speed question)

Relevant but Unfaithful

Q: How fast is binary search?
Context: "Binary search is a search algorithm."
A: "Binary search runs in O(log n) time." (Correct answer but not from the context)

🎯

The 2×2 matrix of RAG quality: Faithful + Relevant = ideal. Faithful + Irrelevant = the system is honest but unhelpful. Unfaithful + Relevant = the answer is correct but we got lucky — can't trust the pipeline. Unfaithful + Irrelevant = complete failure. You need both metrics to be high simultaneously.

05 Metric 4: Chunk Utilization

How much of the retrieved context did the LLM actually use?

$$\text{Chunk Utilization} = \frac{\text{Chunks referenced in answer}}{\text{Total chunks provided}}$$
Measures efficiency of context usage

What It Catches

  • Retrieving 10 chunks but only using 2 (wasting context window)
  • LLM fixating on the first chunk and ignoring the rest
  • Retrieved chunks being redundant (same info repeated)
  • Opportunity to reduce K and save tokens/cost
  • Position bias — LLMs attend more to chunks at the beginning

Good Utilization (0.6-0.8)

Most chunks contribute something to the answer. The retrieval pipeline is well-calibrated and not over-fetching. Some chunks may serve as supporting context without being directly cited.

Low Utilization (<0.3)

Most of the context window is wasted on chunks the LLM ignores. You're paying for tokens that add noise, not signal. Reduce K, improve re-ranking, or check for chunk redundancy.

Optimal Utilization

Perfect utilization (1.0) isn't the goal — some chunks serve as background context. Aim for 0.5-0.8. Below 0.3 means you're retrieving too many chunks. Above 0.9 means you might not be retrieving enough variety.

How the Four Metrics Interact

No single metric tells the whole story. The power of this framework comes from reading the metrics together.

08 Building an Eval Dataset

Automated metrics are approximations. To truly evaluate your RAG system, you need a ground-truth evaluation dataset.

Step 1: Collect Real User Questions

Use actual queries from your users or domain experts. Don't make up questions — they'll miss the real failure modes. Pull from search logs, support tickets, and FAQ databases.

Step 2: Annotate Golden Answers

For each question, have a domain expert write the ideal answer and identify which source passages support it. These golden passages become the ground truth for retrieval metrics.

Step 3: Include Edge Cases

Add questions where the answer isn't in the knowledge base, ambiguous questions, and multi-hop questions that require combining multiple chunks. Also include negative examples where the system should say "I don't know."

Step 4: Automate and Monitor

Run your eval suite on every pipeline change. Track metrics over time. Alert when scores drop below thresholds. Version your eval dataset alongside your code.

Eval Dataset Anti-Patterns

Don't auto-generate eval questions with the same LLM you're evaluating. Don't use only simple factual queries. Don't skip adversarial examples (queries designed to trigger hallucination). Don't evaluate once and forget — eval is ongoing.

Popular RAG Evaluation Frameworks

RAGAS

Open-source framework specifically designed for RAG evaluation. Computes Context Relevance, Faithfulness, Answer Relevance, and Answer Correctness using LLM-as-judge.

DeepEval

Unit testing framework for LLM applications. Provides RAG-specific metrics plus custom metric definitions. Integrates with pytest for CI/CD pipelines.

TruLens

Evaluation and tracking for LLM apps. Provides feedback functions for grounding, relevance, and safety. Includes a dashboard for monitoring metrics over time.

LangSmith

LangChain's evaluation platform. Supports dataset management, automated evals, human annotation, and A/B testing of RAG configurations.

Human vs Automated Evaluation

Automated metrics are scalable but approximate. Human evaluation is accurate but expensive. The best approach combines both.

Calibrate Your Automated Evals

Run 50-100 examples through both human evaluation and your automated metrics. Compute the correlation. If automated metrics disagree with humans more than 20% of the time on faithfulness, adjust your prompts or switch to a different LLM judge. Re-calibrate quarterly as your data evolves.

09 Key Takeaway

📊

Measure retrieval and generation separately. Context Relevance tells you if retrieval is working. Faithfulness tells you if the LLM is grounding its answers. Answer Relevance tells you if the user's question is being addressed. Chunk Utilization tells you if you're using your context window efficiently. All four together give you a complete picture of RAG health.

Healthy RAG Thresholds

  • Context Relevance > 0.7
  • Faithfulness > 0.8
  • Answer Relevance > 0.7
  • Chunk Utilization 0.5-0.8

Warning Signs

  • High faithfulness + low context relevance = lucky
  • Low faithfulness + high context relevance = hallucinating
  • All metrics low = fundamental pipeline issue
  • Utilization < 0.2 = retrieving too much
