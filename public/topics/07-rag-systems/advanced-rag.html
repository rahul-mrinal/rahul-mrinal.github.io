01 When Basic RAG Falls Short

A standard retrieve-then-generate pipeline works well for straightforward factual queries. But it struggles with several common scenarios.

Vague Queries

"Tell me about performance issues" — Performance of what? Database queries? React rendering? Athletic training? The embedding doesn't know which direction to search.

Complex Multi-hop Questions

"How does the caching strategy affect the query latency SLA?" — This requires combining information from caching docs AND SLA docs, which may not co-occur in any single chunk.

Context-Dependent Queries

"What changed since last release?" — Requires temporal reasoning and understanding of what "last release" means in context.

Vocabulary Mismatch

User says "speed up my app," but docs say "optimize performance" and "reduce latency." The embedding may not bridge this gap well enough.

The Common Thread

All these failures share a root cause: the user's query, as written, doesn't directly match the relevant chunks in embedding space. Advanced RAG patterns address this by transforming the query, expanding the search, or restructuring the index.

02 Pattern 1: HyDE (Hypothetical Document Embeddings)

Instead of embedding the raw query, ask an LLM to generate a hypothetical answer, then embed that answer as the search query. The hypothesis lives in the same "language" as your documents, producing better semantic matches.

HyDE Pipeline
Vague Query
→
LLM: Generate Hypothesis
→
Embed Hypothesis
→
Vector Search
→
Better Results
🎯

Analogy: If you're looking for a specific book in a library but only have a vague idea of what it's about, you might describe what you think the book would say. The librarian can then match your description against actual book summaries — which works much better than matching against your vague question.

Strengths

  • Bridges vocabulary mismatch
  • Works great for vague queries
  • No index changes required
  • Simple to implement

Limitations

  • Extra LLM call adds latency (~500ms)
  • Hypothesis might be wrong, biasing search
  • Extra cost per query
  • Doesn't help if the info isn't indexed

04 Pattern 2: Multi-Query Retrieval

Instead of one query, generate multiple rephrased versions of the question and search with each. Combine the results to catch chunks that any single phrasing might miss.

Multi-Query Pipeline
Original Query
→
LLM: 3 Rephrasings
→
3× Vector Search
→
Union + Dedup
→
Re-rank All

Why It Works

Different phrasings emphasize different aspects of the question. "How to speed up database queries" might miss chunks about "query optimization," but the rephrasing "database query optimization techniques" catches them. The union captures a broader, more complete set of relevant chunks.

Strengths

  • Higher recall than single-query retrieval
  • Handles ambiguous queries well
  • Catches different vocabulary
  • Easy to implement with any LLM

Limitations

  • 3× retrieval latency (can parallelize)
  • More chunks to re-rank
  • Extra LLM call for rephrasings
  • Diminishing returns beyond 3-4 queries

06 Pattern 3: Parent-Child Chunking

Index small chunks for precision, retrieve large chunks for context. Small "child" chunks are used for embedding and retrieval, but when a match is found, the full "parent" chunk is returned to the LLM.

Parent-Child Index Structure
Document
→
Large Parent Chunks
→
Small Child Chunks
Query matches child → Return parent for context
📑

Analogy: Think of a textbook's index. The index entries (child chunks) are very specific: "gradient descent, p.142." But when you look it up, you read the full section (parent chunk) on pages 140-145 to get the complete context.

How It Works

  • Parent chunks: 1000-2000 tokens — full paragraphs or sections
  • Child chunks: 100-200 tokens — individual sentences or small passages
  • Each child stores a pointer to its parent
  • Search uses child embeddings, but returns parent text

08 Pattern 4: Self-RAG

In self-RAG, the model decides when it needs retrieval and grades its own outputs. Instead of always retrieving, the model first assesses whether external knowledge is needed.

Self-RAG Decision Flow
Query
→
Need retrieval?
↓ Yes / No
Retrieve + Generate
Generate Directly
↓
Self-grade: Supported? Relevant? Useful?

Three Self-Assessment Tokens

  • [Retrieve]: Does this query need external knowledge? (Yes/No)
  • [IsSupported]: Is the generated claim supported by retrieved evidence? (Fully/Partially/No)
  • [IsUseful]: Is this response actually useful to the user? (5-point scale)

Strengths

  • Skips retrieval when unnecessary (faster)
  • Self-corrects hallucinations
  • Adaptive to query difficulty
  • Built-in quality control

Limitations

  • Requires fine-tuned model with special tokens
  • More complex training pipeline
  • Self-assessment can be unreliable
  • Higher latency for multi-pass generation

Self-RAG Decision Examples

QueryRetrieve?Reasoning
"What is 2 + 2?"NoSimple arithmetic — LLM can answer directly
"What was our Q3 revenue?"YesRequires specific factual data from knowledge base
"Explain gradient descent"MaybeGeneral knowledge — retrieve for domain-specific nuance
"What changed in config v2.4?"YesVersion-specific fact that must come from docs
"Write a haiku about spring"NoCreative task with no factual requirement
Simulating Self-RAG Without Fine-Tuning

You can approximate self-RAG with a two-step prompt: first ask the LLM "Does this question require external knowledge?" and branch based on the response. This is simpler than full self-RAG fine-tuning but captures 80% of the benefit for much less complexity.

10 Key Takeaway

🧠

Start simple, add complexity only when metrics demand it. Basic RAG works for 70-80% of use cases. Add re-ranking first (easiest win), then consider HyDE or multi-query for recall issues, parent-child for context issues, and self-RAG only for sophisticated production systems where you need adaptive retrieval.

Combining Patterns

These patterns aren't mutually exclusive. Many production systems stack multiple patterns for maximum quality.

Effective Combinations

  • HyDE + Re-ranking: HyDE improves recall, re-ranking improves precision
  • Multi-Query + Parent-Child: Broader search with richer context
  • Parent-Child + Re-ranking: Precise child matching, contextual parent retrieval

Avoid These Combos

  • HyDE + Multi-Query: Both transform the query — redundant and expensive
  • All patterns at once: Latency explosion, diminishing returns
  • Self-RAG + anything: Self-RAG already decides what to use
When to Go Advanced

Only adopt advanced patterns after you've measured baseline RAG quality with proper evaluation metrics. If your basic RAG + re-ranker achieves 80%+ on all evaluation metrics, advanced patterns offer diminishing returns. Focus on data quality, chunking strategy, and prompt engineering first — these give 3-5x more improvement per engineering hour invested.
