01 The Index Card Analogy

Imagine you need to study for an exam. You have a 500-page textbook. You could write everything onto index cards — but how much goes on each card?

🃏

Too small (one sentence per card): Each card is precise but has no context. When you pull a card, you can't tell what topic it belongs to. "The mitochondria is the powerhouse of the cell" — great, but is this about biology, energy, or cell structure?

📦

Too large (entire chapters per card): Each card has everything, but you can never find the specific fact you need. When someone asks "What does the mitochondria do?", you hand them 40 pages and say "it's in there somewhere."

Too Small

  • Lost context around statements
  • Fragments of sentences
  • Too many chunks to search
  • Embedding quality degrades

Too Large

  • Diluted relevance signal
  • Harder to match queries precisely
  • Wastes context window budget
  • Forces LLM to find needle in haystack
Key Insight

The right chunk size balances precision (finding exactly what's relevant) with context (having enough surrounding information to be useful). This balance depends on your data, your queries, and your embedding model.

Rule of Thumb

For most RAG systems, 200-500 tokens (roughly 800-2000 characters) is the sweet spot. Smaller chunks improve retrieval precision; larger chunks preserve more context for the LLM. Start at ~300 tokens and adjust based on evaluation.

03 Five Chunking Strategies

Not all chunking is created equal. Each strategy makes different trade-offs between simplicity, semantic coherence, and implementation cost.

1. Fixed-Size Chunking

Split text every N characters or tokens, regardless of content boundaries.

  • Simplest to implement
  • Breaks mid-sentence, mid-word
  • Use when: prototyping, uniform document types

2. Sentence-Based Chunking

Split on sentence boundaries, grouping sentences until chunk size is reached.

  • Preserves complete thoughts
  • Depends on sentence detection quality
  • Use when: clean prose, Q&A content

3. Paragraph-Based Chunking

Split on paragraph breaks (double newlines), treating each paragraph as a unit.

  • Natural topic boundaries
  • Chunk sizes vary widely
  • Use when: well-structured documents, articles

4. Semantic Chunking

Use embeddings to detect topic shifts, splitting when similarity between consecutive sentences drops below a threshold.

  • Best semantic coherence
  • Computationally expensive (needs embedding calls)
  • Use when: high quality matters, budget allows

5. Recursive Chunking

Try splitting by paragraphs first; if chunks are too large, split by sentences; if still too large, split by characters. Used by LangChain's RecursiveCharacterTextSplitter.

  • Adaptive to document structure
  • Balances coherence and size
  • Use when: mixed document formats, production systems

Choosing a Strategy for Your Document Type

Structured Documents

API docs, wikis, knowledge bases with clear headings and sections. Use heading-aware chunking: split on section boundaries, then apply recursive within each section. Preserve heading hierarchy as metadata.

Unstructured Text

Emails, chat logs, transcripts without clear formatting. Use sentence-based chunking with overlap, or semantic chunking if quality justifies the embedding cost. Clean the text first (remove boilerplate, signatures).

Code and Technical Docs

Source code, config files, technical specifications. Use syntax-aware chunking: split on function/class boundaries for code, on section headers for specs. Include the function signature or header in each chunk.

Tables and Structured Data

CSVs, database schemas, spreadsheets. Convert rows or small row groups into natural language descriptions. Each chunk should be a self-contained data point with column headers included.

Multi-Format Corpora

Real knowledge bases contain mixed document types. The best approach is a document-type dispatcher that detects the format (PDF, HTML, Markdown, code) and applies the appropriate chunking strategy for each. Don't use one strategy for everything.

05 Overlap Importance

When you split text into chunks without overlap, critical information that spans a chunk boundary gets torn apart. Overlap ensures that boundary content appears in at least two chunks.

No Overlap Risks

  • Key facts split across chunk boundary
  • Sentences cut in half
  • Entity references separated from context
  • Retrieval misses boundary content

With Overlap Benefits

  • Boundary info appears in two chunks
  • Complete sentences preserved
  • Better retrieval recall
  • Small cost: slightly more chunks & storage
Overlap Rule of Thumb

Use 10-20% overlap relative to chunk size. For 500-character chunks, use 50-100 characters of overlap. Too much overlap creates redundant chunks; too little defeats the purpose.

06 Token Counting

When we say "chunk size," do we mean characters, words, or tokens? These are very different measures, and confusing them is a common source of bugs.

Characters

Individual letters, spaces, punctuation. "Hello world" = 11 characters. Simplest to count but least meaningful — different languages pack different information per character.

Words

Space-separated tokens. "Hello world" = 2 words. Intuitive for humans but misleading for models — "antidisestablishmentarianism" is 1 word but many tokens.

Tokens

Subword units used by the model's tokenizer. "Hello world" ≈ 2 tokens. "Unbelievably" ≈ 3 tokens. This is what actually matters for context windows.

Tokenizer Differences

Different models use different tokenizers. GPT-4 (cl100k_base) and Claude (custom BPE) may tokenize the same text differently. A chunk that fits in one model's context window may overflow another's. Always test with your target model's tokenizer.

Why Tokens Matter for RAG

Tokens are the fundamental unit of consumption in LLM systems. They affect three critical dimensions:

Context Window

The maximum tokens the LLM can process at once. Your system prompt + retrieved chunks + response must all fit. Chunk sizes in tokens directly determines how many chunks you can include.

Cost

LLM APIs charge per token. More chunks = more input tokens = higher cost per query. Efficient chunking directly reduces your API bill.

Embedding Quality

Embedding models have max input lengths (typically 512-8192 tokens). Chunks exceeding this limit get truncated silently, losing information from the end of the chunk.

07 Testing Your Chunks

Chunk quality isn't something you can eyeball — you need a systematic evaluation approach. Here's a framework for testing your chunking strategy.

Step 1: Create Test Queries

Write 20-50 questions that your users would actually ask. Include factual lookups, conceptual questions, and multi-hop reasoning queries.

Step 2: Annotate Ground Truth

For each question, identify which passage(s) in your source documents contain the answer. These become your "golden chunks."

Step 3: Measure Retrieval Quality

Run each query through your retrieval pipeline. Check if the golden chunks appear in the top-K results. Compute Recall@K and Mean Reciprocal Rank (MRR).

Step 4: Iterate on Strategy

If recall is low, try smaller chunks. If the LLM struggles with context, try larger chunks. Test 3-5 chunk sizes systematically and pick the best performer.

The 20-Query Test

Write 20 questions you'd expect users to ask. For each, identify which passage in your source contains the answer. Chunk your documents, run retrieval, and check if the golden passage appears in the top 5 results. If Recall@5 is below 0.7, your chunking strategy needs work.

08 Key Takeaway

🎯

Chunking is the foundation of RAG quality. No amount of sophisticated retrieval or prompt engineering can compensate for poorly chunked documents. Invest time in getting your chunking strategy right — it has the highest ROI of any RAG optimization.

Do

  • Start with recursive chunking (300-500 tokens)
  • Use 10-20% overlap
  • Evaluate with real user queries
  • Test multiple strategies empirically
  • Consider document structure in your strategy

Don't

  • Use fixed-size chunking in production blindly
  • Skip overlap entirely
  • Assume one chunk size fits all document types
  • Confuse characters with tokens
  • Skip retrieval evaluation
