01 Two Phases

A RAG system operates in two distinct phases. Confusing them is a common source of architectural mistakes.

Offline Phase (Indexing)

Runs once (or periodically) to prepare your knowledge base. This happens before any user query.

  • Chunk documents
  • Generate embeddings
  • Store in vector database

Online Phase (Query)

Runs in real-time for every user question. Latency matters here.

  • Embed the query
  • Search vector DB for top-K
  • Re-rank results
  • Assemble prompt with context
  • Generate answer with LLM
📚

Library analogy: The offline phase is like cataloging and shelving all the books. The online phase is when a patron asks a question — you search the catalog, pull relevant books from the shelves, pick the best passages, and synthesize an answer.

Critical Design Decision

You must use the same embedding model for indexing (offline) and querying (online). If you change your embedding model, you must re-index all documents. This is the most common "gotcha" in RAG deployments and has caused many production incidents.

02 Offline Phase: Index Your Knowledge

The offline pipeline transforms raw documents into a searchable vector index.

Raw Documents
→
Chunker
→
Embedding Model

Vector DB

Chunker

Splits documents into passages of 200-500 tokens. Uses recursive splitting for best quality.

Embedding Model

Converts each chunk into a dense vector (768-1536 dimensions). Models like text-embedding-3-small, e5-large-v2, or bge-large-en.

Vector Database

Stores vectors with metadata for fast approximate nearest neighbor (ANN) search. Options include Pinecone, Weaviate, Qdrant, Milvus, and pgvector.

Metadata Matters

Store metadata alongside each chunk: source document, page number, section title, timestamp. This enables filtered search (e.g., only search documents from the last 30 days) and source citation in answers.

Similarity Metrics for Retrieval

Vector databases use different distance metrics to find the nearest neighbors. The choice of metric affects both accuracy and speed.

$$\text{Cosine Similarity} = \frac{\vec{q} \cdot \vec{d}}{\|\vec{q}\| \cdot \|\vec{d}\|}$$
Most common for text embeddings — measures directional similarity regardless of magnitude

Cosine Similarity

Direction-based comparison. Normalized vectors make magnitude irrelevant. Best for text embeddings.

Dot Product

Faster than cosine (no normalization). Equivalent to cosine when vectors are unit-normalized. Use when embeddings are pre-normalized.

Euclidean (L2)

Measures absolute distance in vector space. Sensitive to magnitude. Less common for text; more common for image embeddings.

Choosing K

The value of K (how many chunks to retrieve) is a precision-recall trade-off. Low K (3-5): Fast, precise, but may miss relevant context. High K (20-50): Better recall but includes more noise and consumes more context window. Start with K=10 and adjust based on your evaluation metrics. Always pair high K with a re-ranker to filter noise.

05 Re-ranking Impact

Initial retrieval uses bi-encoder similarity (fast but approximate). Re-ranking uses a cross-encoder that reads query and chunk together for much better relevance judgment.

Re-ranking Comparison

Why Re-rank?

Bi-encoders embed query and document independently — they can't model fine-grained interactions. Cross-encoders process (query, doc) as a pair, capturing word-level interactions. This costs more compute but typically boosts nDCG@5 by 15-30%.

Bi-Encoder vs Cross-Encoder

Bi-Encoder (Retrieval)

Architecture: Encodes query and document separately into vectors, then computes similarity.

  • Can pre-compute document embeddings
  • Scales to millions of documents
  • ~50ms for thousands of comparisons
  • Less accurate for nuanced relevance

Cross-Encoder (Re-ranking)

Architecture: Processes [query; document] as a single input, outputting a relevance score.

  • Full attention between query and document tokens
  • Much more accurate but O(n) per comparison
  • ~100ms for 20-50 candidates
  • Can't pre-compute — runs at query time

When to Skip Re-ranking

Re-ranking adds latency and cost. In some scenarios, it may not be worth it:

Skip Re-ranking When

  • K is already small (3-5 chunks)
  • Queries are very specific and unambiguous
  • Latency budget is extremely tight (<500ms total)
  • Bi-encoder precision is already > 0.9

Always Re-rank When

  • K is large (20+ chunks)
  • Queries are vague or ambiguous
  • Answer quality is more important than speed
  • You're mixing multiple document types in results
The Retrieve-and-Rerank Pattern

The optimal pattern is retrieve broadly (K=20-50), re-rank tightly (keep top 3-5). The bi-encoder casts a wide net cheaply, then the cross-encoder precisely identifies the gems. This consistently outperforms either approach alone.

06 Context Window Budget

Every LLM has a fixed context window. Your prompt, retrieved chunks, and expected response all compete for the same limited space. Going over budget silently truncates context or errors out.

Context Window Budget Calculator

Budget Status
Adjust sliders to calculate.

Context Window Strategies

Small Context (4K-8K)

Be very selective: 3-5 small chunks, concise system prompt, short answers. Re-ranking is essential to ensure the few chunks you include are the best ones.

Large Context (32K-128K)

More forgiving: include 10-20 chunks, detailed system prompt. But don't be wasteful — more context doesn't always mean better answers. "Lost in the middle" phenomenon causes LLMs to ignore content in the middle of long contexts.

"Lost in the Middle" Problem

Research shows that LLMs attend most strongly to the beginning and end of their context window, with weaker attention to the middle. This means the order of your chunks matters. Place the most relevant chunks first and last, with less critical chunks in the middle.

07 Prompt Engineering for RAG

The prompt template is what ties retrieval to generation. A well-designed template makes the LLM ground its answers in the retrieved context.

Basic RAG Prompt Template

System: You are a helpful assistant. Answer the user's question
using ONLY the provided context. If the context doesn't contain
the answer, say "I don't have enough information."

Context:
[Chunk 1]: {chunk_1_text}
[Chunk 2]: {chunk_2_text}
[Chunk 3]: {chunk_3_text}

Question: {user_question}

Answer:

Citation-Aware Template

System: Answer using ONLY the numbered sources below.
Cite sources as [1], [2], etc. after each claim.
If no source supports a claim, do not make it.

Sources:
[1] {source_1} — {chunk_1_text}
[2] {source_2} — {chunk_2_text}
[3] {source_3} — {chunk_3_text}

Question: {user_question}

Tips for Better Prompts

  • Explicitly instruct "only use provided context"
  • Number your sources for citation
  • Include "say I don't know" as a fallback
  • Place context before the question

Common Mistakes

  • No grounding instruction → hallucination
  • Context after question → model ignores it
  • Too many chunks → dilutes signal
  • No citation format → unverifiable answers

Prompt Template A/B Testing

Don't guess which prompt template works best — test them. Run your eval dataset against 2-3 templates, measure faithfulness and answer relevance, and pick the winner. Small prompt changes can cause 10-20% swings in output quality.

08 Key Takeaway

🔗

RAG is a pipeline, and every stage matters. Great retrieval with bad prompting wastes context. Perfect prompts with bad retrieval grounds answers in irrelevant information. Re-ranking is the highest-ROI addition to a basic RAG pipeline — it's cheap, easy, and typically improves answer quality by 20-30%.

Pipeline Optimization Checklist

Do

  • Use the same embedding model for indexing and querying
  • Add a re-ranker — highest ROI improvement
  • Store rich metadata with each chunk
  • Monitor latency at each pipeline stage
  • Test with real user queries, not synthetic ones
  • Version your prompts like you version code

Don't

  • Use different embedding models for index vs query
  • Retrieve more chunks than your context window allows
  • Skip evaluation — "it looks right" isn't a metric
  • Hardcode prompts — make them configurable
  • Ignore metadata filtering — it's a huge precision boost
  • Forget to handle the "no relevant results" case

The 80/20 of RAG Quality

In our experience, the biggest quality wins come from (in order): 1) Better chunking (switch to recursive + overlap), 2) Adding a re-ranker (cross-encoder after retrieval), 3) Prompt engineering (grounding instructions + citation format), and 4) Metadata filtering (narrow search scope). Advanced patterns like HyDE and multi-query are the remaining 20%.
