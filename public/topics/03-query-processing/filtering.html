Filtering in Search

When to use filters vs ranking, and the pre vs post filter debate

01 Ranking vs Filtering

These are fundamentally different operations that beginners often conflate. Getting the distinction right is critical for building search systems that behave predictably.

Ranking (Scoring)

Assigns a continuous score to every document. All documents survive; they're just reordered. A low-ranked doc might still be the best result if nothing else matches.

score(doc) → 0.0 … 1.0

Effect: Changes the order of results

Filtering (Boolean)

Makes a binary decision: include or exclude. No middle ground. A filtered-out document is invisible to the user regardless of how relevant it might be.

filter(doc) → true | false

Effect: Changes the set of results

🎯

Analogy: Ranking is like sorting job applicants by qualifications — everyone gets a ranking. Filtering is like the "must have work authorization" checkbox — no exceptions, you either pass or you're out.

When to Use Which

Use filtering for non-negotiable constraints (language, region, availability). Use ranking for everything that admits degrees of preference (relevance, recency, popularity). The grey area — like "prefer in-stock but show out-of-stock too" — is where product decisions live.

Filter Cardinality Matters

Low Cardinality (<100 values)

Category, color, size, brand. Best approach: bitmap index — one bitmap per value, combine with bitwise AND/OR. Extremely fast for any combination.

High Cardinality (>10K values)

User ID, product SKU, exact price. Best approach: hash index or B-tree. Bitmaps become sparse and waste memory. Consider inverted index for multi-value fields.

Continuous Values (Price, Date, Score)

Range filters on continuous values use sorted arrays or B-trees. For approximate range queries on high-volume data, consider histogram-based bucketing: precompute buckets ($0-25, $25-50, …) and filter by bucket, then refine within the matching bucket.

Elasticsearch Mapping Tip

In Elasticsearch, use the keyword type (not text) for filterable fields. text fields are analyzed (tokenized, stemmed) which breaks exact match filters. A common beginner mistake is mapping "category" as text and then wondering why term queries don't match.

03 Pre-Filter vs Post-Filter

Should you filter before ranking (smaller search space, faster) or after (full recall, then trim)? The answer depends on your data distribution and latency requirements.

Pre-Filter

Flow: Filter → Retrieve → Rank

Pros: Faster retrieval (smaller search space), lower compute cost

Cons: May miss relevant docs if filter is too restrictive, can degrade ANN quality for vector search

Post-Filter

Flow: Retrieve → Rank → Filter

Pros: Full recall from retrieval, ranking quality unaffected

Cons: Wastes compute scoring filtered-out docs, may return fewer results than expected

What to Look For

With identical filters, pre-filter and post-filter usually return the same set of results but potentially in different order. The order can differ because pre-filtering changes the BM25 statistics (IDF, avgdl) — removing documents from the corpus before scoring alters the math. In production, this ranking difference is usually small, but for edge cases it can matter.

When Pre-Filter Breaks Vector Search

The HNSW Graph Problem

HNSW graphs are built over all documents. If you pre-filter 80% of nodes, the remaining graph is sparse and disconnected — the ANN search can't find good candidates because it can't navigate through filtered-out nodes. Solutions:

  • Partition indexes: Separate HNSW per category (Pinecone namespaces)
  • Filterable HNSW: Traverse graph but skip non-matching nodes (Qdrant, Weaviate)
  • Brute-force fallback: If filter is very selective, skip ANN and scan linearly
  • Over-retrieve + post-filter: Retrieve 5× candidates, filter after

04 Faceted Search

Facets show users how many results are available for each filter value, helping them navigate without dead ends. This is the gold standard for filter UX in e-commerce and catalog search.

🏬

Analogy: Faceted search is like the aisle signs in a store. Instead of wandering blindly, you can see "Shoes (47)" and "Accessories (12)" and immediately know where to go. The count tells you whether it's worth exploring that aisle.

Key Facet Design Decisions

Conjunctive (AND)

Selecting "shoes" AND "Nike" shows only Nike shoes. Each additional selection narrows results. Most common for cross-category filters.

Disjunctive (OR)

Selecting "Nike" OR "Adidas" shows both brands. Each additional selection widens results within that facet. Used for same-category multi-select.

Interactive Faceted Search

Click any facet value to filter results. Notice how facet counts update dynamically to reflect the current selection. Click again to deselect.

Facet Count Computation

Computing accurate facet counts is expensive — for each facet value, you need to count how many documents match the current filters plus that value. Elasticsearch solves this with aggs (aggregations) computed alongside the search, using approximate counting for large cardinalities. For vector search engines (Pinecone, Weaviate), facet counting is harder and often approximated.

Facet UX Patterns

05 Filter Performance

Fast filtering is the backbone of interactive search. Users expect filters to feel instant (<50ms), which requires careful data structure choice.

Bitmap / Bitset Approach

For each filter value, maintain a bitmap where bit i is 1 if document i matches. Combining filters becomes a bitwise AND/OR, which modern CPUs process at billions of bits per second.

Bitmap Index for "category"
shoes
1 0 1 1 0 0 1 0
clothing
0 1 0 0 1 0 0 1
accessories
0 0 0 0 0 1 0 0
AND with "in_stock = true"
in_stock
1 1 0 1 1 1 0 0
→
shoes ∧ stock
1 0 0 1 0 0 0 0

Roaring Bitmaps

Compressed bitmap format used by Elasticsearch, Lucene, and most search engines. Uses a hybrid of arrays, bitmaps, and run-length encoding depending on density per 64K chunk. Achieves near-raw bitmap speed with 10-100× compression for sparse filters.

Posting List Intersection

For inverted-index-backed filters, intersect sorted posting lists using skip pointers. O(min(|A|,|B|)) when lists are very different sizes. Lucene's two-phase iterator applies cheap checks first, expensive checks only on survivors.

Elasticsearch Under the Hood

Elasticsearch maintains a "filter cache" of frequently used filters as Roaring Bitmaps. When a cached filter is reused, it's a single bitwise AND — microseconds even on billions of docs. This is why filter queries should use filter context (cacheable) not must context (scored, uncacheable).

06 When Filters Go Wrong

The biggest danger of aggressive filtering: zero results. An empty result page is the worst UX outcome in search — worse than showing slightly wrong results.

The Empty Results Problem

The Intersection Trap

User searches "red wireless headphones under $30 in stock". Every filter individually matches some products, but the intersection is empty. The user sees nothing and leaves your site.

This happens because filter cardinality multiplies: if each filter passes 50% of docs, four filters together pass 0.5⁴ = 6.25%. For rare combinations, the probability of zero results grows fast.

Fallback Strategies

StrategyHow It WorksTrade-off
Progressive RelaxationRemove filters one at a time (least important first) until results appearNeeds filter priority ordering
Show Near-Misses"No exact matches. Showing results that match 3 of 4 filters"Requires scoring partial matches
Suggest Alternatives"Try removing the price filter" / "Available in blue instead of red"Needs precomputed filter counts
Soft FiltersConvert some filters to ranking signals (prefer in-stock, don't require it)Blurs user intent
Guided NavigationShow greyed-out facets with (0) count before user clicksRequires real-time facet counting

Real-World Examples

Amazon's Approach

Amazon shows facet counts and dynamically removes facet values that would yield zero results. If a filter combination returns too few results, they show "related products" below the fold.

Google Shopping

Google relaxes filters automatically and shows a message: "No results for [all filters]. Showing results for [subset]." The user sees useful results and can manually re-add removed filters.

Production Rule of Thumb

Track your "zero results rate" as a KPI. If more than 5% of filtered queries return zero results, your filter UX needs work. Faceted search (showing counts) is the best prevention — users can see when a combination will yield zero results before clicking.

07 Best Practices

Based on patterns from production search systems at scale.

Use Pre-Filter For

  • Hard constraints (language, region, access control)
  • Filters that remove >90% of corpus
  • Filters on indexed fields (bitmap, B-tree)
  • Multi-tenant systems (tenant isolation)
  • Compliance/legal restrictions

Use Post-Filter For

  • Soft preferences the user might relax
  • Filters that remove <10% of results
  • When result count feedback is needed
  • Dynamic / user-specific filters
  • Filters with high cardinality (many values)

Hybrid Approach (Most Common)

Apply hard filters pre-retrieval (security, language, tenant) and soft filters post-retrieval (availability, recency preference). This gives you the speed of pre-filtering for the big cuts and the flexibility of post-filtering for the nuanced ones.

Decision Framework

Vector Search Gotcha

Pre-filtering with vector search (HNSW) is tricky — if you filter out too many nodes, the graph becomes disconnected and recall drops. Qdrant, Weaviate, and Milvus handle this differently. Some use payload-based filtering during HNSW traversal; others fall back to brute force when filter selectivity is too high. Always benchmark filter + vector together.

08 Key Takeaway

Filters Are Not Ranking

Filtering is a binary gate; ranking is a continuous spectrum. The critical design decision is when to filter (pre vs post) and what to filter vs rank. Apply hard constraints as filters, soft preferences as ranking signals. Always show facet counts so users can self-navigate without hitting dead ends. And always have a fallback strategy for zero results.

Implementation Checklist

StepWhat to DoWhy
1. Classify constraints Label each constraint as "hard filter" or "soft ranking signal" Prevents over-filtering
2. Choose data structures Bitmap for low-cardinality, B-tree for ranges, hash for exact Performance at scale
3. Decide pre vs post Hard constraints pre, soft preferences post Balance recall and speed
4. Add facet counts Show users how many results each filter value yields Prevents empty results
5. Implement fallbacks Progressive relaxation, near-miss display, suggestions Never show zero results
6. Monitor zero-result rate Track % of filtered queries with 0 results as a KPI Continuous improvement

Common Mistakes

Don't Do This

  • Using text type for filter fields in Elasticsearch
  • Filtering by scored relevance threshold (use ranking instead)
  • Applying geo filters after retrieving all docs globally
  • Treating "sort by price" as a filter (it's a ranking signal)
  • Allowing filter combinations that always yield zero results

Do This Instead

  • Use keyword type for exact-match filter fields
  • Use score thresholds only for quality gates, not UX filtering
  • Pre-filter by geo bounding box, then refine with distance
  • Sort is orthogonal to filter — expose as separate UI controls
  • Grey out or hide filter values with (0) results
🚪

Remember: A filter is a door — you're either through or you're not. Ranking is a queue — everyone waits in line, some just move forward. Know which mechanism suits each constraint.
