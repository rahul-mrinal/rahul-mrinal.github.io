From typos to "Did you mean?" and synonym expansion

01 The Typo Problem

Studies show that 10–15% of search queries contain spelling errors. On mobile, the rate jumps to 20%+ due to smaller keyboards and auto-correct failures. Without spell correction, these queries return zero or irrelevant results.

Common Typo Types

  • Insertion: "thhe" → "the"
  • Deletion: "th" → "the"
  • Substitution: "tge" → "the"
  • Transposition: "hte" → "the"

Impact on Search

  • Zero results → user abandons
  • Wrong results → user loses trust
  • Missed revenue (e-commerce: $$$)
  • Higher bounce rate & lower engagement

Typo Statistics

🧠

Analogy: Your brain does spell correction automatically — you read "restuarant" and understand "restaurant" without thinking. Search engines need to replicate this human ability, and edit distance is the mathematical foundation that makes it possible.

Why Not Just Use Fuzzy Matching?

Fuzzy matching in the index (like Elasticsearch's fuzziness: AUTO) handles some typos but is expensive — it expands the query to all terms within edit distance 1-2, blowing up the posting list lookups. Dedicated spell correction before retrieval is more efficient and gives you control over the correction strategy.

02 Edit Distance

The Levenshtein distance between two strings is the minimum number of single-character edits (insertions, deletions, substitutions) needed to transform one into the other.

$$d(i, j) = \begin{cases} j & \text{if } i = 0 \\ i & \text{if } j = 0 \\ d(i{-}1, j{-}1) & \text{if } a_i = b_j \\ 1 + \min\begin{cases} d(i{-}1, j) & \text{(delete)} \\ d(i, j{-}1) & \text{(insert)} \\ d(i{-}1, j{-}1) & \text{(replace)} \end{cases} & \text{otherwise} \end{cases}$$
Dynamic programming fills an (m+1)×(n+1) matrix bottom-up

03 Correction Candidates

Given a potentially misspelled word, we generate all dictionary words within edit distance 1 or 2. Edit distance 1 covers ~80% of typos; distance 2 covers ~95%.

For a 5-letter word, edit distance 1 generates ~280 candidates. Edit distance 2 generates ~78,000 — but only a tiny fraction will be real dictionary words.

Brute Force Approach

Generate all edit-1 and edit-2 variants, look each up in a hash set of dictionary words. Simple but expensive for edit distance 2 — generating 78K+ candidates per word.

Symmetric Delete (SymSpell)

Precompute all delete-1 and delete-2 forms of every dictionary word at index time. At query time, compute only delete forms of the input. If any overlap, the words are within edit distance 2. ~1000× faster than brute force.

Performance Trick

Rather than generating all candidates and checking the dictionary, production systems use symmetric delete distance: precompute all delete-1 forms of dictionary words. At query time, compute delete-1 of the query and look up. This reduces the search space dramatically — SymSpell processes 1M corrections/sec on a single CPU core.

04 Frequency-Based Ranking

Multiple dictionary words may be within the same edit distance. We break ties using word frequency — a common word is more likely to be the intended target than a rare one.

$$\text{correction}(w) = \arg\max_{c \in \text{candidates}} P(c) \cdot \mathbb{1}[\text{edit\_dist}(w, c) \leq 2]$$
P(c) is the prior probability of word c, estimated from corpus frequency

Noisy Channel Model

The probabilistic foundation for spell correction. We want: given a typo w, what was the intended word c?

By Bayes' theorem: $P(c|w) \propto P(w|c) \cdot P(c)$

  • P(c) — language model prior: how common is "wireless" vs "wisely"?
  • P(w|c) — error model: how likely is the typo "wireles" given intended "wireless"?

In practice, a simple frequency-based P(c) with edit distance as a proxy for P(w|c) works surprisingly well.

05 "Did You Mean?"

The decision of when to correct is as important as how. Getting this wrong frustrates users.

Auto-Correct

Silently fix the query and show results for the corrected version. Use when confidence is very high (>95%) and the original query returns zero/near-zero results.

Example: "iphoen" → automatically shows results for "iphone"

Suggest ("Did you mean?")

Show results for the original query but offer the correction as a link. Use when the original query has some results or when confidence is moderate.

Example: "python flak" → shows results, suggests "Did you mean: python flask?"

Google's Approach

Google auto-corrects and shows "Showing results for X. Search instead for Y" — correcting by default but giving an escape hatch. This works at Google scale because their correction model is extremely accurate. For smaller systems, "Did you mean?" is safer.

Context-Aware Correction

The word "there" might be a typo for "three" or "their" or "these" — edit distance alone can't decide. Modern systems use n-gram context: "over there" → keep as-is, "there apples" → suggest "three apples". This requires a language model trained on query logs.

06 Synonym Expansion

Even correctly spelled queries miss relevant documents when users and authors use different vocabulary. Synonym expansion bridges this vocabulary gap — the same concept expressed with different words.

The Vocabulary Problem

"high-performance vehicle", "speedy sedan"

Measuring Expansion Quality

Always A/B test synonym expansion. Track: (1) recall improvement — do users find more relevant docs? (2) precision impact — do irrelevant results creep in? (3) click-through rate — do users actually click the new results? Expansion that increases impressions but not clicks is adding noise.

07 Query Rewriting

Synonym expansion is one form of a broader technique: query rewriting. Modern systems rewrite queries in several ways to bridge the vocabulary gap between users and documents.

Synonym Sources

Curated Synonym Lists

Hand-built by domain experts. Highest precision, lowest recall. Used in regulated industries (medical, legal) where incorrect expansion has consequences.

Maintenance cost: High — must be updated as language evolves

Learned Embeddings

Extract synonyms from embedding space: find words with cosine similarity > 0.8 to each query term. High recall but noisy — "dog" and "cat" are similar in embedding space but not synonyms.

Maintenance cost: Low — retrain periodically

Risks of Over-Expansion

  • Query drift: "Java" (programming) → "coffee" (synonym)
  • Noise injection: Too many terms dilute relevance
  • Latency: More terms = more retrieval work
  • False matches: Expanded terms match irrelevant docs

Mitigation Strategies

  • Weighted expansion: Give original terms 2× weight
  • Context-aware: Use surrounding terms for disambiguation
  • Limit depth: Only expand to synonyms, not synonyms of synonyms
  • A/B test: Measure if expansion improves click-through rate
📚

Analogy: Query expansion is like a translator who doesn't just translate your words, but also includes culturally equivalent phrases. "I need a restroom" might also be understood as "WC", "loo", "lavatory", or "washroom" depending on the audience. But going too far — adding "toilet paper" or "plumbing" — dilutes the intent.

08 Key Takeaway

Bridge the Vocabulary Gap

Users are messy — they misspell, abbreviate, and use different words than your content authors. Spell correction and query expansion are your two defences. Use edit distance + frequency for correction, synonym maps + embeddings for expansion, and always measure the impact: a bad expansion (query drift) is worse than no expansion at all.
