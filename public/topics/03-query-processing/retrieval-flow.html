01 The Big Picture

A modern retrieval pipeline is a funnel: each stage narrows the candidate set while increasing the quality of scoring. The philosophy is simple — use cheap methods on many documents, expensive methods on few.

🏟️

Analogy: Hiring for a role. You start with 10,000 resumes (candidate retrieval), filter by hard requirements like degree and visa (filtering), do a quick phone screen (score fusion), then bring 5 finalists for a full-day onsite (re-ranking). Each stage costs more per candidate but runs on fewer.

Speed vs Quality

Early stages trade quality for speed (BM25 over millions in ~5ms). Later stages trade speed for quality (cross-encoder on 10 docs in ~200ms).

Recall Then Precision

Retrieval maximises recall — better to include an irrelevant doc than miss a relevant one. Re-ranking maximises precision on the survivors.

02 Stage 1: Query Preprocessing

Before the query reaches any index, we normalise it into canonical form. This step is critical for recall — a mismatch between query tokens and index tokens means zero matches.

Tokenization

Split on whitespace and punctuation, handling edge cases like contractions (can't → [can, t]), compound words, and special characters.

Simple whitespace split

"New York pizza" → ["New", "York", "pizza"]

Fast, but breaks on punctuation and compound words.

Language-aware tokenizer

"I can't believe it's $9.99!" → ["I", "ca", "n't", "believe", "it", "'s", "$", "9.99", "!"]

Handles contractions, currency, numbers correctly.

Lowercasing (Case Folding)

Convert all tokens to lowercase so "Python", "PYTHON", and "python" all match the same index terms. Exception: entity-sensitive contexts where WHO ≠ who.

When NOT to lowercase

Entity-sensitive searches (e.g., "WHO" the organization vs "who" the pronoun), product names (iPhone), acronyms (AIDS vs aids). Some systems use truecasing — a learned model that preserves meaningful capitalization.

Stemming / Lemmatization

Reduce words to root forms. Porter stemmer: running → run, better → better. Lemmatizer: better → good. Stemming is faster; lemmatization is more accurate.

ApproachMethodSpeedAccuracy
Porter StemmerRule-based suffix strippingVery fastModerate (over-stems sometimes)
Snowball StemmerImproved rule-basedFastGood
WordNet LemmatizerDictionary lookup + POS tagSlowerHigh
spaCy LemmatizerRule + exception tablesModerateHigh

Stop Word Removal

Remove ultra-common words (the, is, at, which) that add noise. Modern systems often skip this — BM25's IDF naturally down-weights them, and removing stop words can hurt phrase queries like "to be or not to be".

When To Remove Stop Words

For BM25-based systems, stop word removal is mostly unnecessary — IDF handles it. For TF-IDF with no IDF discount, stop words dominate and must be removed. For embedding models, keep all tokens — the model was trained on full sentences.

Key Insight

The same preprocessing must be applied at both index time and query time. If you stem documents but not queries (or vice versa), matching breaks silently. This is the #1 cause of "search returns nothing" bugs.

03 Stage 2: Candidate Retrieval

The goal here is high recall at low cost. We cast a wide net using two complementary strategies that cover each other's blind spots.

BM25 (Lexical)

Looks up query terms in an inverted index. Extremely fast (<10ms over millions). Excels at exact keyword matches but misses synonyms and semantic meaning.

$$\text{BM25}(q, d) = \sum_{t \in q} \text{IDF}(t) \cdot \frac{f(t,d) \cdot (k_1+1)}{f(t,d) + k_1 \cdot (1 - b + b \cdot \frac{|d|}{\text{avgdl}})}$$

Vector Search (Semantic)

Encode query into an embedding vector, then find nearest neighbours in vector space. Captures semantic similarity — "automobile" matches "car". Typically uses ANN indexes (HNSW, IVF).

$$\text{sim}(q, d) = \frac{\vec{q} \cdot \vec{d}}{||\vec{q}|| \cdot ||\vec{d}||}$$

Why Both?

BM25 is unbeatable for exact matches ("error code XJ-4402") while vector search handles semantic intent ("how to fix a broken screen"). Together they cover each other's blind spots. In practice, hybrid retrieval (BM25 + vector) outperforms either alone by 5-15% on standard benchmarks.

🔍

Analogy: BM25 is like searching for a book by exact title in a library catalog. Vector search is like asking a librarian "I need something about managing difficult team dynamics" — they understand the concept even though your words don't match any title exactly.

04 Stage 3: Score Fusion

We now have two candidate lists with different score distributions. Fusion combines them into one ranked list.

Reciprocal Rank Fusion (RRF)

RRF ignores raw scores entirely and uses only rank positions. This elegantly handles the score distribution mismatch.

$$\text{RRF}(d) = \sum_{r \in \text{rankers}} \frac{1}{k + \text{rank}_r(d)}$$
k = 60 is the standard constant that prevents high-ranked docs from dominating too aggressively

Weighted Combination

Alternatively, normalise scores to [0,1] and combine: $\text{score}(d) = \alpha \cdot \text{BM25}_{\text{norm}}(d) + (1-\alpha) \cdot \text{vec}_{\text{norm}}(d)$. Requires careful normalisation but lets you tune the balance.

RRF Pros

  • No normalisation needed
  • Robust to outlier scores
  • Parameter-free (k=60 works everywhere)

Weighted Combo Pros

  • More expressive — tune α per domain
  • Preserves score magnitude information
  • Can be learned end-to-end

RRF Worked Example

Given BM25 ranks: [D1, D3, D5, D2] and vector ranks: [D3, D1, D4, D2] with k=60:

DocumentBM25 RankVector RankRRF Score
D1121/61 + 1/62 = 0.0325
D3211/62 + 1/61 = 0.0325
D2441/64 + 1/64 = 0.0313
D53—1/63 + 1/160 = 0.0221
D4—31/160 + 1/63 = 0.0221

D1 and D3 tie because they both appear at rank 1 and 2, just swapped. D2 ranks high because it appears in both lists. D5 and D4 rank lower because they each appear in only one.

Unranked Documents

When a document appears in only one retrieval path, assign a large default rank (e.g., 100) for the missing path. This ensures documents found by both methods are always scored higher than those found by only one — a natural way to reward agreement between rankers.

05 Stage 4: Filtering

Hard constraints that documents must satisfy regardless of relevance score. A document with a perfect BM25 score is useless if it's in the wrong language or out of stock.

Pre-filter vs Post-filter

Pre-filtering narrows the search space before retrieval (faster, but can hurt recall if the filter is too aggressive). Post-filtering retrieves first, then removes non-matching docs (preserves recall but wastes compute on docs that get discarded).

06 Stage 5: Re-Ranking

The final, most expensive stage. A powerful model (cross-encoder, LLM) scores each surviving candidate against the query with full attention.

Cross-Encoder

Concatenates query + document and runs through a BERT-style transformer. Scores all token interactions (unlike bi-encoder which compresses each independently). 100-1000× slower than bi-encoder but significantly more accurate.

Input: [CLS] query [SEP] document [SEP]

Output: Single relevance score from classification head

Bi-Encoder vs Cross-Encoder

A bi-encoder encodes query and document independently — fast (precompute doc embeddings) but misses fine-grained interactions. A cross-encoder sees both together — slow but captures nuanced relevance.

Bi-encoder: encode(q) · encode(d)

Cross-encoder: score(q ⊕ d)

Why Not Use It Everywhere?

A cross-encoder on 1M documents at 10ms each = 10,000 seconds. On 10 documents = 100ms. This is why the funnel exists — we use cheap retrieval to reduce the candidate set to a manageable size, then apply expensive re-ranking.

LLM Re-Ranking

A growing trend is using LLMs to re-rank by presenting candidates and asking "which is most relevant?" This is incredibly expensive but yields the best results. Practical for <5 candidates in high-value scenarios (e.g., RAG for enterprise assistants).

08 Latency Budget

Where does the time go? Adjust candidate counts to see how each stage's latency changes and where the budget is spent. Most production systems target a total latency of 200–500ms for search.

Latency Budget Explorer

Latency Budget Rules of Thumb

Autocomplete (50ms)

Must feel instant. No re-ranking, no vector search. Prefix trie + top-K by popularity. Every millisecond matters at keystroke speed.

Full Search (200-500ms)

Users tolerate 200-500ms for a full page of results. Budget: ~20ms retrieval, ~5ms fusion, ~5ms filtering, ~150-400ms re-ranking. Parallelise BM25 and vector retrieval.

RAG Pipeline (1-3s)

Retrieval feeds into an LLM, so users are already expecting a few seconds. You can afford expensive re-ranking (cross-encoder on 50+ docs) and even LLM-based re-ranking.

Batch/Analytics (minutes)

Offline evaluation, data labelling, corpus reindexing. No latency constraint. Use the most accurate models available. Re-rank thousands of candidates if needed.

09 Design Trade-offs

Every stage balances competing goals. Understanding these trade-offs is the difference between a search system that works and one that delights users.

The Fundamental Tensions

Recall vs Precision

Early stages maximise recall (include everything possibly relevant). Later stages maximise precision (show only the best). These are inherently at odds — improving one typically hurts the other.

Latency vs Quality

Better scoring models (cross-encoders, LLMs) produce higher quality rankings but cost more time. The pipeline exists to apply expensive methods only where they matter most.

Freshness vs Relevance

New documents haven't been seen by enough users to have good engagement signals. Over-indexing on freshness hurts relevance; ignoring it means stale results. Balance with time-decay boosting.

Simplicity vs Accuracy

Each additional pipeline stage adds complexity, more failure modes, and harder debugging. A simpler 3-stage pipeline that's well-tuned often beats a complex 7-stage one that's poorly maintained.

The 80/20 Rule

Re-ranking typically uses 80% of the latency budget but processes only 1% of the documents. If your total latency budget is 300ms, plan to spend ~200ms on re-ranking and divide the remaining 100ms among all other stages.

10 Key Takeaway

The Funnel Principle

Modern retrieval is a multi-stage funnel where each stage trades off speed for quality. Start broad and cheap (BM25 over millions), progressively narrow and score more expensively (cross-encoder on a handful), and apply hard constraints at the right stage. The key design decision is where to draw each boundary — too aggressive early filtering kills recall, too much re-ranking blows the latency budget.

Pipeline Design Checklist

DecisionConsiderationDefault Choice
How many candidates to retrieve? More = better recall, higher latency 100-1000 for BM25, 50-200 for vector
BM25, vector, or both? Both covers more query types Hybrid with RRF fusion
Pre-filter or post-filter? Hard constraints pre, soft post Hybrid: security pre, availability post
How many to re-rank? More = better precision, higher cost 10-50 with cross-encoder
Which re-ranker? Speed vs quality trade-off MiniLM cross-encoder for most; Cohere/Jina API for production
Final top-K? User attention drops fast 5-10 results per page

Common Pipeline Configurations

E-Commerce Search

Pre-filter: category, availability, region

Retrieve: BM25 (product titles) + vector (descriptions)

Fuse: Weighted combo (α=0.6 for BM25)

Re-rank: Cross-encoder + business rules (margin, sponsored)

Budget: 200ms total

RAG / Knowledge Base

Pre-filter: document access permissions

Retrieve: Vector primary, BM25 for exact terms

Fuse: RRF (score distributions vary widely)

Re-rank: Cross-encoder on top 20, then LLM on top 5

Budget: 1-2s (LLM generation dominates anyway)

Web Search (Google-scale)

Pre-filter: language, SafeSearch, region

Retrieve: Inverted index (billions of pages)

Fuse: Multi-signal combination (PageRank, freshness, etc.)

Re-rank: Deep neural ranker on top 100

Budget: 500ms including rendering

Semantic Code Search

Pre-filter: repository, language, file type

Retrieve: Vector (code embeddings) + BM25 (identifier names)

Fuse: RRF with repo-level boost

Re-rank: Code-specialized cross-encoder

Budget: 300ms for interactive, unlimited for batch

🎯

Remember: You can always add more stages to a pipeline, but you can never recover documents that were dropped too early. When in doubt, retrieve more candidates and let re-ranking sort them out.
