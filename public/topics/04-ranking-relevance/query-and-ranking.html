01 Query Preprocessing

Before a search query ever touches an index, it goes through a preprocessing pipeline that normalizes, expands, and cleans the raw user input. Each step dramatically affects recall and precision.

🔧

Analogy: Imagine you're a translator. Someone speaks to you with an accent, slang, and grammatical errors. Before translating, you mentally clean up the sentence, guess the intended words, and expand abbreviations. Query preprocessing does the same thing - it turns messy human input into a clean, structured representation that the search engine can work with.

Step 1: Tokenization

Split the raw query string into individual tokens. This is trickier than just splitting on spaces.

Simple whitespace split

"New York pizza" → ["New", "York", "pizza"]

Fast, but breaks on punctuation and compound words.

Language-aware tokenizer

"I can't believe it's $9.99!" → ["I", "ca", "n't", "believe", "it", "'s", "$", "9.99", "!"]

Handles contractions, currency, numbers correctly.

Step 2: Lowercasing (Case Folding)

Convert all tokens to lowercase so "Python", "PYTHON", and "python" all match the same index terms.

When NOT to lowercase:

Entity-sensitive searches (e.g., "WHO" the organization vs "who" the pronoun), product names (iPhone), acronyms (AIDS vs aids). Some systems use truecasing - a learned model that preserves meaningful capitalization.

Step 3: Stemming vs Lemmatization

Reduce words to their root form so morphological variants match each other.

Aspect Stemming Lemmatization
Method Rule-based suffix stripping Dictionary + morphological analysis
Speed Very fast Slower (needs POS tagging)
"running" → "run" → "run" (verb)
"better" → "better" (fails) → "good" (adjective)
"studies" → "studi" (ugly but works) → "study"
"university" → "univers" → "university"
Algorithm Porter, Snowball WordNet, spaCy
Best for High recall, speed-critical Precision, user-facing suggestions

Step 4: Stop Word Removal

Remove extremely common words that carry little search value: "the", "is", "at", "of", "and", etc.

When to remove

General web search, document retrieval - stop words inflate index size and rarely improve relevance.

When NOT to remove

"To be or not to be" - the query IS stop words. Phrase search ("the who"), song titles, exact-match requirements. Modern systems with good IDF weighting often skip this step entirely.

Step 5: Spell Correction & "Did You Mean?"

Users misspell queries constantly. A spell corrector uses edit distance (Levenshtein), n-gram overlap, and language models to suggest corrections.

$$\text{EditDistance}(\text{"recieve"}, \text{"receive"}) = 1 \quad\text{(swap i↔e)}$$
Levenshtein distance: minimum insertions, deletions, substitutions to transform one string into another
How Google "Did You Mean?" works (simplified):

1. Check if the query has low result count or low click-through. 2. Generate candidates within edit distance ≤ 2. 3. Score candidates by: (a) query log frequency - what do other users actually type? (b) language model probability. 4. If the corrected query scores significantly higher → suggest it.

Step 6: Query Expansion (Synonyms)

Broaden the query by adding synonyms or related terms. "car" might expand to include "automobile", "vehicle".

Method How it works Example
Thesaurus-based Static synonym dictionary "laptop" → +["notebook", "computer"]
Embedding-based Nearest neighbors in vector space "AI" → +["machine learning", "deep learning"]
Query logs Other users who searched X also searched Y "NYC" → +["New York City"]
Pseudo-relevance feedback Top-k docs → extract frequent terms → add to query Auto-expands based on initial results

02 Query to Embeddings

For vector/semantic search, the preprocessed query must be converted into a dense vector (embedding) - a point in high-dimensional space where meaning is encoded as geometry.

Raw query string
→
Tokenize (model-specific)
→
Encoder model
→
768-d vector

Same model at index time & query time

The embedding model used to encode documents at indexing time must be the same model used to encode queries at search time. If you index with all-MiniLM-L6-v2 but query with text-embedding-3-small, the vectors live in different spaces and cosine similarity is meaningless.

Why this matters:

Each model learns its own latent space. Dimension 42 in Model A might encode "formality" while dimension 42 in Model B encodes "topic:science". There's no universal coordinate system across models.

Symmetric vs Asymmetric Models

Type Design Best For Example Models
Symmetric Query and document are similar length/style. Same encoder for both. Semantic similarity, duplicate detection, clustering all-MiniLM-L6-v2, gte-base
Asymmetric Short query vs long document. May use different encoding strategies. Search, Q&A retrieval, RAG msmarco-distilbert, e5-large (with "query:" prefix)
How asymmetric models work:

Models like E5 and BGE use instruction prefixes: prepend "query: " to queries and "passage: " to documents. This tells the model to project the short query into the same region of space as relevant long documents. Without these prefixes, performance drops significantly.

Query Embedding vs Document Embedding

Query embedding

Generated at search time - latency matters. Typically 5-50ms for a single query on GPU. The query is usually short (5-15 tokens), so encoding is fast.

Document embedding

Generated at index time - latency is less critical (batch processing). Documents are longer, may need chunking. Stored in a vector index (HNSW, IVF) for fast retrieval.

Latency Breakdown

Pro tip:

A common question: "Why not use a giant model for embeddings?" Answer: Because query embedding happens at search time, and every millisecond counts. A model that takes 200ms per query adds 200ms to every single search. That's why production systems use lightweight models (6-12 layers) and quantize them to INT8. The sweet spot is a model small enough for real-time inference but large enough to capture semantic nuance.

$$\text{sim}(\vec{q},\, \vec{d}) = \cos(\vec{q},\, \vec{d}) = \frac{\vec{q} \cdot \vec{d}}{\|\vec{q}\| \;\|\vec{d}\|}$$
Cosine similarity - the standard metric for comparing query and document embeddings

Stage-by-stage breakdown

Stage 1–2: Query understanding

The raw query is preprocessed (Section 1) and converted to both: (a) a set of tokens for BM25 lookup, and (b) a dense vector embedding for ANN search. This dual representation is the foundation of hybrid search.

Stage 3: Dual retrieval (candidate generation)

Two parallel retrieval paths run simultaneously:

BM25 path

Inverted index lookup. Returns top-k documents ranked by keyword relevance. Latency: ~1-5ms. Great for exact matches and rare terms.

Vector path

ANN search (HNSW/IVF). Returns top-k documents by semantic similarity. Latency: ~5-20ms. Great for conceptual matches.

Stage 4: Merge

The two candidate sets are combined into a single list. Common strategies: Reciprocal Rank Fusion (RRF) or linear interpolation. The merge step typically increases the candidate pool to ~100-1000 documents. (More on this in Section 7.)

Stage 5: Re-ranking

A heavyweight model (cross-encoder) re-scores the merged candidates. Unlike bi-encoders (which encode query and doc separately), a cross-encoder processes the query-document pair together, capturing fine-grained interactions. This is 100-1000x slower per document, so it only processes the top ~100 candidates. This is the most expensive but most impactful stage.

Stage 6: Filtering & business logic

Apply hard constraints: in-stock only, price range, permissions/ACL, geo-proximity, language, content freshness. These may also happen pre-retrieval. (More on this in Section 4.)

Stage 7: Return results

Final top-k results are returned with metadata, snippets, highlights, and debug scores. The full pipeline typically completes in 50-200ms for a well-optimized system.

04 Filtering

Filters enforce hard constraints that override relevance scores. A perfectly relevant result that's out of stock or outside the user's price range is useless.

Pre-filtering vs Post-filtering

Pre-filtering

Apply filters before similarity search. The index only searches over documents that match the filters.

✅ Pro Faster - smaller search space
✅ Pro Exact top-k from filtered set
❌ Con Filter+index interaction is complex
❌ Con May degrade ANN recall
Post-filtering

Retrieve top-k candidates first, then remove those that don't match filters.

✅ Pro Simple to implement
✅ Pro No index complexity
❌ Con May return fewer than k results
❌ Con Wastes compute on filtered-out docs
The "empty results" problem with post-filtering:

If you retrieve top-100 by similarity and then filter by "price < $20", you might end up with only 3 results - or zero. The fix: over-fetch (retrieve top-500, then filter to top-10) or use pre-filtering for highly selective filters.

Filter types

Type Operator Example
Range >=, <=, BETWEEN price BETWEEN 10 AND 50
Exact match =, IN category = "Electronics"
Boolean = in_stock = true
Geo WITHIN radius location WITHIN 10km of user
Date range >=, <= published_date >= "2024-01-01"
Array contains CONTAINS tags CONTAINS "wireless"

How filters interact with scoring

Filters are binary - a document either passes or doesn't. They do NOT affect the relevance score. However, removing documents changes the relative ranking of what remains. Some systems support soft filters (boost matching documents without removing non-matching ones).

05 Multi-Stage Ranking Pipeline

Real-world search systems don't score every document with a single model. They use a funnel - progressively more expensive models on progressively fewer candidates.

🏗️

Analogy: Hiring. You don't give every applicant a 5-hour deep evaluation. Stage 1: resume screening (fast, low cost) narrows 10,000 → 500. Stage 2: phone screen narrows 500 → 50. Stage 3: final evaluation narrows 50 → 5. Each stage is more expensive but more accurate, applied to fewer candidates.

The three layers

L0
Candidate Generation
Millions → Thousands
→
L1
Lightweight Scoring
Thousands → Hundreds
→
L2
Heavy Re-Ranking
Hundreds → Top-k

L0 - Candidate Generation

Goal: Rapidly narrow the entire corpus to a manageable set.

Input Entire index (millions–billions of documents)
Output ~1,000–10,000 candidates
Methods Inverted index (BM25), ANN search (HNSW), hash-based retrieval
Latency 1–20ms
Quality High recall, moderate precision - "don't miss relevant docs"

L1 - Lightweight Scoring

Goal: Score candidates with a fast model that uses more features than L0.

Input ~1,000–10,000 candidates
Output ~100–500 candidates
Methods Bi-encoder similarity, lightweight LTR (XGBoost), feature-based scoring
Latency 5–30ms
Features BM25 score, cosine similarity, document popularity, freshness, field match count

L2 - Heavy Re-Ranking

Goal: Maximize precision on the final result page with the most powerful model.

Input ~100–500 candidates
Output ~10–20 final results
Methods Cross-encoder (BERT-based), GPT re-ranker, Cohere Rerank, ColBERT
Latency 20–200ms
Why it's better Cross-attention between query and doc captures token-level interactions that bi-encoders miss

Why multi-stage?

A cross-encoder takes ~20ms per document. Scoring 1M documents = 5.5 hours. Scoring 100 candidates = 2 seconds. The funnel makes the expensive model tractable.

$$\text{Total latency} \approx \underbrace{\frac{|C|}{T_{L0}}}_{\text{L0}} + \underbrace{|R_1| \cdot t_{L1}}_{\text{L1}} + \underbrace{|R_2| \cdot t_{L2}}_{\text{L2}}$$
\(|C|\) = corpus size, \(|R_i|\) = candidates at stage \(i\), \(t_{Li}\) = per-doc latency at stage \(i\)

06 BM25 Scoring (Quick Recap)

BM25 is the backbone of keyword-based retrieval. Here's the formula - for the full deep dive, see the BM25 Masterclass →

$$\color{#6c63ff}{\text{BM25}(q,\, d)} \;=\; \sum_{t \,\in\, q} \;\color{#00c9a7}{\text{IDF}(t)} \;\cdot\; \frac{\color{#6c63ff}{f(t,d)} \;\cdot\; (\color{#ffd93d}{k_1} + 1)}{\color{#6c63ff}{f(t,d)} \;+\; \color{#ffd93d}{k_1} \;\cdot\; \left(1 - \color{#ff6b6b}{b} + \color{#ff6b6b}{b} \;\cdot\; \dfrac{|d|}{\text{avgdl}}\right)}$$
Sum over query terms: IDF weight × saturating TF with length normalization

The three key signals

Term Frequency

How often the query term appears in the document. Saturates - diminishing returns after a point. Controlled by \(k_1\).

Document Frequency

How many documents contain this term (IDF). Rare terms score higher. "eigenvalue" >> "the".

Document Length

Longer docs get penalized (they naturally contain more term matches). Controlled by \(b\). Normalized against average doc length.

Defaults that work 90% of the time:

\(k_1 = 1.2\), \(b = 0.75\). These are the Lucene/Elasticsearch defaults. Only tune if you have relevance judgments and can measure NDCG/MAP.

07 Hybrid Scoring

Neither BM25 nor vector search alone is optimal. Hybrid scoring combines both to get the best of exact keyword matching AND semantic understanding.

Why hybrid wins

BM25 alone misses...

"affordable housing" won't match a doc about "low-cost apartments" - different words, same meaning. BM25 requires exact term overlap.

Vector alone misses...

"error code 0x80070005" - a very specific, rare string. Embeddings compress this into a generic "error" neighborhood, losing the exact match. BM25 finds it instantly.

Method 1: Reciprocal Rank Fusion (RRF)

RRF combines ranked lists without needing to normalize scores. It only cares about rank position:

$$\text{RRF}(d) = \sum_{r \,\in\, \text{rankers}} \frac{1}{\color{#ffd93d}{k} + \text{rank}_r(d)}$$
\(\color{#ffd93d}{k}\) = smoothing constant (typically 60). \(\text{rank}_r(d)\) = position of doc \(d\) in ranker \(r\)'s list (1-indexed)
RRF example:

Doc X is rank 1 in BM25, rank 5 in vector → RRF = 1/(60+1) + 1/(60+5) = 0.01639 + 0.01538 = 0.03177

Doc Y is rank 3 in BM25, rank 2 in vector → RRF = 1/(60+3) + 1/(60+2) = 0.01587 + 0.01613 = 0.03200

Doc Y wins - it's consistently ranked well in both, even though Doc X was #1 in BM25.

Method 2: Linear Combination (Alpha Weighting)

$$\text{HybridScore}(d) = \color{#6c63ff}{\alpha} \cdot \text{BM25}_{\text{norm}}(d) + \color{#00c9a7}{(1-\alpha)} \cdot \text{Vector}_{\text{norm}}(d)$$
\(\color{#6c63ff}{\alpha}\) controls the blend - 1.0 = pure keyword, 0.0 = pure semantic
Score normalization is critical:

BM25 scores might range from 0-15, while cosine similarity is 0-1. Without normalization, BM25 dominates. Common approaches: min-max normalization per query, z-score normalization, or rank-based normalization.

How to tune alpha

Alpha Bias toward Best when
\(\alpha = 0.7\) Heavy keyword Technical docs, error codes, product SKUs
\(\alpha = 0.5\) Balanced General search - good default
\(\alpha = 0.3\) Heavy semantic Natural language questions, conversational queries

08 Relevance Tuning

Relevance tuning is the art of adjusting scoring parameters to improve result quality. It's how you move from "technically correct" to "users love this search."

Field Boosting

Not all fields are created equal. A match in the title is far more indicative of relevance than a match buried in the body.

$$\text{Score}(q, d) = \color{#6c63ff}{w_{\text{title}}} \cdot \text{BM25}(q, d_{\text{title}}) + \color{#00c9a7}{w_{\text{body}}} \cdot \text{BM25}(q, d_{\text{body}}) + \color{#ffd93d}{w_{\text{tags}}} \cdot \text{BM25}(q, d_{\text{tags}})$$
Weighted sum of per-field BM25 scores
Field Typical Boost Why
Title 3.0–5.0× Titles are concise summaries - a match here is strong signal
Headers (H1-H3) 2.0–3.0× Section headers indicate topic structure
Body 1.0× (baseline) Most content lives here - but matches are less targeted
URL/slug 1.5–2.0× URLs often contain key terms
Tags/categories 2.0–4.0× Curated metadata - high signal
Comments 0.3–0.5× User-generated, noisy - low signal

Function Scoring

Beyond text relevance, inject business signals directly into the score:

Recency boost
$$\text{boost} = e^{-\lambda \cdot \text{age\_days}}$$

Exponential decay - recent docs score higher. \(\lambda\) controls decay speed. News sites use aggressive decay; encyclopedias don't.

Popularity boost
$$\text{boost} = \log_2(1 + \text{views})$$

Log-scaled to prevent viral content from dominating everything. 1000 views = 10× boost, not 1000×.

Query-time Boosts

Applied per-query rather than globally. Examples:

User intent: If query contains "buy" or "price", boost product pages and suppress blog posts.

User context: If user is on mobile, boost results with mobile-friendly pages.

Personalization: Boost categories the user has clicked on before.

A/B Testing Relevance

Never ship relevance changes without measurement. The standard approach:

Define metrics (NDCG, CTR, dwell time)
→
Randomize users into A/B
→
Run experiment 1-2 weeks
→
Statistical significance test
→
Ship or rollback

09 Ranking Signals Deep Dive

A modern ranking function combines many signals into a final score. Understanding each signal type is critical for building and debugging search systems.

Signal Categories

1. Keyword Match Signals

Signal Description Weight
BM25 score Classic term frequency × IDF with saturation High
Exact phrase match Query terms appear adjacent and in order Very High
Field match Which field(s) matched (title vs body) High
Term proximity How close query terms are to each other in the doc Medium
Query coverage Fraction of query terms found in doc Medium

2. Semantic Similarity Signals

Signal Description Weight
Cosine similarity Query embedding · document embedding High
Cross-encoder score Joint query-doc scoring (attention over both) Very High
Passage-level similarity Best-matching chunk within a long document High
Multi-vector similarity ColBERT-style token-level matching High

3. Popularity & Engagement Signals

Signal Description Watch out for
Click-through rate % of impressions that get clicked Position bias (top results always get more clicks)
Dwell time How long users stay on the result Can conflate "engaging" with "confusing"
Page views Total views over time Favors old content
Social shares External engagement signal Gameable, noisy
Bounce rate Users who immediately return to search Inverse signal - high bounce = bad

4. Freshness Signals

Signal Description Applicability
Publish date When the content was first created News, blogs, social media
Last modified Most recent edit timestamp Wiki, documentation
Crawl freshness When the search engine last indexed it Web search
Content velocity How often the page changes Dynamic vs static pages

5. Personalization Signals

Signal Description Privacy impact
User history Past clicks, searches, purchases High - requires consent
User location Geo-bias results (local restaurants, stores) Medium
User segment Role-based boosting (developer vs manager) Low - aggregate
Language preference Prefer results in user's language Low
Device context Mobile vs desktop - different result types Low

How signals combine into a final score

Modern systems use Learning to Rank (LTR) - a machine learning model trained on human relevance judgments:

$$\text{FinalScore}(q, d) = F\bigl(\underbrace{s_1, s_2, \ldots, s_n}_{\text{all signals as features}}\bigr)$$
\(F\) is typically a gradient-boosted tree (LambdaMART, XGBoost) or a neural model
LTR approach Training Models
Pointwise Predict absolute relevance score per doc Linear regression, neural net
Pairwise Learn which doc in a pair is more relevant RankNet, LambdaRank
Listwise Optimize the entire ranking list (NDCG) LambdaMART, ListNet
Key evaluation metrics for ranking:

NDCG@k (Normalized Discounted Cumulative Gain)

Measures ranking quality. Penalizes relevant docs ranked low. Industry standard.

MAP (Mean Average Precision)

Average precision across all relevant documents. Good for binary relevance.

MRR (Mean Reciprocal Rank)

1/rank of the first relevant result. Good for navigational queries.

Recall@k

% of relevant docs in top-k. Critical for candidate generation (L0) evaluation.

Pro tip - common questions:

"How would you debug a bad ranking?" → Look at the signals for the miranked docs. Check BM25 scores, embedding similarity, freshness. Often one signal is dominating or miscalibrated.

"How do you handle the cold start problem?" → New documents have no engagement signals. Solution: rely heavily on text-match and semantic signals initially, then blend in engagement as data accumulates.

"How do you prevent popularity bias?" → Log-scale popularity signals, use exploration (show some non-popular results to gather data), or apply a "newness boost" that decays over time.
