01 Learning to Rank (LTR)

Hand-tuned ranking formulas like BM25 work well for generic search, but break at scale. When you have hundreds of ranking signals - freshness, popularity, click-through rate, user location, title match quality - no human can manually tune the weights. Learning to Rank uses machine learning to learn the optimal ranking function from labeled data.

🎯

Analogy: Imagine you're a judge at a cooking competition. You could manually score each dish on 50 criteria and add up the points (hand-tuned). Or you could train an apprentice by showing them thousands of past competitions with winning dishes - they'd learn the subtle patterns of what makes a winner, including interactions between criteria that you'd never think to code by hand. That's LTR.

Why hand-tuned ranking fails

Too many signals

Modern search has 100+ features: BM25, click rates, freshness, authority, field matches, embeddings. Manually weighting them all is impossible.

Feature interactions

The interplay between features matters. A fresh doc from a trusted source should rank higher than a stale doc from a trusted source - but that's a non-linear interaction you can't capture with linear weights.

The three LTR approaches

Aspect Pointwise Pairwise Listwise
Core idea Predict the absolute relevance score of each document independently Given two documents, predict which one should rank higher Optimize the entire ranked list at once using an IR metric
Loss function Regression (MSE) or classification (cross-entropy) Pairwise cross-entropy - penalize when a less relevant doc is ranked above a more relevant one Directly optimizes NDCG, MAP, or other list-level metrics (often via approximation)
Examples Linear regression, random forest classifier RankNet, RankSVM, RankBoost LambdaMART, LambdaRank, ListNet, AdaRank
Pros Simple to implement, easy to debug Captures relative preference well; often better than pointwise Best performance - directly optimizes what we care about
Cons Ignores relative ordering; treats each doc independently Computationally expensive (O(n²) pairs); doesn't optimize list-level metric More complex; metric approximation can be tricky
Industry use Quick baselines, A/B test feature screening Moderate - used when labeled data has pairwise preferences Industry standard for production search - used by Google, Bing, Airbnb

Key loss functions

$$\text{RankNet Loss} \;=\; -\sum_{(i,j):\, y_i > y_j} \left[ \log \sigma\!\left( \color{#6c63ff}{s_i} - \color{#ff6b6b}{s_j} \right) \right]$$
Penalizes when a more relevant doc \(i\) scores lower than a less relevant doc \(j\). \(\sigma\) = sigmoid.
$$\text{LambdaMART: } \;\lambda_{ij} \;=\; \frac{-\sigma}{1 + e^{\sigma(s_i - s_j)}} \;\cdot\; \left| \Delta \color{#00c9a7}{\text{NDCG}} \right|$$
Gradient is scaled by the NDCG change from swapping docs \(i\) and \(j\) - concentrates learning on swaps that matter most.

Features used in LTR

Query features

Query length, number of terms, query popularity, is navigational?, query category, language

Document features

PageRank, freshness, doc length, spam score, domain authority, content quality score, click count

Query–Document features

BM25 score, TF-IDF, title match, exact phrase match, embedding similarity, URL match, anchor text match

Training data sources

Human judgments

Trained raters assign relevance labels (0–4) to query-document pairs. High quality but expensive - typically $0.10–$0.50 per judgment. The TREC and LETOR datasets use this approach.

Click logs

Implicit feedback from user behavior: clicks, dwell time, add-to-cart, purchase. Cheap and abundant but noisy and biased (see Section 2).

Pro tip:

When asked "how would you improve search ranking?" - LTR is almost always the right answer for production systems. The standard stack: BM25 for retrieval → LambdaMART for re-ranking. Start with features you already have (BM25 score, document metadata), train on click logs, and iterate.

02 Click-Based Feedback Loops

Users never fill out relevance surveys - but they click, scroll, dwell, and bounce. This implicit feedback is the lifeblood of modern search ranking. Understanding its biases is critical.

🖱️

Analogy: Imagine you run a bookstore and rearrange the shelves every week. Books at eye level get picked up more - but is that because they're better, or just because they're easier to see? Click data in search has the same problem: position bias means top results get clicked regardless of quality.

Click-through rate as a signal

$$\color{#6c63ff}{\text{CTR}(d, q)} \;=\; \frac{\text{clicks on } d \text{ for query } q}{\text{impressions of } d \text{ for query } q}$$
A document clicked 30 times out of 100 impressions has CTR = 0.30

Raw CTR is misleading because of position bias. A result at position 1 might get 40% CTR, while the exact same result at position 5 would get 8% CTR.

The position bias problem

Position Typical CTR Examination Probability
1 30–40% ~100%
2 15–20% ~80%
3 8–12% ~60%
5 3–5% ~35%
10 1–2% ~10%

Click models

Examination Hypothesis

A click requires two independent events: the user examines the result (position-dependent) AND finds it relevant (quality-dependent).

$$P(\text{click}) = P(\text{examine} \mid \text{pos}) \cdot P(\text{relevant} \mid \text{doc, query})$$
Cascade Model

Users scan results top-to-bottom, stopping when they find a satisfactory result. Each result is examined only if all previous results were examined but not clicked.

$$P(\text{examine}_k) = \prod_{i=1}^{k-1} (1 - P(\text{click}_i))$$

Debiasing clicks

Inverse Propensity Weighting (IPW)

Weight each click by the inverse of the probability that the result was examined at its position. A click at position 10 is weighted much higher than one at position 1, because the user had to actively look for it.

$$\text{debiased\_relevance}(d) = \frac{\text{click}(d)}{P(\text{examine} \mid \text{position}(d))}$$

Converting clicks to training labels

Strategy How it works Quality
Click = relevant Any click means relevant Low - noisy, position-biased
Skip-above If user clicks result at position 5 but skipped 3 and 4, then 5 > 3 and 5 > 4 Medium - pairwise preferences
Click + dwell Only count as relevant if dwell time > 30s Medium-High - filters accidental clicks
Last click The last clicked result in a session is the most relevant (user was "satisfied") Medium - works for navigational queries
IPW-debiased Weight by inverse propensity score High - handles position bias

The feedback loop

↓ produces
More Relevant Results Shown
↓ generates
More User Clicks & Engagement

Dangers of the feedback loop

Popularity bias (rich-get-richer)

Already-popular results get more clicks → get trained as "more relevant" → get ranked higher → get even more clicks. New content never gets a chance. This is why editorial boosts and exploration/exploitation strategies are critical.

Filter bubbles

If users only click one type of result, the model learns to only show that type. Over time, the search system narrows what users see, reducing serendipity and diversity. Mitigation: inject diverse results at random positions and measure engagement.

Pro tip:

Expect the question: "How would you use click data for ranking?" The key answer: never use raw clicks directly. Always debias for position, use pairwise preferences (skip-above), combine with dwell time, and add exploration to avoid feedback loops.

03 Personalization

The same query - "python" - means completely different things to a software engineer and a zoologist. Personalization adapts search results to the individual user based on their profile, history, and context.

👤

Analogy: A good barista remembers your usual order. When you say "the usual," they know exactly what you mean. Personalized search works the same way - it remembers your preferences and adapts results accordingly. But if the barista only ever gives you the same thing, you'll never discover a new drink you might love.

Personalization approaches

Approach Signal Example Cold start?
User profile Past searches, clicks, purchases User who always clicks Python programming results → boost programming results for "python" Fails for new users
Collaborative filtering Similar users' behavior "Users like you also clicked X" - borrow preferences from similar users Works if similar users exist
Contextual Location, device, time of day "Pizza" at noon on mobile → nearby restaurants. "Pizza" at 10pm on desktop → recipes Works immediately
Session-based Current session behavior User searched "flights to Tokyo" then "Tokyo" → personalize for travel, not the city's Wikipedia page Works within session

The personalization spectrum

$$\color{#6c63ff}{\text{score}(q, d, u)} \;=\; (1 - \color{#ffd93d}{\alpha}) \cdot \text{relevance}(q, d) \;+\; \color{#ffd93d}{\alpha} \cdot \text{personal}(q, d, u)$$
\(\alpha = 0\): no personalization. \(\alpha = 1\): fully personalized. Typical: \(\alpha \approx 0.2\text{–}0.4\).

When personalization helps vs hurts

Helps

Ambiguous queries ("apple," "python," "jaguar"), discovery queries, content feeds, e-commerce product search, news ranking

Hurts

Navigational queries (user wants a specific page), fact-finding queries (one correct answer), fairness-sensitive queries (jobs, loans, healthcare)

Key challenges

Cold start problem

New users have no history. Solutions: use contextual signals (location, device), fall back to popularity-based ranking, ask for explicit preferences (onboarding).

Filter bubble concern

Over-personalization traps users in an echo chamber. Solutions: diversity injection, exploration/exploitation tradeoffs, occasional "serendipity" results.

Privacy considerations

Personalization requires user data. GDPR, CCPA, and similar regulations require explicit consent for data collection. Many systems offer "incognito" or "private" search. The trend is toward on-device personalization (like Apple's approach) that never sends user data to the server.

"Did you mean?" - spell correction

When a user types a query with no good results, search engines offer corrections. The standard approach:

Detect low-result query
→
Generate candidates (edit distance ≤ 2)
→
Rank by language model P(correction)

Show "Did you mean: X?"
$$P(\text{correction} \mid \text{query}) \;\propto\; P(\text{query} \mid \text{correction}) \cdot P(\text{correction})$$
Noisy channel model: P(typo|intended) × P(intended query). "Machien learning" → "machine learning"

05 Search Result Diversity

If a user searches "jaguar" and all 10 results are about the car, they'll never find what they wanted if they meant the animal. Diversity ensures the result set covers multiple interpretations and subtopics.

🎨

Analogy: A good playlist doesn't play 10 songs from the same artist back-to-back - even if that artist is your favorite. It mixes things up. Search diversity works the same way: it balances relevance with variety to maximize the chance that at least one result is what the user wanted.

MMR: Maximal Marginal Relevance

The most widely-used diversity algorithm. It greedily selects documents that are both relevant to the query and different from already-selected documents.

$$\text{MMR} = \arg\max_{d_i \in R \setminus S} \left[ \color{#ffd93d}{\lambda} \cdot \color{#6c63ff}{\text{Sim}_1(d_i, q)} - (1 - \color{#ffd93d}{\lambda}) \cdot \max_{d_j \in S} \color{#ff6b6b}{\text{Sim}_2(d_i, d_j)} \right]$$
\(\color{#6c63ff}{\text{Sim}_1}\) = relevance to query  •  \(\color{#ff6b6b}{\text{Sim}_2}\) = similarity to already-selected docs  •  \(\color{#ffd93d}{\lambda}\) = diversity tradeoff (0.5 – 0.7 typical)
\(R\) Candidate document set (e.g., top-100 from initial retrieval)
\(S\) Already-selected documents (starts empty, grows as we pick)
\(\color{#ffd93d}{\lambda}\) Tradeoff parameter. \(\lambda = 1\): pure relevance. \(\lambda = 0\): pure diversity.
\(\text{Sim}_1\) Query-document relevance (e.g., BM25 score, cosine similarity)
\(\text{Sim}_2\) Document-document similarity (penalizes redundancy)

Interactive: MMR re-ranking

MMR Diversity Tradeoff - Query: "jaguar"

λ = 1.0 → pure relevance ranking. λ = 0.0 → pure diversity. Drag to see the ranking change.

Why diversity matters

Ambiguous queries

"Apple" - company, fruit, or record label? Showing all three hedges your bets. Measured by α-NDCG which rewards covering multiple intents.

Subtopic coverage

"Machine learning" - tutorials, news, courses, tools, research papers. Even with a single intent, users benefit from seeing different facets of the topic.

Diversity algorithms comparison

Algorithm Approach Complexity Notes
MMR Greedy: pick doc maximizing λ·relevance − (1−λ)·max_similarity O(k·n) Most common in practice; simple and effective
xQuAD Explicit: model subtopics, cover each one O(k·n·m) Requires subtopic taxonomy; used in web search
PM-2 Proportional: allocate result slots proportional to subtopic importance O(k·n·m) Fairer coverage of minority intents
DPP Determinantal point processes: probabilistic diversity O(k³·n) Principled but computationally expensive
The diversity–relevance tradeoff

Too much diversity = irrelevant results sneak in. Too little = users with minority intents are poorly served. The sweet spot depends on query ambiguity: navigational queries need low diversity ("facebook login" has one intent), while informational queries benefit from high diversity ("python" has many meanings).

06 Multi-Modal Search

Traditional search is text-in, text-out. Multi-modal search breaks that boundary: search across text, images, audio, and video using a shared embedding space.

🔍

Analogy: Imagine a universal translator that converts everything - English, Japanese, sheet music, photographs - into the same language. Once everything speaks the same language, you can ask questions in one modality and get answers in another. That's what CLIP and similar models do for search.

CLIP: the breakthrough

CLIP (Contrastive Language-Image Pretraining) by OpenAI learns a shared embedding space for text and images by training on 400M image-text pairs from the internet.

$$\mathcal{L}_{\text{CLIP}} = -\frac{1}{N}\sum_{i=1}^{N}\left[\log \frac{e^{\text{sim}(\color{#6c63ff}{v_i}, \color{#00c9a7}{t_i})/\tau}}{\sum_{j=1}^{N} e^{\text{sim}(\color{#6c63ff}{v_i}, \color{#00c9a7}{t_j})/\tau}}\right]$$
\(\color{#6c63ff}{v_i}\) = image embedding  •  \(\color{#00c9a7}{t_i}\) = text embedding  •  \(\tau\) = temperature  •  Contrastive: pull matching pairs together, push non-matching apart

Encode queries and documents independently → store document embeddings in a vector DB → at query time, encode the query and do ANN (approximate nearest neighbor) search. This is fast because document encoding is done offline.

Visual search for e-commerce

How it works

User takes a photo of a product they like → system encodes the image → finds visually similar products in the catalog. Pinterest, Google Lens, Amazon StyleSnap all use this approach.

Challenges

Background clutter (user's photo vs studio photo), color matching (lighting variations), style vs exact match preferences, combining visual similarity with metadata (size, price, availability).

07 Real-Time Search

Traditional search indexes static data and queries it later. Real-time search flips the paradigm: data is continuously streaming in, and the system must make it searchable within seconds - or search against the stream with standing queries.

⚡

Analogy: Traditional search is like fishing with a net - you cast the net (query) into a pond (index) and pull up whatever's there. Real-time search is like setting a trap in a river - you define what you're looking for, and the system alerts you whenever a matching item flows past.

Two paradigms

Near-real-time indexing

New documents become searchable within seconds of arrival. Elasticsearch's default refresh interval is 1 second. Uses an in-memory buffer (translog) that's periodically flushed to disk segments.

Doc arrives
→
Buffer (translog)
→
Refresh (1s)
→
Searchable!
Percolator queries (reverse search)

Instead of indexing documents and querying them, you index the queries and match incoming documents against them. When a new document arrives, the percolator checks which stored queries it matches.

Register query
→
New doc arrives
→
Match against queries
→
Alert!

}

Challenges

Index refresh overhead

Frequent refreshes mean frequent segment creation → more merges → higher CPU/IO. Tuning refresh_interval is a tradeoff between latency and throughput.

Percolator scalability

With millions of registered queries, percolating a single document becomes expensive. Solutions: query pre-filtering (only test likely matches), sharding by query type, candidate generation using extracted terms.

Pro tip:

When asked "how would you build a real-time alerting system?" - the answer is: Kafka for ingestion → Elasticsearch with percolator queries for matching → notification service for delivery. Mention the tradeoff between percolator query count and match latency, and how to pre-filter queries using extracted terms.
