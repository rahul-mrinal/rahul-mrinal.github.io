Metadata and Fields in Search

Structure your index with the right field types

01 Why Fields Matter

A search index isn't a blob of text — it's a structured collection of fields, each with its own type and behavior. Just like a database table has columns with specific data types, a search index has fields that determine how data is stored, analyzed, and queried.

🗂️

Analogy: Think of a library card catalog. Each card has distinct fields: title (searchable text), author (exact keyword), Dewey number (numeric), and availability (boolean). You search the title field with fuzzy matching but filter the Dewey number with exact ranges. Different field types enable different operations.

Without Field Types

Everything is a text blob. Searching for price > 50 means string-matching on "50" inside text, catching "150", "503", and "50 states" — useless for actual filtering.

With Field Types

Price is numeric, category is a keyword, description is analyzed text. The engine knows exactly how to index, store, and query each one. Filters are instant and precise.

Metadata vs. Content

Documents in a search index typically have two kinds of data:

Content Fields

The actual searchable text: titles, descriptions, body text. These go through analysis pipelines and power full-text search.

Metadata Fields

Structured attributes: categories, prices, dates, booleans. These power filtering, sorting, faceting, and aggregation — the structured side of search.

{ "title": "Wireless Headphones Pro", ← content (text) "description": "Premium noise-cancelling...", ← content (text) "category": "Audio", ← metadata (keyword) "price": 349.99, ← metadata (numeric) "in_stock": true, ← metadata (boolean) "created_at": "2025-03-15T10:30:00Z" ← metadata (date) }

02 Field Types

The five fundamental field types in search engines. Each is optimized for different data structures, operations, and query patterns.

T

Text

Full-text search with tokenization, stemming, and relevance scoring. Used for titles, descriptions, body content.

K

Keyword

Exact-match, no analysis. Used for categories, tags, IDs, status values. Supports aggregation and sorting.

#

Numeric

Integer or float values for range queries and sorting. Used for price, ratings, counts, scores.

✓

Boolean

True/false values for binary filters. Used for in_stock, is_active, has_discount, is_published.

📅

Date

Temporal data for range queries and sorting by recency. Used for created_at, published_date, last_modified.

03 Search vs. Filter

Search and filtering are fundamentally different operations. Search finds relevant documents using text analysis and scoring. Filtering includes or excludes documents using exact criteria — no scoring involved.

AspectSearch (Query)Filter
OperationFull-text match with relevance scoringExact/range inclusion or exclusion
ScoringYes — results are ranked by relevanceNo — binary yes/no match
CachingNot cached (score varies per query)Cached (same filter = same bitset)
Field typesText fields (analyzed)Keyword, numeric, boolean, date
PerformanceSlower (scoring is expensive)Faster (bitset intersection)
Example"wireless headphones"price < 100 AND in_stock = true

Text fields pass through an analysis pipeline before indexing. This pipeline determines how raw text becomes searchable terms. Keyword fields skip this entirely — they're stored as-is.

Text Field Analysis

Input: "Running shoes for KIDS"

→ Tokenize: ["Running", "shoes", "for", "KIDS"]

→ Lowercase: ["running", "shoes", "for", "kids"]

→ Stop words: ["running", "shoes", "kids"]

→ Stemming: ["run", "shoe", "kid"]

Now a search for "kid's shoe" matches this document.

Keyword Field — No Analysis

Input: "Running Shoes"

→ Stored as: "Running Shoes"

Only an exact match "Running Shoes" works. "running shoes" does NOT match. This is intentional for categories, IDs, and enum values.

Tokenization

Tokenization splits text into individual terms (tokens). The standard tokenizer splits on whitespace and punctuation. Stemming reduces words to their root form: "running" → "run", "better" → "good". This allows matching across word forms.

Common Analyzer Types

Character Filters

Character filters pre-process the raw string before tokenization. Common uses include stripping HTML tags, mapping special characters (e.g., é → e), and normalizing unicode.

{ "char_filter": [ "html_strip", { "type": "mapping", "mappings": ["& => and", "+ => plus"] } ] }

Token Filters

Token filters transform individual tokens after tokenization. They run in order, and each filter's output feeds the next.

06 Multi-Field Strategy

Sometimes you need the same content indexed in multiple ways. A product name should be searchable (text field with analysis) and also sortable (keyword field for exact alphabetical sorting). Multi-field mappings solve this.

One Source, Multiple Views

Multi-field mappings let you index a single source field into multiple internal representations. The data is stored once but analyzed differently for each sub-field. This is far more efficient than duplicating the field in your source documents.

{ "name": { "type": "text", "analyzer": "standard", "fields": { "raw": { "type": "keyword" }, "autocomplete": { "type": "text", "analyzer": "edge_ngram" } } } }

Schema Design Rule of Thumb

If users type free-form queries against a field → make it text. If users select from a dropdown or toggle → make it keyword or boolean. If users drag a range slider → make it numeric or date.

Domain-Specific Schemas

E-Commerce

  • title → text (+ keyword for sorting)
  • description → text
  • brand → keyword (facet)
  • price → float (range filter)
  • rating → float (sort + filter)
  • color → keyword (multi-value facet)
  • in_stock → boolean

Knowledge Base / Docs

  • title → text (high boost)
  • body → text
  • author → keyword
  • tags → keyword (array)
  • updated_at → date (recency sort)
  • section → keyword (filter)
  • embedding → dense_vector

Common Anti-Patterns

Putting Everything in One Text Field

Concatenating title, description, category, and metadata into a single searchable blob. You lose the ability to boost title matches over body matches, filter by category, or sort by price.

Using Text Type for IDs

If a product SKU is indexed as text, the analyzer might tokenize "SKU-12345" into ["sku", "12345"]. A filter for SKU-12345 fails because the exact string doesn't exist in the index. Use keyword instead.

Over-Indexing Every Field

Making every field both searchable and filterable doubles your index size. Only enable search on fields users actually query, and only enable filtering on fields used for facets or range queries.

Ignoring Null Values

Documents with missing fields can cause unexpected behavior in aggregations and sorting. Define explicit null_value mappings or handle missing fields in your query logic.

Start Small, Iterate

Begin with the minimum viable schema — only the fields you need for your initial search experience. Adding new fields to an existing index is easy (in most engines). Changing field types requires a full reindex. Get the types right first, then expand coverage.

08 Key Takeaway

Fields Are Your API Contract

Your schema defines what operations are possible on your index. Choose field types intentionally: text for full-text search, keywords for exact filtering and facets, numerics for ranges, booleans for toggles, and dates for temporal queries. Get the schema right, and everything downstream — search quality, filtering performance, faceted navigation — falls into place.

The Five Questions

For every field in your schema, ask:

1. Will users search it?

If yes → text with an appropriate analyzer.

2. Will users filter it?

If yes → keyword, numeric, boolean, or date.

3. Will users sort by it?

If yes → keyword (alphabetical) or numeric/date (ordered).

4. Will users aggregate it?

If yes → keyword for term aggregations, numeric for stats.

5. Does it need to be stored at all?

Not every field needs to be in the search index. If it's only used for display (not search, filter, sort, or aggregate), consider storing it in your primary database and joining at display time.
