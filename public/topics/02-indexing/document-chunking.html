Document Chunking Strategies

Break documents into optimal pieces for search and retrieval

01 Why Chunk?

Modern language models and embedding models have finite context windows — typically 512 to 8,192 tokens. A 50-page research paper doesn't fit. Even if it did, cramming everything in dilutes relevance. Chunking solves both problems.

Context Window Limits

Embedding models like text-embedding-3-small truncate at 8,191 tokens. If your document is 20,000 tokens, 60% of it silently vanishes. Chunking ensures every piece gets properly embedded.

Precision vs. Context

Small chunks give precise matches but lose surrounding context. Large chunks preserve context but dilute the signal. The art is finding the sweet spot for your use case.

📖

Analogy: Imagine searching a library. If each "document" is an entire book, your search returns whole books — mostly irrelevant pages. If each "document" is a single sentence, you find the exact line but have no context. Chunking is like organizing by paragraphs or sections — the right granularity for useful results.

$$\text{Retrieval Quality} = f\bigl(\color{#6c63ff}{\text{chunk\_size}},\; \color{#00c9a7}{\text{overlap}},\; \color{#ff6b6b}{\text{boundary\_type}}\bigr)$$
All three parameters interact — optimizing one alone isn't enough

02 Fixed-Size Chunking

The simplest strategy: split text every N characters (or tokens), with optional overlap. Fast, deterministic, and surprisingly effective as a baseline.

Fixed-Size Chunking Playground

How It Works

The algorithm walks through the text with a sliding window of size chunk_size, stepping forward by chunk_size - overlap characters each time. Overlap ensures no information falls through the cracks at boundaries.

Pseudocode

def fixed_size_chunk(text, chunk_size, overlap):
    chunks = []
    start = 0
    while start < len(text):
        end = start + chunk_size
        chunks.append(text[start:end])
        start += chunk_size - overlap    # step forward
    return chunks

Pros

  • Dead simple to implement
  • Predictable, uniform chunk sizes
  • Works with any content type
  • No NLP dependencies

Cons

  • Splits mid-word and mid-sentence
  • No semantic awareness
  • Context loss at boundaries
  • Poor for structured content

03 Sentence-Based Chunking

Instead of splitting at arbitrary character positions (potentially mid-word), sentence-based chunking splits on natural sentence boundaries. This preserves grammatical coherence within each chunk.

How Sentence Detection Works

The simplest approach splits on period, question mark, and exclamation mark followed by whitespace. But real-world text has edge cases:

  • Abbreviations: "Dr. Smith" shouldn't split between "Dr." and "Smith"
  • Decimal numbers: "The price is $19.99" isn't two sentences
  • Ellipsis: "Wait... what?" has a single logical sentence
  • URLs: "Visit example.com for more" shouldn't split on the period

Production systems use NLP-based sentence tokenizers (e.g., spaCy, NLTK) that handle these cases. The playground below uses simplified regex rules for demonstration.

04 Paragraph-Based Chunking

Paragraphs are the most natural unit of thought in written text. Splitting on double newlines (\n\n) respects the author's original structure and typically produces semantically coherent chunks.

When Paragraphs Shine

Well-structured documents — technical docs, blog posts, research papers — naturally group related ideas into paragraphs. Paragraph-based chunking leverages this structure for free. It works especially well when combined with a max-size fallback for oversized paragraphs.

Paragraph-Based Chunking Playground

Pros

  • Preserves author intent
  • Usually semantically coherent
  • No mid-thought breaks
  • Simple to implement

Cons

  • Paragraph sizes vary wildly
  • Some paragraphs are too long
  • One-line paragraphs lose context
  • Doesn't work for non-prose (code, tables)

05 Semantic Chunking

Semantic chunking uses embedding similarity to detect topic shifts. Instead of splitting at fixed positions, it compares consecutive sentence embeddings and splits where similarity drops — indicating a topic change.

→
Split at Topic Shifts
$$\text{split at } i \;\text{ if }\; \text{sim}(\vec{s}_i, \vec{s}_{i+1}) < \color{#ff6b6b}{\theta}$$
Where \(\theta\) is the similarity threshold and \(\vec{s}_i\) is the embedding of sentence \(i\)

When to Use Semantic Chunking

  • Documents cover multiple topics within a single text
  • Topic boundaries don't align with paragraph breaks
  • You need the highest retrieval precision and can afford the embedding cost

Trade-offs

Semantic chunking requires an embedding model call for every sentence — making it 10–100x more expensive at indexing time than rule-based methods. It also introduces a tunable threshold parameter that must be calibrated per dataset.

Similarity Threshold Tuning

Low Threshold (θ = 0.3)
Many small chunks

Splits aggressively at every minor topic shift. High precision but fragmented context.

High Threshold (θ = 0.8)
Fewer large chunks

Only splits on major topic changes. Preserves context but may include off-topic sentences.

Recursive Chunking (Bonus)

A hybrid approach used by LangChain and similar frameworks. It tries a hierarchy of separators — first double newlines, then single newlines, then sentences, then characters — and only falls back to the next level when chunks exceed the maximum size.

The Sweet Spot

Most practitioners find that 200–500 tokens (roughly 150–400 words) works well for general-purpose retrieval. Specialized domains — legal, medical, code — often benefit from different ranges based on the natural structure of their content.

07 Overlap Strategies

Without overlap, important context at chunk boundaries is lost. A sentence that spans two chunks may be split in half, making neither chunk useful for retrieving that information.

Overlap Visualizer

See how increasing overlap shares more text between adjacent chunks. The yellow highlighted regions show text that appears in both the previous and current chunk.

Without Overlap — Information Loss

Consider the sentence: "The indexing pipeline processes documents and stores them in the search engine."

If chunk 1 ends at ...processes docu and chunk 2 starts at ments and stores..., neither chunk contains the full sentence. A query for "indexing pipeline" might miss this critical information.

Overlap: The Math

$$\text{Total chunks} = \left\lceil \frac{\color{#6c63ff}{N} - \color{#00c9a7}{O}}{\color{#6c63ff}{C} - \color{#00c9a7}{O}} \right\rceil$$
\(\color{#6c63ff}{C}\) = chunk size  ·  \(\color{#00c9a7}{O}\) = overlap  ·  \(\color{#6c63ff}{N}\) = total text length

Storage Overhead from Overlap

Overlap duplicates text across chunks, increasing storage and embedding costs. The overhead ratio is approximately:

$$\text{overhead} \approx \frac{\color{#00c9a7}{O}}{\color{#6c63ff}{C} - \color{#00c9a7}{O}}$$

At 20% overlap (e.g., 50 of 250 chars), overhead is ~25%. At 50% overlap, overhead is 100% (double the chunks). Choose wisely.

Sentence-Aware Overlap

Instead of overlapping by a fixed character count, overlap by whole sentences. This ensures the overlapping content is always a complete, coherent unit. The last 1–2 sentences of chunk N become the first 1–2 sentences of chunk N+1. This approach pairs naturally with sentence-based chunking.

When Overlap Helps Most

  • Documents with long, flowing prose
  • Topics that span natural boundaries
  • When retrieval recall matters more than cost
  • Fixed-size chunking (which has no semantic awareness)

When to Reduce Overlap

  • Documents with clear section boundaries
  • Short documents where each chunk covers a single topic
  • Cost-constrained environments (overlap increases storage + embedding costs)
  • Paragraph-based chunking (boundaries are already natural)

Hybrid Chunking

The most robust production systems use a two-pass approach: first split on structural boundaries (paragraphs, headings, code blocks), then enforce a maximum size by sub-splitting oversized chunks with overlap. This combines semantic coherence with predictable sizing.

Content-Specific Recommendations

Technical Documentation

  • Split by headings/sections first
  • Then sentence-based within sections
  • 256–512 tokens per chunk
  • Include heading text in every chunk for context

Legal / Regulatory Text

  • Split by clause or article number
  • Larger chunks (512–1024 tokens)
  • High overlap (20–30%) to preserve cross-references
  • Preserve section numbers in metadata

Source Code

  • Split by function/class/method
  • Include imports and docstrings
  • Preserve indentation and structure
  • Use AST-aware chunking when possible

Chat / Conversation Logs

  • Split by conversation turn or time gap
  • Keep speaker attribution with each chunk
  • Group related exchanges together
  • 100–300 tokens per chunk

09 Key Takeaway

Chunking is the Foundation

Every downstream component — embedding, indexing, retrieval, and generation — is affected by your chunking decisions. There's no universally "best" strategy. Start with sentence-based chunking at 200–400 tokens with 10–15% overlap, measure retrieval quality on your real queries, and iterate. The best chunking strategy is the one you've tested against your data.
