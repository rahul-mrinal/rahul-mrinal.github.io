01 Index Lifecycle

A search index is a living data structure. Documents flow in, get updated, become outdated, and eventually need to be removed. Understanding the full lifecycle — from schema creation to reindexing — is essential for maintaining a healthy search system.

Analogy: Think of an index like a warehouse inventory system. You set up the database schema (Create), add products to shelves (Index), update prices and quantities (Update), remove discontinued items (Delete), and periodically reorganize the entire warehouse for efficiency (Reindex).

02 Create

Creating documents means adding new entries to the index. Each document gets a unique ID and is processed through the analysis pipeline based on its field types.

Single Document Insert

Simple but slow for large datasets. Each insert triggers analysis, index updates, and optionally a refresh to make the document searchable.

POST /products/_doc/1
{
  "title": "Wireless Headphones",
  "price": 99.99,
  "in_stock": true
}

Bulk / Batch Insert

Send hundreds or thousands of documents in a single request. 10–100x faster than individual inserts because it amortizes network overhead and allows batch optimization.

POST /_bulk
{"index":{"_index":"products","_id":"1"}}
{"title":"Wireless Headphones","price":99.99}
{"index":{"_index":"products","_id":"2"}}
{"title":"USB-C Cable","price":12.99}
Batch Size Matters

Typical optimal batch sizes are 500–5,000 documents per bulk request. Too small and you waste overhead. Too large and you risk timeouts or memory pressure. Profile with your actual data to find the sweet spot.

03 Update

Documents in search indexes are immutable under the hood. An "update" actually deletes the old version and creates a new one. The distinction between partial and full updates is about what you send, not what happens internally.

Partial Update

Send only the fields you want to change. The engine merges them with the existing document. More convenient but still triggers a full re-index of the document internally.

POST /products/_update/1
{
  "doc": {
    "price": 89.99
  }
}

Full Document Replace

Send the complete document. Overwrites everything. Simpler mental model and avoids issues with stale fields, but requires you to have the full document available.

PUT /products/_doc/1
{
  "title": "Wireless Headphones",
  "price": 89.99,
  "in_stock": true
}

Important: Updates Are Not In-Place

Search engines use append-only data structures. When you "update" a document, the old version is marked as deleted, and a brand new version is written. This is why frequent updates to the same document can cause index bloat until a merge (compaction) occurs.

Update Strategies Comparison

AspectPartial UpdateFull Replace
Payload sizeOnly changed fieldsEntire document
Internal operationRead → Merge → ReindexDelete → Reindex
Risk of stale fieldsPossible if source divergesNone — always complete

Optimistic Concurrency

Use version numbers or sequence IDs to prevent lost updates. When updating, include the expected version — if another process updated the document first, the operation is rejected and you can retry with the latest version. This prevents the "last write wins" problem in concurrent systems.

# Update with version check (Elasticsearch)
PUT /products/_doc/1?if_seq_no=5&if_primary_term=1
{
  "title": "Updated Title",
  "price": 89.99
}

04 Delete

Removing documents from a search index isn't always straightforward. The two main strategies have different trade-offs for consistency, performance, and recoverability.

# Hard delete by ID
DELETE /products/_doc/42

# Delete by query (all out-of-stock items)
POST /products/_delete_by_query
{
  "query": { "term": { "in_stock": false } }
}

Hard Delete

Mark the document as deleted in the index. It stops appearing in search results immediately, but the physical space isn't reclaimed until the next segment merge.

  • Immediate removal from results
  • Irreversible (need a backup to restore)
  • Space reclaimed lazily during merge

Soft Delete

Set a deleted: true field on the document and add a filter to exclude deleted documents from all queries. The document remains in the index for auditing or recovery.

  • Recoverable (just flip the flag)
  • Requires query-level filtering
  • Index size grows without cleanup

06 The Reindex Problem

Sometimes you need to rebuild your entire index from scratch. This happens more often than you'd expect:

  • Schema changes — You need to add a new field type, change an analyzer, or restructure mappings. Most search engines don't allow changing field types on existing indexes.
  • Data model evolution — Your application grows, and the way you structure documents changes fundamentally.
  • Analyzer updates — You switch from the standard analyzer to a custom one with better stemming or synonyms.
  • Corruption recovery — After a hardware failure or bug, rebuilding from the source of truth is the safest path.
  • Performance optimization — Over time, heavy update/delete patterns cause index fragmentation that only a full rebuild can fix.

The Naive Approach (Don't Do This)

Delete the old index, create a new one, and start indexing. During the rebuild — which can take minutes to hours — your search is completely down. Users get errors or empty results.

07 Alias Swap Pattern

The alias swap pattern is the standard way to achieve zero-downtime reindexing. An alias is a pointer name that can be atomically switched from one index to another.

{ "actions": [ { "remove": { "index": "products_v1", "alias": "products" } }, { "add": { "index": "products_v2", "alias": "products" } } ] }

This is an atomic operation — both actions execute in a single transaction. No requests are dropped.

Why Aliases Are Essential

Without aliases, your application code contains hardcoded index names like products_v3. Every reindex requires a code deploy to change the name. With aliases, your app always references products, and the alias silently routes to whichever versioned index is active. Infrastructure change, zero code change.

Multi-Index Aliases

An alias can point to multiple indexes simultaneously. This enables use cases like:

Time-Based Sharding

A logs alias points to logs-2025-01, logs-2025-02, etc. Queries against the alias search all months. When a month rolls off retention, just remove it from the alias.

Write vs. Read Aliases

A products-write alias points to the current index for ingestion. A products-read alias points to a different index that's been optimized for queries. Data flows from write to read via a sync job.

08 Versioning Strategies

Beyond the basic alias swap, there are several strategies for managing index versions in production. The right choice depends on your data volume, change frequency, and tolerance for complexity.

Blue-Green Deployment

Maintain two complete environments (blue and green). At any time, one is live and one is idle. Reindex into the idle environment, test, then swap traffic. Provides a full rollback target.

  • Instant rollback capability
  • Full isolation for testing
  • 2x infrastructure cost

Rolling / Incremental

Instead of a full rebuild, incrementally update documents that have changed since the last index version. Uses a changelog or timestamp-based approach.

  • Much faster than full reindex
  • Lower resource overhead
  • Can't handle schema changes
  • Risk of drift over time
Naming Convention

Use a consistent naming pattern for versioned indexes: {name}_v{version} or {name}_{timestamp}. Examples: products_v7, products_20260404. The alias always stays the same: products. This makes it trivial to identify which version is active and when it was created.

# View alias → index mapping
GET /_alias/products

# Response: shows which versioned index the alias points to
{
  "products_v7": {
    "aliases": {
      "products": {}
    }
  }
}

2Create the new index with updated mappingsSchema changes only apply to new indexes

4Validate document counts and sample queriesCatch issues before they affect users

8Delete old index after validation periodReclaim resources
Automate Reindexing

In production, wrap the entire reindex workflow in a script or CI/CD pipeline. Include health checks, document count validation (new count should be within 1% of old), sample query comparison, and automatic rollback if validation fails. Manual reindexing at 2 AM is a rite of passage, but automating it is how you sleep soundly.

10 Key Takeaway

Treat Your Index Like a Deployment

Search indexes are not static databases — they're living systems that evolve with your application. Master the CRUD operations for day-to-day management, but invest early in alias-based reindexing for zero-downtime schema migrations. The alias swap pattern is the single most important operational pattern in search engineering. Learn it, automate it, and never take your search down for maintenance again.

Quick Reference Card

Do

  • Always use aliases, never point apps at versioned index names
  • Batch inserts for bulk operations (500–5K per batch)
  • Use optimistic concurrency control for updates
  • Automate the entire reindex workflow in CI/CD
  • Validate document counts and sample queries before swapping
  • Keep old indexes for 24–48h post-swap for rollback

Don't

  • Delete and recreate indexes for schema changes
  • Point applications directly at products_v3
  • Update millions of documents one at a time
  • Skip validation before alias swap
  • Ignore segment merge overhead from heavy update patterns
  • Forget to monitor error rates after a swap
