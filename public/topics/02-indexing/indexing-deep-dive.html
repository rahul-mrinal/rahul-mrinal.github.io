Indexing: Deep Dive

From brute-force scanning to inverted indexes, chunking strategies, and field types - everything you need to know

01 What is Indexing?

Imagine you have 10 million documents and a user types a query. You could open every single document, read every single word, and check for matches. But that's insane. Indexing is the process of building data structures ahead of time so that queries can be answered in milliseconds instead of hours.

📖

Analogy: Think of the index at the back of a textbook. When you want to learn about "binary search," you don't read the entire 800-page book. You flip to the index, find "binary search → page 247," and go directly there. A search index does the same thing for every word across millions of documents.

The brute-force disaster

Without an index, you must scan every document for every query. The time complexity is:

$$\color{#ff6b6b}{T_{\text{brute}}} = \mathcal{O}(\color{#ffd93d}{N} \times \color{#6c63ff}{M})$$
\(\color{#ffd93d}{N}\) = number of documents  •  \(\color{#6c63ff}{M}\) = average tokens per document
How bad is this?

If you have 10 million documents averaging 1,000 tokens each, every query scans 10 billion tokens. At 1 GHz processing speed, that's ~10 seconds per query. With 100 queries/second, you'd need 1,000 servers just for brute force.

With an index

An index pre-processes all documents into a lookup structure. Now a query for "binary search" just looks up those terms in the index and immediately gets back a list of matching documents:

$$\color{#00c9a7}{T_{\text{indexed}}} = \mathcal{O}(\color{#6c63ff}{|q|} \times \color{#ffd93d}{\overline{L}})$$
\(\color{#6c63ff}{|q|}\) = number of query terms  •  \(\color{#ffd93d}{\overline{L}}\) = average posting list length (documents containing the term)
The speedup is enormous.

Instead of scanning 10 billion tokens, you look up 2-3 query terms in a hash map and intersect posting lists with maybe 50,000 entries each. That's microseconds, not seconds. A reduction of 5-6 orders of magnitude.

Types of indexes in search

Index Type What It Stores Used For
Inverted Index Term → list of documents Full-text keyword search (BM25)
Vector Index Document → dense embedding Semantic / similarity search (ANN)
Columnar Index Field → sorted values Filtering, faceting, sorting
Geospatial Index Coordinates → regions Location-based queries
B-Tree / LSM Key → value Exact key lookups, range queries

In this masterclass, we'll focus on the inverted index (the backbone of search) and how documents are prepared, chunked, and stored for retrieval.

02 The Inverted Index

The inverted index is the single most important data structure in information retrieval. It's what makes Google, Elasticsearch, and every search engine fast.

Forward index vs. inverted index

A forward index maps documents to terms. An inverted index flips this - it maps terms to documents.

Forward Index

Document → terms it contains

Doc 1 → [the, cat, sat, on, the, mat]
Doc 2 → [the, dog, sat, on, the, cat]
Doc 3 → [the, cat, and, the, dog]

To find "cat" → must scan ALL docs. Slow!

Inverted Index

Term → documents containing it

"cat" → [Doc 1, Doc 2, Doc 3]
"dog" → [Doc 2, Doc 3]
"mat" → [Doc 1]
"sat" → [Doc 1, Doc 2]

To find "cat" → instant lookup. Fast!

How it's built - step by step

1. Tokenize
→
2. Normalize
→
3. Build Posting Lists
→
4. Store & Compress
Step 1: Tokenize

Split the raw text into individual tokens (words). Handle punctuation, hyphens, special characters.

"Machine Learning is AMAZING!"  →  ["Machine", "Learning", "is", "AMAZING"]
Step 2: Normalize

Lowercase, stem/lemmatize, remove stop words. This ensures "Running" and "run" map to the same entry.

["Machine", "Learning", "is", "AMAZING"]
  → lowercase → ["machine", "learning", "is", "amazing"]
  → remove stops → ["machine", "learning", "amazing"]
Step 3: Build Posting Lists

For each unique term, record which document it appeared in and how many times (term frequency). Optionally record positions for phrase queries.

Posting list anatomy

Each term in the inverted index points to a posting list - an ordered list of document references:

Inverted Index with Term Frequencies
machine →
D1tf:3 D4tf:1 D7tf:5
learning →
D1tf:2 D3tf:1 D7tf:4 D9tf:1
neural →
D3tf:2

Positional indexes for phrase queries

If a user searches for "machine learning" (in quotes - a phrase query), we need to know not just which documents contain both words, but where they appear. A positional index stores token positions:

Positional Inverted Index
machine →
D1: pos [0, 14, 28] D4: pos [7]
learning →
D1: pos [1, 15] D4: pos [8]

To verify the phrase "machine learning", we check: does any document have machine at position p and learning at position p+1? In D1, positions 0 and 1 match. In D4, positions 7 and 8 match. Both documents contain the exact phrase.

03 Document Chunking

Most real-world documents are far too long to index as a single unit. A 50-page PDF, a long blog post, a legal contract - these need to be broken into smaller pieces called chunks before indexing.

Why we chunk

Token limits

Embedding models (for vector search) have max token limits (512, 8192, etc.). A 20,000-word document simply can't be embedded as one unit.

Relevance dilution

If a document has one relevant paragraph buried in 50 pages of unrelated text, the overall document score gets diluted. Smaller chunks let that one paragraph shine.

Better retrieval precision

Returning a specific chunk lets the reader (or LLM) find the exact answer faster than returning an entire 50-page document.

Memory & speed

Processing smaller chunks is faster and uses less memory at query time. Especially important for reranking and LLM context windows.

Chunking strategies

Strategy How It Works Pros Cons
Fixed-size Split every N characters/tokens Simple, predictable chunk sizes Cuts mid-sentence, breaks context
Sentence-based Split on sentence boundaries Preserves sentence meaning Uneven sizes, some sentences are tiny
Paragraph-based Split on double newlines / paragraphs Preserves topical coherence Huge variance in paragraph size
Semantic Use embeddings to detect topic shifts Best semantic coherence Expensive, requires embedding model
Recursive Try paragraph → sentence → fixed-size fallback Best of all worlds More complex implementation

Overlap between chunks

When you split text at a boundary, context at the edges is lost. Overlap solves this by including some text from the previous chunk at the start of the next chunk:

Chunking with Overlap (chunk_size=100, overlap=20)
Chunk 1 (chars 0–100)
The quick brown fox jumps over the lazy dog. Machine learning is a subset of artificial intelligence...
Chunk 2 (chars 80–180)
overlap ...artificial intelligence that enables computers to learn from data without being explicitly...
Chunk 3 (chars 160–260)
overlap ...being explicitly programmed. Deep learning is a further subset that uses neural networks with...

Chunk size tradeoffs

Too small (< 100 tokens)

Chunks lack context. "It increased by 50%" - what increased? The chunk doesn't know. Embeddings are poor because there's not enough signal. Lots of chunks = slower retrieval.

Too large (> 2000 tokens)

Relevance dilution returns. A chunk covers multiple topics, so BM25/vector scores are averaged across unrelated content. May exceed embedding model limits.

Sweet spot: 200–800 tokens

Most practitioners find chunks of 200-800 tokens work best. This is roughly 1-4 paragraphs - enough context to be meaningful, small enough to be precise. Common defaults: 512 tokens for embedding models, 256-500 for BM25.

04 Metadata & Fields

Documents aren't just blobs of text. They have metadata - structured attributes like category, date, author, price, or tags. How you store and index these alongside the text content is critical for building useful search.

What is metadata?

🏷️

Analogy: Metadata is like the label on a jar. The text content is the stuff inside the jar (the actual food). The label tells you the brand, price, expiration date, and ingredients - you don't need to taste the food to filter by these attributes. Similarly, metadata lets you filter, sort, and facet without full-text searching the content.

Use case: eCommerce product

Here's how a product document looks with metadata fields in a search engine like Elasticsearch:

{
  "title": "Sony WH-1000XM5 Wireless Headphones",
  "description": "Industry-leading noise canceling headphones with Auto NC Optimizer, crystal-clear hands-free calling, and up to 30 hours of battery life...",
  "price": 348.00,
  "category": "Electronics > Audio > Headphones",
  "brand": "Sony",
  "rating": 4.7,
  "in_stock": true,
  "tags": ["wireless", "bluetooth", "noise-canceling"],
  "created_at": "2024-05-15T10:30:00Z"
}

How metadata fields are stored

Metadata fields are stored separately from full-text content in a search index. Each field type has its own optimized storage:

Field Storage Operations Supported
title Inverted index (analyzed) Full-text search, BM25 scoring
description Inverted index (analyzed) Full-text search, BM25 scoring
price BKD tree (numeric) Range queries, sorting, aggregations
category Keyword index (not analyzed) Exact match filtering, faceting
brand Keyword index (not analyzed) Exact match, aggregations
rating BKD tree (numeric) Range filtering, sorting
in_stock Boolean field Exact match filtering
tags Keyword index (multi-value) Exact match, facet counts
created_at BKD tree (date) Date range queries, sorting

Filtered search vs. full-text search

Full-text search

User types free-form text. The engine tokenizes the query, looks up terms in the inverted index, and scores documents by relevance (BM25).

Query: "wireless noise canceling headphones"
→ Uses: inverted index on title + description
→ Returns: ranked by relevance score
Filtered search

User selects structured constraints (price range, brand, category). The engine uses metadata indexes for fast exact filtering - no scoring needed.

Filter: brand = "Sony"
         AND price < 400
         AND in_stock = true
→ Uses: keyword + numeric indexes
→ Returns: all matching docs (no ranking)
The real power: combining both

In practice, search queries combine full-text and filters: "wireless headphones" with filters brand=Sony, price < $400, in_stock=true. The engine first applies the filter (cheap bitset operation), then runs BM25 only on the filtered subset. This is dramatically faster than scoring all documents and filtering afterward.

Why metadata matters for RAG pipelines

In Retrieval-Augmented Generation (RAG), metadata is crucial for:

Pre-filtering Only retrieve chunks from specific sources, date ranges, or categories before running vector search
Source attribution Every chunk carries its source document ID, page number, URL - essential for citations in LLM responses
Access control Metadata fields like department or access_level enable permission-based retrieval
Freshness Sort or filter by updated_at to prefer recent information over stale data

05 Keyword Fields vs. Text Fields vs. Vector Fields

Understanding the three fundamental field types is essential for designing search indexes. Each type is optimized for a different kind of query.

Keyword

Stored as-is, not analyzed. Used for exact matching, filtering, sorting, and aggregations.

Input:
"New York City"
Indexed as:
New York City
Matches:
✓
"New York City"
✗
"new york"
✗
"York"

Text (Analyzed)

Tokenized, lowercased, stemmed. Used for full-text search with BM25 scoring.

Input:
"New York City"
Indexed as:
[new, york, city]
Matches:
✓
"new york"
✓
"York"
✓
"city"

Vector (Dense)

Dense float array from embedding model. Used for semantic similarity via ANN search.

Input:
"New York City"
Indexed as:
[0.12, -0.87, 0.34, ...]
Matches:
✓
"Big Apple"
✓
"NYC"
✓
"Manhattan"

When to use which

Aspect Keyword Text (Analyzed) Vector
Query type Exact match, filter, facet Full-text search Semantic similarity
Scoring None (binary match) BM25 Cosine / dot product
Analysis None Tokenize + normalize Embedding model
Storage cost Low Medium High (768-1536 floats/doc)

Elasticsearch / OpenSearch mapping example

Here's a real-world mapping showing all three field types in action:

PUT /products
{
  "mappings": {
    "properties": {
      // TEXT field - analyzed, full-text searchable
      "title": {
        "type": "text",
        "analyzer": "standard",
        "fields": {
          // Sub-field: keyword copy for sorting/aggs
          "keyword": { "type": "keyword" }
        }
      },

      // TEXT field - analyzed for BM25 search
      "description": {
        "type": "text",
        "analyzer": "english"
      },

      // KEYWORD field - exact match only
      "brand":    { "type": "keyword" },
      "category": { "type": "keyword" },
      "tags":     { "type": "keyword" },

      // NUMERIC fields - range queries, sorting
      "price":  { "type": "float" },
      "rating": { "type": "float" },

      // BOOLEAN field - filtering
      "in_stock": { "type": "boolean" },

      // DATE field - time-based filtering
      "created_at": { "type": "date" },

      // VECTOR field - semantic search via embeddings
      "description_embedding": {
        "type": "dense_vector",
        "dims": 768,
        "index": true,
        "similarity": "cosine"
      }
    }
  }
}
Key insight: multi-field mappings

Notice that title has both a text type and a keyword sub-field. This is a common pattern - the text version is used for full-text search, and the keyword version is used for sorting and aggregations. Index the same data twice with different analyzers for different use cases.

06 Index Operations

Creating an index is just the beginning. In production, you need to understand how documents flow in and out, how the index stays fresh, and how to evolve the schema without downtime.

Refresh interval & near-real-time (NRT) search

When you index a document, it doesn't become searchable immediately. Search engines use a buffer-and-flush model:

In-memory buffer New documents land in an in-memory buffer first. Not yet searchable.
Refresh Periodically (default: every 1 second in Elasticsearch), the buffer is flushed to a new segment on disk. Now the documents are searchable.
Flush / Commit The translog is cleared and all data is safely persisted. Happens less frequently.
$$\text{Search latency after indexing} \approx \text{refresh\_interval} = \color{#00c9a7}{1\text{s (default)}}$$
Documents become searchable within ~1 second of indexing (NRT)
Tuning refresh intervals

Bulk indexing: Set refresh_interval=-1 during bulk loads. Refreshing after every batch wastes I/O. Do one final refresh when done.

Real-time dashboards: Keep 1s (default) for near-instant visibility.

Logs/metrics: Set to 30s or 60s - freshness matters less, throughput matters more.

Segment merging

Each refresh creates a new segment - an immutable mini-index. Over time, you accumulate hundreds of small segments. Searching across many segments is slow, so the engine periodically merges them:

Segment Merge Process
Seg 0
50 docs
Seg 1
30 docs
Seg 2
45 docs
Seg 3
20 docs
⟹
Merged Segment
145 docs
Why segments are immutable

Segments are never modified after creation - only merged into new segments. This means "deleting" a document just marks it as deleted (a tombstone). The actual data is cleaned up during the next merge. This immutability enables lock-free concurrent reads and makes crash recovery simple.

Index aliases: zero-downtime reindexing

What happens when you need to change the schema? You can't modify an existing mapping (e.g., change a field from text to keyword). The solution: index aliases.

1. Create new index (v2)
→
2. Reindex all docs into v2
→
3. Swap alias atomically
→
4. Delete old index
// Your app always queries the alias, never the index directly
POST /_aliases
{
  "actions": [
    { "remove": { "index": "products_v1", "alias": "products" } },
    { "add":    { "index": "products_v2", "alias": "products" } }
  ]
}
// This is ATOMIC - zero downtime, no missed queries

Schema evolution

Change Can You Do It In-Place? Solution
Add a new field Yes Dynamic mapping adds it automatically
Change field type No Reindex with alias swap
Change analyzer No Reindex with alias swap
Delete a field Sort of Field stays in mapping but reindex to reclaim space
Rename a field No Add alias or reindex
Add sub-fields Yes Update mapping, reindex existing docs

07 Practical Considerations

Designing indexes for production requires thinking about data volume, query patterns, and infrastructure. Here are the guidelines that matter.

Index size estimation

A rough formula for estimating index size on disk:

$$\color{#6c63ff}{\text{Index Size}} \approx \color{#ffd93d}{\text{Raw Data}} \times \color{#00c9a7}{\text{Overhead Factor}}$$
Overhead factor depends on field types: text ~1.5x, keyword ~1.1x, dense_vector ~4x (768-dim float32 = 3KB/doc)
Example estimation
Raw documents 10 million products, ~2KB each = 20 GB raw
Text fields title + description indexed and stored: ~30 GB
Keyword fields brand, category, tags: ~3 GB
Numeric fields price, rating: ~0.5 GB
Vector field (768d) 10M × 3KB = ~30 GB
Total estimate ~63.5 GB (about 3.2x raw data)

Shard sizing guidelines

In Elasticsearch/OpenSearch, each index is divided into shards. Shard sizing is one of the most important production decisions:

Too many small shards

Each shard has overhead (memory for segment metadata, thread pools). 1,000 shards × 100MB each = 100GB of data but enormous cluster overhead. The cluster master chokes managing metadata.

Too few large shards

A single 500GB shard takes forever to recover after a node failure. Reindexing is slow. No parallelism for queries - one shard = one thread.

The sweet spot
Shard size 10–50 GB per shard (Elastic's official recommendation)
Shard count Total data ÷ target shard size. For 200GB → 4-20 shards.
Shards per node Keep under ~20 shards per GB of heap. With 32GB heap → max ~640 shards per node.
Replicas 1 replica (default) doubles storage but provides fault tolerance and read throughput.

One index vs. multiple indexes

Pattern When to Use Example
Single index Homogeneous data, same schema, queried together All products in one products index
Index per type Different schemas, rarely queried together products, reviews, users
Index per time period Time-series data with retention policies logs-2024-01, logs-2024-02, ...
Index per tenant Multi-tenant SaaS with isolation needs tenant-abc-products, tenant-xyz-products

Time-series vs. catalog indexes

Catalog indexes

Products, users, articles. Documents are updated in place. Index is long-lived. Size grows slowly. Schema is stable.

Strategy: Single index with aliases. Shard count set once. Use reindex + alias swap for schema changes.

Time-series indexes

Logs, metrics, events. Documents are append-only (never updated). Data is time-partitioned. Old data is deleted or archived.

Strategy: Index per time period (daily/weekly). Use ILM (Index Lifecycle Management) to automatically rollover, warm, and delete old indexes.

Quick decision framework
< 1M docs 1 shard is fine. Don't overthink it.
1M–100M docs Start with 2-5 primary shards. Add replicas for HA.
100M+ docs Shard based on 30-50GB target size. Consider time-based indexes if applicable. Monitor heap and segment counts.
Multi-field search Use BM25F (field-boosted) with text + keyword sub-fields. Add vector field for hybrid search.

Quick Reference

Q: What is an inverted index?

A data structure that maps terms to the documents containing them - the reverse of a forward index. It's what makes full-text search fast: O(1) term lookup instead of O(N) document scan.

Q: Why do we chunk documents?

Token limits on embedding models, relevance dilution in long documents, faster retrieval, and better precision when returning results to users or LLMs.

Q: Keyword field vs. text field?

Keyword: stored verbatim, used for exact match/filter/sort/agg. Text: analyzed (tokenized, lowercased, stemmed), used for full-text search with BM25 scoring.

Q: How does near-real-time search work?

New documents go to an in-memory buffer, then flushed to a searchable segment every refresh_interval (default 1 second). Not instant, but fast enough for most use cases.

Q: How do you handle schema changes without downtime?

Index aliases. Create a new index with the new mapping, reindex all data, then atomically swap the alias from old to new index. Your application code never changes - it always queries the alias.

Indexing: The foundation of every search system - from Elasticsearch and Apache Lucene to Pinecone and modern RAG pipelines.

Master the fundamentals and every search technology becomes intuitive.
